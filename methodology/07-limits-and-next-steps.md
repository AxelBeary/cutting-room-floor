# 07 局限与可改进方向（诚实说：这是把 OWASP 做全，不是发明）

> 本篇属于《敏感字段的暴露面最小化》系列第 07 段。收尾不喊口号，只把这套做法"现在还立不住在哪、要立得更硬还差什么"讲清楚。
> 时点护栏：取自 Inkglean 实现快照（2026-09-前），不表示当前仍如此

## 当前这套做法的真实局限

1. **仍是应用层的约定，靠人自觉。** 安全列清单常量、类型二分、出口裁剪，全都依赖"下一个改代码的人引用了常量、没绕过它"。一次不经意的 `SELECT *` 或手写返回，就能把某条防线拆掉，而它不会自己报警。
2. **没有机器强制。** 目前没有任何静态规则禁止"绕过安全列清单"，也没有 CI 门禁阻止"新增字段未经登记就出现在某端点响应里"。防漂移全靠 code review 的注意力。
3. **逆泄露断言的覆盖 = 测试用例的覆盖。** 新加一个非管理端出口却忘了配断言，这个出口就处于无保护状态，且测试全绿不会提示你。
4. **"值不出现在任意位置"有盲区。** 它只对"明文原样出现在响应体里"的值有效；对编码后（Base64/URL 编码）、格式化后（补零、改分隔符）、或派生值（由敏感值算出的哈希、截断前缀）不敏感。它比只看键宽一层，但不等于语义级的信息流分析。
5. **单系统闭环不等于普适范式。** 在一个不大的模块里把几件事凑齐，迁移到跨服务、多团队、共享 DTO 的大系统时，"安全列清单归谁维护""端点×字段矩阵怎么合并"都是未解的工程问题，本篇没碰。

## 若要升格为"少见的范式"，需要补的机器强制（当前均未做，如实列为方向）

要把上面第 1、2、3 条从"靠人"变成"靠工具"，缺的是这几样——**本案例都没实现，只作为可改进方向如实登记，不当已完成的卖点**：

1. **静态规则禁绕过**：写 ESLint / Semgrep 规则，禁止对敏感表使用 `SELECT *`、禁止在非管理端函数里引用"含敏感列类型"、禁止出口对象出现未登记的敏感字段名。让"绕过安全列清单"在 lint 阶段就红。
2. **端点 × 字段可见性矩阵快照 + PR 阻断**：从代码自动生成"每个端点实际会输出哪些字段"的矩阵快照，纳入版本控制；PR diff 里若出现"某端点新增了一个未登记的可见字段"，直接阻断合并。这把"字段悄悄多返回一个"从"没人注意到"变成"CI 拦下"。
3. **变异测试证断言有效**：故意往某端点注入一个敏感字段（变异体），验证对应的逆泄露断言真的变红。用变异分数证明"全绿"不是因为断言是空真——把第 03 段的"正向对照"思想从人工升级成机器穷举。
4. **下沉到数据库层**：把列白名单从应用查询串下沉为数据库视图 / 列级 `GRANT`，让应用即便写错查询也拿不到敏感列（把防线从"约定"升级成"权限"）。
5. **集中式序列化拦截**：用框架级的全局拦截器（如统一 `@Exclude` + 显式 `@Expose`）替代"每个出口手写白名单"，减少"漏一个出口"的面。

做完 1–3 并积累"它真的拦住了多少次未登记字段新增"的对照数据之后，这套做法才谈得上从"一次完整落地"升格为"可推广的少见范式"。**当前没做，所以本篇的诚实结论停在下一句。**

## 一句话收束

这篇不是提出新防泄露机制的论文，而是**把 OWASP API3 在举报/审核模块里做全、并把每个零件的公开来历逐条交代清楚**的一份可照着做的教学案例。它的价值上限就是"完整 + 诚实"这两个词——超出这两点的任何"首创""新范式"表述，都是本篇明确拒绝的。
