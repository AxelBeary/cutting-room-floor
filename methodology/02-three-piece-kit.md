# 02 三件套：安全列清单常量 / 类型二分 / 管理端显式重附

> 本篇属于《敏感字段的暴露面最小化》系列第 02 段。承接第 01 段的"按构造"，这段讲它落到工程上是哪三件互相咬合的事。字段/类型/常量名均为去标识的教学命名。
> 时点护栏：取自 Inkglean 实现快照（2026-09-前），不表示当前仍如此

光有"这次别选敏感列"的一句自觉，撑不过下一次改动。要让它可维护、可审计，本案例用了三件套，分处 SQL、类型、序列化三层，任一层都被另一层兜住。

## 件一：安全列清单常量（SQL 层）

把"非管理端读路径统一允许查哪些列"提成**一份常量**，所有非管理端读函数都引用它，而不是各写各的列：

```text
// 一份事实源：非管理端读路径共用的安全列清单常量，刻意不含来源标识列
SAFE_MESSAGE_COLS = "id, 画师 ID 列，昵称列，留言内容列，语言列，状态列，画师回复列，画师回复时间列，created_at"

// 所有非管理端读函数引用该常量，而非各写各的列
getMessageById(id)   = SELECT <SAFE_MESSAGE_COLS> FROM messages WHERE id = ?
getPublicMessages(..) = SELECT <SAFE_MESSAGE_COLS> FROM messages WHERE status = approved ...
getMyMessages(..)     = SELECT <SAFE_MESSAGE_COLS> FROM messages WHERE 画师 ID 列 = ? ...
```

要点：
- **单点收敛**：新增/调整可读列只改这一处，三条读路径同时生效，不会出现"这条改了那条没改"的分叉。
- **默认安全**：表上新加敏感列时，它不在清单里，三条路径一起把它挡在外面。
- **管理端例外，且是显式的**：管理员做纠纷取证时确实要看来源标识，所以有**另一条**管理端读路径，那里才用全列（`SELECT m.*`）。关键是把"用全列"这件事**限制在管理端读路径这一处**，而不是全局默认。

> 注：别把"统一常量"讲神了。本案例里"安全列清单"确实是单一常量复用；但另有一处长度钳制的上限值并非"全局唯一定义复用"（见第 04 段的诚实修正）——"某物被提成常量"不代表"所有相关常量都被统一"。

## 件二：类型二分（编译期）

SQL 不选敏感列，只保证运行时取不到；但如果有人日后绕过常量、另起一句查询，运行时防线就破了。第二件套把"能不能携带这个字段"编码进**类型系统**：把同一张表的行拆成两种类型——

```text
// 非管理端口径：类型里就没有来源标识字段
type Message = { id, 画师 ID 列，昵称列，留言内容列，语言列，状态列，画师回复列，画师回复时间列，created_at }

// 管理端口径：只有这个类型才带来源标识，且继承自 Message
type 管理端专用类型 = Message & { 来源标识列：string | null }
```

于是：
- 所有非管理端读函数的返回类型是 `Message`，它的字段集里根本没有 `source_ip`；
- 想把一个 `MessageWithSource` 直接返回给公开/画师端点，类型上就对不上；
- 想访问 `message.source_ip` 而当前变量是 `Message` 类型，编译期就报错，逼你显式处理"这是管理端才有的数据"。

这一步把"防泄露"从"运行时的数据事实"升级成"编译期的类型事实"——正是按构造精神的延伸：让错误的写法无法通过类型检查，而不是运行时祈祷没人写错。

> 这一步也不是本案例原创：TypeORM 的 `select: false` + 需要时 `addSelect` 显式重选、NestJS 的 `@Exclude()` + `class-transformer`、PostgreSQL 的列级 `GRANT`、Hasura/PostGraphile 把列权限编译进 SQL，都是"默认不暴露、要暴露得显式声明"的框架级同构物（见第 05 段）。

## 件三：管理端显式重附（序列化层）

前两件守住"读路径",第三件守"出口怎么序列化"。做法是**响应 DTO 默认就裁掉敏感列**，管理端点若确实要某个敏感字段，在默认裁剪之后**再显式把它一个个重附回去**：

```text
// 默认裁剪：出站对象只列白名单字段（第二道口径护栏）
// 逐字段列举，不含敏感列
到站字段逐个列举 (m) = { id, 昵称列:m.昵称列，留言内容列:m.留言内容列，... }   

// 管理端点：默认裁剪后，再显式重附个别取证字段
管理端响应对象 = { ...到站字段逐个列举 (m), 来源标识列:m.来源标识列 }
```

为什么"默认裁剪 + 显式重附"而不是"默认全给 + 显式剔除"：
- 前者是**白名单**——要暴露什么得点名，新加的敏感字段默认落在裁剪之外；
- 后者是**黑名单**——要藏什么得点名，新加的敏感字段默认落在暴露之内。
- 安全方向上，默认值必须是"关"，不是"开"。这与 Django REST 那句"禁用 `exclude` 黑名单、要用 `fields` 白名单"是同一个道理，只是这里是输出侧的翻版。

## 三件套怎么互锁

| 层 | 机制 | 破了会怎样 | 由谁兜 |
|---|---|---|---|
| SQL | 安全列清单常量 | 有人绕过常量另起查询 | 类型二分（返回类型不带该字段） |
| 类型 | 拆"不含/含敏感列"两类型 | 有人强转/新建带该字段的分支 | 出口 DTO 默认裁剪 |
| 序列化 | 白名单裁剪 + 管理端显式重附 | 裁剪漏了一个出口 | 逆泄露断言（第 03 段）测试兜底 |

三层各有一道独立防线，任何一层被无意写破，下一层仍在。最后再靠测试层（第 03 段）把"三层同时失守"这种最坏情况钉进 CI。这套"多层默认关、逐层显式开"的取向，就是 OWASP API3 在举报/审核模块里的完整落地——三件都是标准件，价值在把它们凑齐并互锁。
