# 01 按构造防泄露 vs 出口剔除：为什么"先查全部再删"迟早会漏

> 本篇属于《敏感字段的暴露面最小化》系列第 01 段。字段名与标识符均为去标识的教学命名。
> 时点护栏：取自 Inkglean 实现快照（2026-09-前），不表示当前仍如此

## 从一个真实的痛点说起

一个系统里最容易发生、又最难被发现的合规事故，往往不是被人攻破，而是：

> 某天有人在敏感表上加了一列（比如"来源标识"），而某个接口的查询是 `SELECT *`——于是这个新列顺着老接口，被原封不动地返回给了不该看到它的人。没有人"决定"要泄露它，泄露只是序列化的默认行为。

OWASP 把这类问题归进 API3（Excessive Data Exposure）：后端图省事，把数据库对象整块 `to_json` 吐出去，指望前端"反正我不显示这个字段"。前端不显示 ≠ 前端拿不到；拿到的东西就在浏览器网络面板里，人人可看。

## 两种防泄露思路

面对"敏感列不能出现在响应里"，有两条路：

### 反例：出口剔除（egress trimming / 黑名单）

```text
row = SELECT * FROM messages WHERE id = ?     // 先查全部
delete row.来源标识列                          // 出口处逐个删敏感列
return row
```

或者反过来维护一个"敏感列黑名单"，序列化时把黑名单里的列剔掉。

它的失效模式有三条，每一条都会真实发生：
1. **加列即泄露**：黑名单/删除语句是"针对已知敏感列"写的。表上新加一列敏感数据时，没人记得回来补这里——新列默认就是"非敏感"，直接漏出去。
2. **漏一个出口即泄露**：剔除逻辑散落在每个返回路径上。少写一个出口（比如写操作的回显、某个新加的内部调用），那个出口就是全列泄露。本案例的真实教训正是：改读路径时漏了写路径的回显，两者是同级泄露面。
3. **删不干净**：黑名单删的是"键"，但同一个值可能被复制、拼进别的字段、嵌套在别的结构里，`delete row.x` 删不掉出现在 `row.summary` 文本里的 x。

### 正例：按构造防泄露（by construction / 白名单）

```text
// 非管理端读路径共用的"安全列清单常量"，刻意不含来源标识列
SAFE_MESSAGE_COLS = "id, 画师 ID 列，昵称列，留言内容列，语言列，状态列，画师回复列，画师回复时间列，created_at"

row = SELECT <SAFE_MESSAGE_COLS> FROM messages WHERE id = ?   // SQL 根上就不选敏感列
return row
```

差别在于：**敏感列不是"查出来再删掉"，而是"从来没被查询选中过"**。数据在 SQL 层就没进内存，出口自然无从泄露。加新列时，除非有人主动把它写进这份列清单，否则它在非管理端读路径上永远取不到——默认是"安全"的，而不是"默认泄露"。

一句被写进代码注释、值得单独抄出来的判据：

> 不用"SELECT * 再在出口剔除"的写法：一旦哪天加列或漏一个出口就会泄露；SQL 不选这一列，泄露面从根上不存在。

## 为什么叫"按构造"

"按构造（by construction）"是形式方法里的老词：与其在运行时到处检查"你有没有犯错"，不如把系统构造得让错误根本无法表达。放到这里就是——与其在 N 个出口各写一句"记得删敏感列"（runtime check），不如让查询本身在类型和数据流上就不携带敏感列（构造性保证）。后者的检查点从 N 个出口收敛成 1 份列清单，审计时只需盯住这一份。

这跟 LIO / SIF 这类信息流控制研究（"把信任从应用代码上移到框架/编译器"）是同一种取向的工程直觉——本篇不是发明它，只是在一个业务小模块里照着做了一遍（详见第 05 段的避让表）。

## 代价，也得如实说

按构造不是免费的：
- 不能再用 `SELECT *` 偷懒，得手写并维护列清单；加合法展示列时要记得同步进去。
- 一份"安全列清单"要能被多条非管理端读路径复用，否则又退化成散落多处。本案例的做法是把它提成常量（见第 02 段）。
- 它只解决"读路径不选敏感列"，还需要类型层与测试层配套，才不至于哪天有人绕过这份常量另起一句查询——这正是第 02、03 段要补齐的。

## 本段要点回顾

- 出口剔除是"默认泄露、逐点补救"，失效模式是加列/漏出口/删不净；
- 按构造是"默认安全、检查点收敛到一份白名单"，敏感列从查询根上就不被选中；
- 这就是 OWASP API3"要 cherry-pick 属性、别整块序列化"的主张，落到 SQL 侧的写法。
