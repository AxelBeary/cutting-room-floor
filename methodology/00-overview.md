## 本篇的诚实定位（先说清楚，免得被当成"发明"）

这不是一套新范式。它是 OWASP API Security Top 10 的 API3（Excessive Data Exposure / Broken Object Property Level Authorization）在一个举报·审核模块里的一次完整、严格落地——把官方早就写明的东西，一条不漏地做到代码、类型、测试三层，并且让这三层互相咬合。

每个零件都有公开出处：
- "不要 to_json 全量序列化、要挑字段" 是 OWASP API3:2019 原文；
- "对象级属性授权缺失（BOPLA）" 是 OWASP API3:2023 的重述，其官方 Scenario #1 恰恰就是"举报接口泄露被举报人属性"，与本案例几乎撞车；
- "输入侧用 allowlist 而非 blocklist" 是 Mass Assignment Cheat Sheet 的标准建议；
- 列权限、字段投影、白名单序列化在 NestJS / TypeORM / Django REST / Spring Data REST / Hasura / PostgreSQL 里都是框架一等公民；
- "断言某文本不出现在响应里" 早在 Django SimpleTestCase.assertNotContains 里就有。

所以本篇不主张任何机制新颖性。它唯一可能少见的是组合的完整度：在一个不大的系统里，把"按构造防泄露""逆泄露断言""同一标识按用途分级""管理端显式重附"四件事闭环互锁，并用一条测试纪律把"敏感值不得出现在响应体任意位置"钉死。这一点的确切边界，见《05 与公开先例的关系》与《07 局限与可改进方向》——那两篇才是本篇可信度的命门。
