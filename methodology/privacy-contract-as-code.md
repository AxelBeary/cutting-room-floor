# 把隐私政策做成可执行契约：告知—实现一致性的防漂移测试（流程 SOP 篇）

> 一句定位：把对外政策散文（隐私政策 / 服务条款）当成产品自己仓库里的**一等交付物**，用**回归测试**锁住它的诚实度，并专设一条**"反向不诚实"断言**——没改正文就不许把"最后更新"日期往前推。本篇只收**可被别人照着做的流程与规矩**。

> 沿用原稿章节号：本篇为 §〇~§七（含 §六 速查表），§八/§九 起在另一篇。

> 版本：v1.1（2026-09-19，拆分手术 + 实名与真值回写）｜ 性质：方法论 SOP，**待收口会话复核放行**，未放行前只准留在 `wip/honesty-gate/`
> 来源：Inkglean（拾绘）的一次"对外文书诚实度收尾"实践；本文把它抽象成任何项目都能照做的方法论。来源主体按本仓术语对照表登记的口径实名写作 **Inkglean（拾绘）**（不使用仓库目录名与曾用名），下文以"来源仓"指代其产品代码仓。代码块中的 `updated` 日期为**带时点的实测值**（截至 2026-09-19 只读回源核实所得，只说明该时点确实如此，不表示"当前仍如此"）；政策措辞为**概述**、非逐字引用；留存天数、测试份数等事实数字同一时点回源核实为真。证据路径写成 `<Inkglean 仓>/…` 占位形式，组件与测试文件只用角色描述指代，不写真实文件名。

## 〇、先说清楚：这篇要解决的不是"有没有隐私政策"，而是"政策会不会骗人"

几乎每个产品都有隐私政策。问题不在有没有，而在**它说的话和系统实际做的事会不会慢慢对不上**——我们对用户承诺"日志保留 180 天"，代码却悄悄改成了永久留存；文书写着"可在偏好中关闭埋点"，可实际上只有管理员有全站开关、个人端根本没有入口；最隐蔽的一种是：正文一个字没动，只把"最后更新日期"从三月改到九月，制造"我们近期复审并更新了隐私政策"的**虚假信号**。

这类"告知与实现不一致"（disclosure–implementation drift）在传统上靠人盯：法务写好一版，工程半年后改了实现却忘了改文书，直到被审计或被媒体扒出来。学术界的应对是**站在监管者视角**，从外部爬取政策、再用 NLP/流量分析去对账（先例对照见另一篇 `split-paper-material.md`）。那条路有效，但它发生在产品**之外**、发布**之后**，产品作者自己日常开发时拿不到反馈。

我们走的是另一条完全相反的路：**不依赖第三方事后对账，而是把政策散文本身放进产品自己的仓库，让它像普通代码一样被回归测试守护**。改政策文案、改代码能力，只要两者一旦对不上，CI 就变红。这不是算法创新，而是**工程实践的重新定位**——所以它新颖性主张是"实践型"的，本文档老实承认这一点（论证见另一篇 `split-paper-material.md`）。

这份方法论的目标读者是：**任何需要对外发布文书（隐私政策、服务条款、数据说明、SLA、可访问性声明……），又希望"文书说的话"长期可信的产品团队**。读完你应该能在自己的仓库里搭起同一套东西。

## 一、失败模式分类：政策散文到底会怎么"变脏"

要防漂移，先给"漂移"建类型学。下面四类是我们真实遇到、且**每一类都能写出对应断言**的。这张表是整篇的地基——后面每个测试都对应这里的一行。

| 编号 | 失败模式 | 通俗说法 | 危险在哪 | 可断言性 |
|---|---|---|---|---|
| D1 | **改了正文不改日期** | 悄悄改了收集范围，"最后更新"还停在半年前 | 用户看到的"生效日期"是假的，无从知道政策已变 | 高（日期须等于正文最近实改日） |
| D2 | **改了日期没改正文** | 正文一字未动，只把日期往前推 | 制造"近期复审过"的虚假合规姿态——**本文重点的反向不诚实** | 高（需"正文实改历史"作参照） |
| D3 | **承诺未接通的能力** | 文案写"即时推送提醒你"，但通知通道根本没实现/默认关 | 对用户许诺了一个不存在的能力 | 高（不得含未接通词、须含"开发中"类实话） |
| D4 | **口径与实现对不上** | 写"你可自行关闭"，实际只有管理员全站开关 | 权利话术与真实控制粒度相反 | 高（关闭性口径须与实现对齐） |
| D5 | **公示范围被悄悄删** | "不含内容与文件""保留 180 天"这类限缩承诺被顺手删 | 删除即放大权力，用户失去既得保护 | 高（关键范围句须存在性断言） |

**关键设计原则**：一条对外承诺 = 一类失败模式 = 一条回归断言。断言的**对象不是文案自己的措辞**，而是**"文案"与"代码真实能力/真实字段"之间的一致性**。这是本方法论与"文案 lint"的根本区别——我们测的是**跨制品的一致性**，不是文案内部。

> ⚠️ 局限：这张表只覆盖"可被结构化断言"的漂移。纯语义层面的自相矛盾（例如两处正文对同一权利表述冲突）机器难判，仍需 §五 的人工终审兜底。诚实声明这个边界，别把测试当成能替代审校。

## 二、方法①：政策结构化 = 唯一事实源，界面只渲染不复制

### 怎么做（可复现）

把对外文书**从"页面里写死的段落"变成"数据"**。在来源产品（Inkglean）里，隐私政策与服务条款两份文书都不存在于任何模板正文中，而是以结构化数组的形式，作为 i18n 语言包的一个命名空间存在（简化后的形状见下）。

```ts
// <Inkglean 仓>/…/locales/ 语言包 zh-CN 侧（结构示意、非逐字；措辞为概述，日期为带时点实测值）
compliance: {
  common: { updated: '更新日期', privacy: '隐私政策', terms: '服务条款' },
  privacy: {
    pageTitle: '隐私政策',
    updated: '2026-09-13',                                  // 实测值：截至 2026-09-19 只读回源核实，zh-CN 与 en 两侧同键一致
    note: '本政策为平台标准版模板文案（人工审校），非法律意见……',  // 免责标注也在数据里
    sections: [
      { title: '一、我们收集哪些数据',
        paragraphs: ['…仅收集完成服务所必需的数据：'],
        items: [
          '浏览行为（埋点：只记录访问了哪些页面、点了哪个功能，不含内容与文件；'
          + '由管理端统一开关、个人端暂不单独提供关闭入口；日志保留 180 天）——（概述措辞，非逐字；留存天数为截至 2026-09-19 回源核实的真值）',
        ] },
    ],
  },
  terms: { pageTitle: '服务条款与合作协议', updated: '2026-08-23', note: '…非法律意见…', sections: [ ] },  // 同一时点实测值
}
```

渲染端则是**一份通用组件喂两份文书**：同一个通用文书渲染组件（下文用角色描述"文书渲染组件"指代，不写其真实文件名），靠路由 `name` 判定当前渲染 `privacy` 还是 `terms`，把 `sections` 里的 `title / paragraphs / items` 逐个 `v-for` 出来，标题、日期、免责注全部走 `$t()`/`tm()` 取键。

```vue
<!-- <Inkglean 仓>/…/views/ 文书渲染组件（逻辑示意，已去真实文件名） -->
<h1>{{ $t(`compliance.${docType}.pageTitle`) }}</h1>
<p>{{ $t('compliance.common.updated') }}：{{ $t(`compliance.${docType}.updated`) }}</p>
<section v-for="sec in sections" :key="sec.title">
  <h2>{{ sec.title }}</h2>
  <p v-for="p in sec.paragraphs">{{ p }}</p>
  <ul v-if="sec.items"><li v-for="i in sec.items">{{ i }}</li></ul>
</section>
<p>{{ $t(`compliance.${docType}.note`) }}</p>
```

> ⚠️ 静态核对（读源码所得，非本会话复跑 CI）：两份对外文书都从同一份 i18n 数据驱动渲染，组件里**没有一句写死的政策正文**（数组消息用 `tm()` 取，`t()` 只处理字符串会回退成 key——这是个常见的坑，注释里专门标了）。

### 为什么

- **单一事实源**是断言能成立的前提：只有当"政策全文"是**可被测试直接 import 的结构化数据**时，"改文案"和"改日期"才成为可比较的两个动作。散落在模板字符串里的政策，测试根本抓不到。
- **只渲染不复制**顺带解决了多语言一致性：中英两份是同一棵树上的两个叶子（`zh-CN` 与 `en` 同键），杜绝"中文改了英文没跟"。
- **免责标注进数据**（"模板文案·人工审校·非法律意见"）让"这不是法律意见"这件事本身也成为受管控的字段，而不是脚边小字。

### 会踩的坑

1. **诱惑走回头路**：有人图省事直接在组件里写死一段中文——一旦写死，测试就瞎了。纪律：政策正文**只能**来自数据命名空间，评审时见到模板里的政策硬编码要挡回去。
2. **数组消息不能用 `t()`**：`vue-i18n` 里对数组用 `t()` 会退化成打印 key；必须用 `tm()` 拿结构化消息。上面注释里那条就是真实事故留下的。
3. **结构化颗粒别切太细**：目标是"每条对外承诺是可定位的一个节点"，不是把政策 XML 化到每个标点。颗粒太细 → 断言脆、维护贵；太粗 → 断言抓不到具体承诺。**以"一条承诺一句话"为界**（如"埋点条目"整条是一个 `items` 元素，就够写 §四 的三类断言了）。

## 三、方法③：日期—正文耦合断言（含"反向不诚实"专防）

这是本文最有辨识度的一块，也是本次查重范围内**未检索到具名先例**的核心（对照见另一篇 `split-paper-material.md` §九 与"详 1"）。它把"最后更新日期"从一句装饰，变成**被双向锁死的字段**。

### 正向锁：改了正文，日期必须跟上；且日期就是实测的那个值

```ts
// 对外文书诚实度防漂移测试（A）（示意，已去掉内部批次号与真实文件名）
const DATE_RE = /^\d{4}-\d{2}-\d{2}$/

describe('隐私政策更新日期与正文实改对齐', () => {
  it('中英 privacy.updated 均为当前正文实改日且格式合法', () => {
    expect(zhCN.compliance.privacy.updated).toBe('2026-09-13')   // 实测值：截至 2026-09-19 回源核实，断言把日期钉成字面量
    expect(en.compliance.privacy.updated).toBe('2026-09-13')
    expect(zhCN.compliance.privacy.updated).toMatch(DATE_RE)
  })
})
```

这条把"日期"钉成一个**字面量**。当有人改了政策正文（比如新加一条数据收集披露）却没同步改这个测试里的日期，测试就会与"正文变更"这道流程耦合起来——收口时逼着你回答：**正文动了，日期该不该动？** 该动就改断言值，不该动就说明这次确实没碰正文（引向反向锁）。

### 反向锁：没改正文，就不许把日期往前推（"反向不诚实"专防）

正向锁挡不住最阴的那种：正文一个字不动、只把日期往前刷，制造"近期复审更新"的假象。对付它要用**跨文书相对关系**或**正文指纹**来锁。这里用的是一种很轻巧的关系式断言——服务条款正文这批没改，那么它的日期**不得越过**隐私政策日期：

```ts
it('本批未改服务条款正文：terms.updated 不得跑到 privacy.updated 之后（防只动日期的反向不诚实）', () => {
  // 实测关系：terms.updated=2026-08-23 ≤ privacy.updated=2026-09-13（截至 2026-09-19 回源核实成立）；断言锁的是相对关系
  expect(Date.parse(zhCN.compliance.terms.updated))
    .toBeLessThanOrEqual(Date.parse(zhCN.compliance.privacy.updated))
})
```

**为什么这条能防反向不诚实**：一旦有人想给"没动的服务条款"单独把日期推到很靠后（比隐私政策真正修订日还晚，暗示"条款刚被更新过"），关系式立刻红。它用一个**廉价的相对约束**，逼近了"日期不得晚于正文真实变更"这个较难直接测的绝对目标。

> ⚠️ 静态核对（非本会话实测）：来源仓状态记录里明写"服务条款日期**故意不动**（本批未改其正文，改了反而成新不实陈述，并已用断言锁住）"——这正是"反向不诚实"意识落到工程断言的直接证据。

### 更强的做法（本文推荐，来源仓用了轻量版）

相对关系式是"够用但不最严"的实现。可移植的更彻底版本有两种，按需选：
- **正文指纹**：对政策 `sections` 规范化后算一个 hash，存进测试或快照。指纹变（真改了正文）→ 断言要求 `updated` 必须同步变；指纹不变 → 断言禁止 `updated` 变化。这才是真正双向锁死"日期 ⟺ 正文实改"，且不依赖"两份文书的相对顺序"这种间接信号。
- **提交历史耦合**：在 CI 里比对"政策数据文件的最近一次实改提交日期"与 `updated` 字段是否同日。缺点是把测试和 git 历史耦上，脆弱；本文更推荐纯数据的指纹法。

### 会踩的坑

1. **别把 `updated` 断言写成"只要不早于某天"的松约束**——那样"随便往前推日期"照样过。要么钉成字面量，要么钉成"与正文指纹同生同灭"。
2. **中英两份都要锁**：漏了 `en` 就等于给"只改一边制造信息差"留后门。
3. **相对关系式要对被锁文书的"沉默"做假设**：它只在"这批确实没改服务条款"时成立。若哪天真要单独更新服务条款，得**同时**改这条断言的前提交言——把它写进 §五 的人工终审清单，避免测试变红时有人直接删断言了事。

## 四、方法②④：承诺—能力对账断言（断言的是"文案 ↔ 真实能力"）

D3/D4/D5 三类漂移的共同解法：**把每条对外承诺，翻译成一条对"文案 vs 实现"的对账断言**。断言的两侧，一侧是政策/开关文案，另一侧是系统的真实能力（有没有某个实现、控制粒度是哪一级）。以下三条都取材自真实测试。

### 4.1 未接通功能不得在文案里承诺（治 D3）

通知通道还没接通，就不许文案写"提醒你 / 即时推送"，且必须含"开发中/还用不了"这类实话：

```ts
it('通知开关文案不再承诺未接通的能力', () => {
  expect(zhCN.preferences.notifyDesc).not.toMatch(/提醒你|通知你|即时推送/)
  expect(zhCN.preferences.notifyDesc).toContain('开发中')
  expect(zhCN.preferences.notifyDesc).toMatch(/不会真的|还用不了/)
  expect(en.preferences.notifyDesc).not.toMatch(/alerts you|notifies you/i)
  expect(en.preferences.notifyDesc).toMatch(/in development/i)
})
```

**更深一层——同口径不互相矛盾**：同一个事实会在多处文案出现（客户侧勾选项说明、画师侧开关说明、共用提示）。断言不止要每处都"说实话"，还要防止"A 处描述了 B 处不成立的细节"造成新的不实陈述：

```ts
it('活文案与共用提示同口径：同一事实、各自精简，不复读也不矛盾', () => {
  for (const text of [zhCN.common.notifyDevHint, zhCN.preferences.notifyDesc])
    expect(text).toContain('开发中')
  // notifyDevHint 讲的是"灰置、默认不勾"的客户侧勾选；画师侧开关并未灰置，
  // 若把这句复读进画师文案就构成新的不实——这里锁住这条边界
  expect(zhCN.preferences.notifyDesc).not.toContain('先灰着')
})
```

**顺手清死键**：曾有从来没有组件引用的"死文案键"，害得对账时把死键当活文案派工。退役它们并锁"不得复活"：

```ts
it('死键已退役（无渲染器不得加回）', () => {
  for (const settings of [zhCN.settings, en.settings])
    expect('notifyText' in settings).toBe(false)   // 用 in 断言"键不存在"
  expect(zhCN.preferences.notifyLabel).toBeTruthy() // 反向防误删：真在渲染的必须还活着
})
```

### 4.2 可关闭性口径与实现对齐（治 D4）

以 Inkglean 隐私政策的"浏览行为"条目为例：该条目早期向用户写"可自行关闭"，但实现只提供**管理端全站开关**、个人端无入口——这就是 D4（早期措辞据施工期所见的改动历史；截至 2026-09-19 回源核实时，该条目已是写明"管理端统一开关、个人端暂不单独提供关闭入口"的版本，本稿只作概述、不逐字引用）。断言把口径改回实话，并锁死"不得再出现自相矛盾的话术"：

```ts
function privacyItems(locale) {                       // 把政策 items 摊平成一个字符串数组
  return locale.compliance.privacy.sections.flatMap(sec => sec.items || [])
}
const zhItem = privacyItems(zhCN).find(l => l.startsWith('浏览行为'))

it('不再承诺用户能自己关闭埋点，改为写明管理员全站开关', () => {
  expect(zhItem).not.toMatch(/可在偏好中关闭|可自行关闭|随时关闭/)
  expect(enItem.toLowerCase()).not.toMatch(/you can (?:disable|turn off|opt out)/)
  expect(zhItem).toContain('管理员')                  // 真实控制粒度：全站、管理端
})
```

### 4.3 留存/范围公示不得被悄悄删（治 D5）

改口径时，人容易"只把开关那句话改了，却把数据范围/留存期限那两句顺手删了"——删了限缩承诺等于放大权力。于是**存在性断言**把关键范围句钉住：

```ts
it('原有的数据范围说明与留存期没有被删', () => {
  expect(zhItem).toContain('180 天')      // 锁关键留存期数字（截至 2026-09-19 回源核实：政策条目与后端 events TTL 双向印证为整 180 天）
  expect(enItem).toContain('180 days')
  expect(zhItem).toContain('页面')         // "只记录访问了哪些页面"这一范围限定
  expect(zhItem).toMatch(/不含/)           // "不含内容与文件"这条既得保护必须留着
})
```

### 为什么这一整节成立

因为**政策和实现住在同一个仓库、同一棵依赖树里**：测试文件能同时 `import` 政策数据和（间接地）反映真实能力的口径，把"说的话"和"做的事"放进同一个 `expect`。这是"第三方对账"给不了的即时反馈——第三方只能事后猜你的实现，你在 CI 里就能当场证明。

### 会踩的坑

1. **断言两侧要选对**：新手容易把 D4 写成"文案里必须有'管理员'三字"的纯字符串检查，忘了它其实是**在锁"控制粒度 = 全站"这一实现事实**。一旦将来真的补了个人端开关，这条要**连同实现一起**翻向——所以它是"承诺随能力改"，不是"文案不许动"。
2. **存在性断言会挡合理重构**：把"180 天"改成"约 180 天"或挪了位置都可能红。缓解：断言锁**语义关键片段**（数字、"不含"、"页面"）而非整句逐字匹配。
3. **摊平 `sections` 依赖结构形状**：政策结构（`sections/paragraphs/items`）一改，`privacyItems()` 这类辅助函数要跟着改。把辅助函数当"契约适配器"维护，注释写清它对应渲染端的哪个形状。

## 五、方法⑤⑥：纳入常规门禁 + 人工终审与台账

前面四节是"写什么断言"，这一节是"让它们真的拦住漂移"。

### 5.1 纳入门禁（⑤）

- 这些测试就是普通的单元测试文件（Inkglean 前端用 vitest），**混在常规测试套件里跑**，不需要特殊基础设施。
- 进 **pre-merge 必过闸**：改政策数据 / 改相关文案 / 改相关能力，只要触发任一断言，PR 不放行。
- **红了不许直接删断言**：这是最重要的一条纪律。断言变红通常意味着"文案与能力确实不一致了"——正确响应是**二选一**：要么把实现补上（真去接通那个能力），要么把文案改成实话（承认还没这个能力）。**删断言 = 允许政策继续骗人**，必须被 code review 挡下。

### 5.2 人工终审 + 台账（⑥）

机器只能覆盖 §一 表格里"可结构化"的漂移；政策散文的语义正确性、法律措辞分寸，仍需人。方法：

- **对外文书诚实度当作需人工终审的工程交付物**，不是附属法务文档。收口一批改动时，专门有人（不必是法务）回读一遍改了哪条承诺、免责标注还在不在。
- **留台账**：每次政策为什么改、和哪条断言耦合、哪批未动正文故日期不动——都记下来。来源仓的做法是把这类决定沉到状态记录里（例如"服务条款日期故意不动，因本批未改其正文"这种因果说明），下一个接手的人不用重新推。
- **免责标注常驻**：政策正文顶部标注"模板文案·人工审校·非法律意见"，既是给用户的诚实，也是给作者自己的提醒——这套文书的诚实度是**工程责任**，不是买了个法务模板就完事。

### 会踩的坑

1. **把测试当审校替身**：门禁只能证明"没触发已知漂移类型"，证明不了"新出现的、没写进断言的漂移"。台账里记"新增承诺时同步新增一条断言"这个动作，让断言集随承诺集一起长。
2. **门禁松口一次就崩**：第一次为了赶发布删断言，纪律就破了。宁可把断言改成"暂时降级为 WARN"并挂 TODO，也不静默删除。

## 六、方法骨架六步速查（照做清单）

| 步 | 做什么 | 为什么 | 怎么做（最小动作） | 头号坑 |
|---|---|---|---|---|
| ① | 政策结构化 = 唯一事实源，界面只渲染 | 让测试能 import 到政策全文，是一切的地板 | 政策正文进数据命名空间；写一份通用渲染组件喂多份文书 | 有人图省事把一段政策写死进模板 |
| ② | 每条对外承诺写一条对账断言 | 把"说的话 vs 做的事"放进同一个 `expect` | 断言对象是"文案 ↔ 真实能力"，不是文案内部 | 把对账断言写成纯字符串检查，丢掉了"锁实现事实"的本意 |
| ③ | 日期—正文耦合断言 | 防 D1（改正文不改日期）与 **D2 反向不诚实** | 正向：`updated` 钉成正文实改日字面量/绑正文指纹；反向：没改正文不许推日期 | 把日期约束写成"只要不早于某天"的松断言 |
| ④ | 承诺-能力对账断言 | 防 D3/D4/D5 | 未接通功能不得承诺、可关闭性口径对齐实现、留存/范围公示做存在性断言 | 存在性断言逐字锁整句，合理重构被误伤 |
| ⑤ | 纳入常规门禁 | 让漂移在合入前就拦住 | 混进测试套件、pre-merge 必过 | 一红就删断言 |
| ⑥ | 人工终审 + 留台账 | 补机器测不到的语义层 | 政策当交付物终审；为什么改/哪批没动正文都记账 | 把测试当审校的替代品 |

**新增一条对外承诺时的标准动作（循环回到 ②③④）**：承诺进了政策数据 → 顺手为它写 ≥1 条断言（承诺了什么能力就断言实现对不对齐；有数字/范围/日期就写存在性/耦合断言）→ 该断言进门禁。断言集随承诺集一同生长，这套东西才不会腐化。

## 七、适用边界：什么时候该用、什么时候别硬套

**适合**：
- 有**明确、可数的对外承诺**（留存期限、可否关闭、收集范围、通知能力、SLA 数字……）的文档；
- 承诺**会变**（随功能迭代反复调整），因此存在"文案落后于实现"的现实风险；
- 团队已在跑 CI，能近乎零成本地挂上这些测试。

**不适合 / 要降级**：
- 一次性、几乎不改的静态声明——投入产出不划算；
- 需要精确法律效力的措辞——本文锁的是**"告知与实现一致"**，不担保法律合规性（这也是为什么免责标注要常驻、终审要人工）；
- 政策与实现物理分离（政策文本不在产品仓库里）的情况——得先做 §二的"结构化进仓"这一步，否则无从断言。

**本文诚实定位**：贡献不在算法（没有新的 NLP/污点分析），而在**工程实践的新定位**——把对外政策散文当一等交付物、用回归测试锁诚实度、并专设"反向不诚实"断言。新颖性论证与先例避让另见 `split-paper-material.md`（§九 摘要 + "详 1~详 3"逐族划界）。
