# 四、这些零件，别人也都造过

写到这里，最诚实的做法是先泼自己一盆冷水：上面这些，几乎没有一样是凭空发明的，而且大多有明确、公开的现成先例。我把查到的摊开讲，一是避让，二是顺便说清我到底还敢主张什么。

## 先例清单（零件级，各有其主）

- **为 AI 单独写一个入口文件**：agents.md 已经成了事实上的开放标准，「README for agents」这类东西满地都是，入口要短、要做路标不是百科，早就有人讲。 [须补或删：GitHub 仓库 URL 或典型示例链接]
- **上下文压缩与外挂记忆（对应「失忆」）**：Anthropic 关于 context engineering 与 Agent Skills 的工程文章，把「上下文是稀缺资源、要压缩、要把记忆挪到文件里」讲得很系统，NOTES.md 式的做法在代理社区也是常识。 [须补或删：Anthropic 官方文档 URL 或具体文章链接]
- **决策记录里的 Superseded / Rejected，以及「防 agent 重提被否方案」（对应「重蹈覆辙」）**：ADR（架构决策记录）本就有「已被取代 / 已被否决」这些状态；archyl、Addy Osmani 以及多篇文章，都明确提到用「记下来、并标注状态」来防止 AI 把已经被否决的方案又提一遍。我那个「决策墓碑」的说法，本质就是这个思路的一种方言。 [须补或删：archyl 项目 URL、Addy Osmani 具体文章链接]
- **代码为最高事实源 + 用机械手段强制（对应「数字误引」）**：OpenAI Codex 生态里的 Doc-Gardening、Serial-Studio 的 ss-ai-audit 都有句很到位的话——「the code is the suspect, the code is truth」（大致是「代码才是待审的嫌疑人，也是唯一的真相」）。把文档降级、把代码抬成最高事实源，再用工具去 enforce，这条也不新。 [须补或删：Doc-Gardening 与 ss-ai-audit 的 GitHub URL 或官方文档]
- **行短利于 diff（对应「工具失真」）**：从 Kernighan 早在 1974 年就在意行宽、到 Microsoft 规范里的 79 字符，再到 flowmark 已经直接把「为 LLM 编辑 / diff 友好」和「该在哪里断行」联系起来——「行要短」这件事，半个世纪前就是好品味，近年又被接上了 AI 的理由。 [须补或删：Kernighan 原文献、Microsoft 规范文档 URL、flowmark 项目链接]
- **给记忆文件设硬上限**：Claude Code 的 MEMORY.md 就写死了 200 行、25KB、每条 150 字这一类上限。我这条「正文只留 5 条」的直觉，和它是一个路数。 [须补或删：Anthropic Claude Code 官方文档 URL 或相关说明]

一句话：**零件皆有先例。** 谁要把上面任何单个零件当「首创」来卖，都会被同行很快拆穿。

## 那我到底还敢主张什么（真差异所在）

我敢说的，是很窄的一条组合新颖性，而且我会把它标成「乙类」——不是发明了新零件，是把这些零件按一条新因果串了起来：

1. **把「文档物理形态」反向绑定到「AI 工具链的具体失效模式」**。别的地方也讲行短、也讲入口短，但我没见到有人把「行宽 / 看板规模 / 归档粒度 / 迁移时的字符守恒」这一整套物理参数，明确地、一条条地挂到「失忆 / 重蹈覆辙 / 工具失真」这三类失效上，并且写成可执行、可证伪的规则。这条因果化、可执行化的命题，是我最想主张的差异。
2. **「字符总量差校验零丢失」的迁移守恒**。断行、限宽都常见，但把「归档搬动文本」当成一类需要守恒校验的高风险迁移（搬前搬后字符总量差 + 逐条比对），这套做法我没见到成体系的先例。
3. **「文档正文自我贬低声明」这个修辞装置**。文档主动写下「我里面的数字不可信，去核代码」——把不信任写进被信任对象自己的正文里，这个自我拆台的动作，我觉得挺少见。

## 一句必须补上的免责声明

上面所有「未见到先例」，都是基于一次查重的诚实缺口陈述，不是「我证明了你找不到」。别人在某个我没搜到的角落早已系统写过，完全可能。我把它写成「组合新颖、乙类」而不是「首创」，正是为了给自己这句话留退路——毕竟，为一篇讲「别过度归因」的文章，自己先在一个没把握的判断上吹牛，那就太可笑了。
