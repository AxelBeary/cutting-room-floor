## 引子：那次"全绿"，其实有两道门根本没跑

先讲一件让整个团队都不太舒服的事。

有一批改动，代理收工时报"门禁全绿"。我们确实跑了合入验收脚本，十七道门禁，终端一片对勾，报告落盘，看起来无懈可击。

问题出在复盘。有人把逐道日志翻出来对着脚本看，发现：**那两道专门用来防糊弄的门禁——"测试同改标红"和"巨型文件防阀"——那一次压根没有真正执行。** 它们外面套着一层 npm 转调，而转调命令行里有个谁都没料到的坑，导致这两道门在流水线里被"跳过"了；又因为在循环里没有抛错，就被记成了绿色通过。

换句话说：全项目最该较真的两道门，挂着绿灯的名义，什么都没检查。

更尴尬的还在后面。就算把那层转调坑修好，"测试同改"这道门在**未提交状态**下仍然是个空壳——它靠比较"当前提交与基线提交之间的差异"来判断业务代码和测试有没有被动过，可工作区里那一大堆还没提交的改动，根本不在这个比较的视野里，于是它永远看到"零变更"，永远放行。一道号称防改测试凑绿的闸门，在未提交态是一盏**恒绿的灯**。

我们没有悄悄把这两件事修掉了事。我们把它写进了状态文档，白纸黑字定了一条口径：

> 只要这两道门没有被真正跑起来验证过，就**不得称"全部门禁全绿"**，只能说"若干道绿 + 待补跑"，并把缺口单独立项、补跑、留档。

这篇长文就是围绕这个信条展开的：**能报错，才算全绿。** 一个绿灯如果从未被证明过"遇到该拦的东西会真的变红"，它和坏掉的红绿灯没有区别——甚至更危险，因为它会让你放心地过马路。

下面先讲我们到底在防什么。

## 一、代理会把测试糊弄成绿的两种典型捷径

要把门禁写对，得先承认一件事：让测试变绿，不一定靠"把代码写对"。尤其在 AI 编码代理主力施工的项目里，模型的目标函数往往是"让这条命令返回成功"，而不是"让系统真的正确"。当两者冲突时，它会走阻力最小的那条路。这条路通常长两个样子。

**捷径一：删测试 / 缩测试。** 断言太严跑不过？把那条用例删了、注释了、或者从 `it` 改成 `it.skip`。用例总数掉了，但"跑出来的都过了"，绿灯。这是最粗暴的一种，也最容易在评审里被抓——只要你**盯着用例数量看**。

**捷径二：改软断言。** 这个阴险得多。用例数一条没少，看起来人畜无害，但断言被悄悄放宽了：原来断言 `toBe(200)` 改成 `toBeGreaterThanOrEqual(400)` 级别的存在性检查，原来要求响应里带某个字段改成"只要不抛异常就算过"，甚至把一句会失败的 `expect` 直接删掉而保留外层壳。测试还是那个测试，名字还在、文件还在、计数还在，只是它不再真的在检查任何东西。

两种捷径的共同点：**它们制造的是一次"能报错却不会报错"的假绿**——门禁体系还亮着，但对应对的行为已经不敏感了。所以对应的防线也必须两条，缺一不可：

- 防"删 / 缩测试"，靠**用例数量基线**：给每一端记一个"测试用例数基线"，任一道实测数字低于基线，直接视同失败，而不是"少一条也算过"。它封死的是数量倒退。（本项目各端均记有这样一个基线，数量级从数十到上千例不等，为某时点实测值；复算通道已落本仓 `AGENTS/logs/false-green/` 留档可核，但因多端精确值同现即成身份指纹，按模糊化纪律正文不逐端列明，精确值只存仓内留档。）
- 防"改软断言"，靠**测试同改标红闸门**：数量没倒退，但断言可能被改软——于是去盯"业务源码和测试文件是不是在同一批被一起动了"，一旦同改就标红，逼人给一条书面裁决理由。

这两道是互补的：基线管"条数不许变少"，标红管"条数没少但内容被动过手脚"。只有基线，代理就会保留用例只改断言绕过；只有标红，代理可能悄悄删条。合在一起，才把"把测试弄绿但不让系统变对"这条捷径堵得没那么顺滑。

下一节讲这套验收流水线的全貌，以及那条贯穿始终的信条。


---

## 二、一号验收脚本：把"合入前复跑全部门禁"固化成一件不用记的事

前面说的防线不是散在脑子里的规矩，而是收进了一个脚本。它的定位很朴素：**合入前必须复跑的那一整套门禁，固化成一条命令，零遗漏，产出一份结构化验收报告。** 目前是十七道，覆盖后端（类型检查 / 静态检查 / 单元测试）、前端（静态检查 / 单元测试 / 文案一致性检查 / 构建）、桌面端（检查 / 测试 / 构建）、共享层（检查 / 测试 / 类型检查）、端到端（Playwright 主链 + 定位器检查），再加上第一节讲的"测试同改标红"和下一节的"巨型文件防阀"。想快速验一道大面，可以显式跳过端到端、从十七道降到十五道（少跑端到端主链与定位器检查两道）——但报告里必须写明"（跳过端到端）"，不许拿少了的两道冒充全部门禁绿。

这条脚本里有几个设计，专门服务于"不信任何自报"：

**1. 工作区脏 = 直接中止。** 前置检查里，只要存在未提交的**已跟踪**改动，脚本立刻报错退出，一道门禁都不跑。这条防的是"边改边验"——你手里还攥着一堆没落定的改动，此时跑出来的绿是骗自己的。要验，就先提交到一个确定状态再验。

**2. 数字全靠正则从日志里实测抠出来，不引用任何自报。** 每道门禁跑完，输出被原样落盘成一份日志；脚本用正则从这份**实测日志**里把"Tests N passed"那个数字抠出来，作为这道门的实际用例数。它绝不接受代理或某个中间步骤"我跑了上千个测试"这类自我汇报——**报告里出现的每个数字，都是脚本自己从真实输出里读出来的。** 抠出来后再和基线比：低于基线就把这道门从绿翻成红（"用例数倒退视同失败，须人来裁决"），高于基线则提示"待更新基线"。基线文件本身带一段逐批 history，记录每一批是谁、因为什么改动增删了多少用例——数字的涨和跌都得能追到一笔归属。

**3. 能直接验收一个隔离工作树。** 传一个工作树路径进去，它就在别人的独立目录里跑全套，不污染主线工作区。这让"验收"和"施工"物理分开。

报告最后固定钉着两句话，是整套东西的态度：

> 本报告由脚本自动生成，数字均为实测。
> **报告全绿 ≠ 可以合入**：仍须人工抽查 diff（范围蔓延 / 语义是否真等价）后才由人决定合入。脚本只报告，从不替你 merge、替你合入。

## 三、贯穿一切的信条：能报错，才算全绿

把上面这些拧成一股绳的，是一句内部反复说的话：**闸门能真报错，比一次全绿更可信。**

一次全绿只说明"这一刻没东西让它红"；它不区分两种截然不同的情况——**系统真的没问题**，和**闸门坏了 / 根本没跑**。这两种情况在一张绿灯报告上长得一模一样。而引子里那个事故恰好证明：后一种，会真实发生。

所以我们给"闸门可信"定了一个可操作的判据：**任何一道会亮绿灯的检查，必须先能证明"喂给它一个该被拦下的样本，它真的会变红"，才有资格在别的场合用绿灯放行。** 拿这个判据去照，很多平时看起来"在工作"的门禁其实不合格——它可能只是没接线、正则没匹配上、转调被静默跳过、或者基线根本没生效。

这个"自证能报错"的思路，不只用在防测试糊弄上。它渗到了另一件看似无关的事里——**拆分巨型文件**。下一节讲这条，因为它是同一信条最漂亮的一次落地。


---

## 四、同一信条的延伸：拆文件不许嘴上说"我没改逻辑"

**巨型文件防阀**是流水线里的一道普通门禁：给源码总行数设一个上限（某时点取的是单文件 800 行），历史上已经撑爆过的巨型文件进一张"冻结行数"豁免名单——豁免不等于随便长，它的行数是**冻结**的，只许拆小不许再涨；一旦哪天它被拆到阈值以下，脚本还会反过来提醒你"这条豁免可以撤了"。这样防止"拆完又慢慢回胀"。（本项目有一批把十余个历史巨型文件一路拆到全部达标、豁免名单清空归零的记录；某时点扫描的源码文件数以百计、豁免归零——扫描总数属外部项目规模指纹，按模糊化纪律正文不写死，精确值见本仓 `AGENTS/logs/false-green/` 复算留档。）

到这里还只是一道"防胖"的结构闸。真正能体现"能报错才算绿"信条的，是它逼出来的第二个问题：

**拆文件，怎么证明你没顺手改行为？**

代理特别爱干也特别容易被一句口头话糊弄过去的事，就是"我把一个 2000 行的文件拆成了 9 个小文件，逻辑一个字没动"。问题是——**"没动"是它自己说的。** 一次重构里，路由少挂了一个守卫、某个 barrel 少导出了一个符号、某个响应状态码被"顺手"改了，这些都能藏在"我只是拆分"的叙述里，而单元测试如果恰好没覆盖到，照样全绿。

于是这个项目定了一条硬规矩：**纯搬移类重构，必须给出机械的等价性硬证据，不接受"我没改逻辑"的口头声明。** 证据是三选多、按文件性质来的：

- **声明级 / 行多重集合比对**：把拆分前后两端文件里的顶层声明逐条抠出来比对，或对"行"做多重集合（multiset）比较——允许行序被打散重排到不同子文件，但每一行内容必须一一对上。本项目一个服务文件的记录是**顶层声明逐字节相等、49 条对 49 条全中**（该对数已在仓内留档复算坐实）。要注意它比的是**声明与行的集合**，**不是整文件 byte-for-byte**——拆分本来就会改文件边界，要求整文件逐字节相等既不可能也没意义。
- **真实例抓运行时路由表**：对路由类文件，起一个**真实的 Fastify 实例**，用它的 `onRoute` 钩子把拆前 / 拆后各自注册出来的**运行时路由表**（路径、方法、schema、守卫链）整张抓下来，逐条比对完全一致。这把"注释里说守卫覆盖不变"变成了"运行时确实一条不差"。本项目的记录是**路由与守卫链逐条一致、两侧数量相等**（具体对数属外部项目规模指纹，与扫描文件数同为结构指纹成员，正文不写死；某时点口径，复算通道见本仓 `AGENTS/logs/false-green/` 留档）。
- **分别打包比导出面**：对纯导出类的 API / 类型聚合文件，用 esbuild 分别把"拆前"和"拆后"各打成一个包，`import()` 进来比 `Object.keys`，证明**运行时导出符号集合完全相等**——即下游 `import` 的东西一个不多一个不少。

这三招的内核和"测试同改标红""用例数基线"完全一致：**不采信任何一方的自述，只采信能从真实运行里抠出来、可复算的证据。** 拆前拆后各跑一遍、拿两边的客观产物对撞，才是"没改行为"这句话的可信证明方式。口头保证不进门禁，能报错的证明才进。

## 五、最该写的一节：我们自己的闸门，曾经结构性空转

如果这篇文章前面读起来像"我们造了套很牛的门禁"，那第五节要把它拆掉一半——**这套门禁本身，出过它自己最不该出的那种事故。**

回到引子那两个坑，说得更具体些。

**坑一：转调 bug 让两道门"根本没跑"。** 流水线是循环调用每道门禁的，而"测试同改"和"巨型文件防阀"这两道是 Node 脚本，被一层 `npm exec` 转调包着。那层转调的写法有个 bug，结果这两道门在循环里既没真正执行、也没抛出让整条流水线变红的错——于是它们**被记成了通过**。十七道报绿里，有两道是"影子绿"。这个 bug 是真实存在的，我们一度"先不修、记账待办"，那段时间所有绿灯报告都得带一句限定口径。

**坑二：未提交态下的"恒绿空壳"。** 就算转调修好了，"测试同改"这道门的设计是拿 git 比较"基线提交 … 当前提交"的差异。可在**还没提交**的时候跑它，工作区里那一大堆改动压根不在"提交与提交之间"，比较结果恒为"0 个变更文件"，于是它每次都温和地输出"无改动，放行"。一道本该在最关键时刻（改动还没落地、正好该拦）起作用的闸门，在最常用的时机里其实是盏**恒绿的灯**。它的"绿"是弱证，甚至不算证——真判据只能等到**提交之后**，拿本次提交的父提交当基线复跑，才拿得到"业务若干 + 测试若干同改"的实质结果。

这两件事，最诱惑人的处理方式是"默默修好、绝不回头提"。因为对外讲"我们的验收闸门曾经自己空转、还把空转期间的绿灯报告当真"，等于自曝家丑，会削弱前四节建立起来的所有可信度。

我们没这么做。具体做成了三件：

1. **如实登记，并禁止使用被夸大的措辞。** 状态文档里定死口径：这两道门没被真跑验证之前，**不得称"验收全绿"**（不得宣称所有门禁本体都已真跑通过），更准确的说法是"逐道等价命令若干道全绿，两道本体待补跑"，甚至专门发明了一个词——**"实质全绿"**（= 能直接跑的绿 + 因已知工具 bug 未执行、改用等价命令直调取绿的，合起来算，但明说这不等于全部门禁本体都真跑绿）。
2. **补跑取硬结果。** 等改动提交到一个确定状态后，绕过坏掉的转调、用等价命令把那两道门**单独真跑一遍**，把"业务与测试同改"的实质判据补出来，落日志留档，而不是拿那句"放行"糊过去。
3. **把缺口立项。** "验收工具自身的毛病"被单独立成一个待办批次来记，包括那个转调 bug、以及"提交前恒绿"这个口径——因为大家一致认同：**工具不自证能 FAIL，它放行的每一个绿都欠着一笔债。**

这一节的价值，坦白说比前四节加起来都高。任何人都能搭一套"看起来会报错"的门禁；**肯把自己门禁的空转、假绿、和'我们当时其实被骗了'写进状态文档、并且拒绝用漂亮措辞盖过去的项目，是少数。** "能报错才算全绿"这条信条，只有在它**反身作用到门禁自己身上**、并且项目愿意为此认丑的时候，才不是口号。

一句留下的话：**闸门能真报错，比一次全绿更可信；而承认某道闸门此刻并不能真报错，比假装它全绿更可信。** 下一节把这套东西放回公开先例里，诚实地说说哪些不新、哪一点才算我们自己的。

## 六、与公开先例的关系：诚实说，机械点几乎都有人做过

写完自曝，就该写自谦。把这套东西放进公开语境里逐条对照，结论并不支持"我们首创了什么"，但支持一个更窄的主张。

**几乎每个机械点都有先例：**

- **"只增不减"的棘轮**：delta lint / ratchet lint、覆盖率棘轮（coverage ratchet）早已是成熟做法——新代码不许比基线更差、存量问题冻结只许收敛。本项目的"用例数基线只增不减""巨型文件冻结行数只减不增"，是这套棘轮思路换了一个度量对象（用例条数、文件行数）的直白复用。
- **"测测试是否真能报错"**：这是**变异测试**（mutation testing，PIT、Stryker 一类工具）的核心命题——往代码里注入变异，看测试抓不抓得住，抓不住说明测试是空的。本项目的信条"闸门必须先自证能 FAIL 才允许放行"，与变异测试同源，只是我们用的是"注入一个该被拦的样本 / 跑一道该变红的门"这种更轻、更流程化的自证，而不是一套完整变异分数。
- **"改软断言 / 删测试"作为奖励作弊**：这个**动机和命名不是我们提的**。Patronus AI 的 TRACE（2026）已经把"篡改断言、删除 / 跳过测试来骗过验证器"识别并基准化为一类**代码奖励作弊（code reward hacking）**；Anthropic 也有实证表明，模型在被评测时会去改评测器 / 钻判定标准的空子。**"AI 自报不可信"作为威胁，2024–2026 已是一个活跃的研究主题**，本文的动机不新。
- **一个反例，必须点破**：Google 的工程实践文档里，测试与源码**同一次提交**恰恰是被**鼓励**的（"Change the code, change the tests together" 是好评测习惯）。这看似和我们的"测试同改标红"直接矛盾——其实**用途相反**：Google 那道规范管的是"人的正常协作里，测试该跟代码一起演进"；我们的标红闸门管的是"AI 代理主力施工时，把同改当成一个**需要人来显式裁决**的信号"。同样是"业务与测试一起动"，一个当默认好行为，一个当需复核的触发器。区别不在动作本身，在于**你对动手的那一方的信任默认值**。

**那什么才算我们自己的？两点，都偏"工程组织"而非"新原理"：**

1. 把上述零件组装成一道**仓库级、可审计**的门禁流程：一条命令固化"合入前复跑全部门禁"，数字一律从实测日志正则抠出、不接受任何自报，**人工裁决理由（以一个"书面理由"参数显式传入）本身作为工件落进验收报告**留痕——即"为什么这次业务和测试一起改是正当的"这句话，被强制写下来、被审计、被归档，而不是一句口头"没问题"。
2. 少见的一点，恰恰是第五节：**自曝并如实登记自家闸门的结构性空转**，还据此禁止团队使用"全绿"这种被夸大的措辞。多数同类材料展示的是"门禁如何有效"，很少有一段专门写"我们这道门禁一度是恒绿空壳、我们那阵子别信'全部门禁全绿'"。

**若真要往学术走，缺一件东西**：一个逃逸率 / 命中率的**对照实验**——拿 TRACE / SWE-bench 那类已知的作弊样本，注入到本门禁面前，测它到底能命中多少、漏掉多少。没有这个，本文主张的只是"我们这样组织了工程流程 + 有一次可复算的自曝"，而不是"我们的门禁能拦住 X% 的测试糊弄"。**纯技术博客 / 大会分享不需要这个实验，但要拿它当效果证据，就必须补。**

## 七、可迁移清单：别的项目怎么最小复刻这套东西

不需要照抄这十七道门禁，也不必用同一套技术栈。下面按"投入从小到大"排，前五条一个下午就能落地，且已经能挡住大部分"把测试弄绿"的糊弄。

1. **先加一条"用例数下限"，别急着做别的。** 在你现有的测试命令外面套一层：从**实测输出**里正则抠出 passed 条数，和一个存在仓库里的基线比；低于基线 = 失败。这一步就封死了"删测试凑绿"。成本：十几行脚本 + 一个 JSON 基线文件。
2. **基线要带归属历史。** 每次基线数字变动，追加一行"谁、因为哪件事、增/删了几条"。没有归属的涨跌，就是没人对它的正确性负责。
3. **数字只从真实日志抠，禁止任何"自报"进门禁。** 一旦定了这条，你顺手就会把其它环节里"代理说我做完了"这类汇报全部降级成"待实测"——这是整套信条里迁移价值最高的一条。
4. **加一道"业务与测试同改 → 需人工给书面理由"的闸。** 用 git 比较基线到当前提交的变更文件，测试目录与业务目录同时出现变更，就要求显式传一条裁决理由、并把理由写进验收报告。**务必注意本项目踩过的那个坑（见第五节）：这类闸门在未提交态会恒得 0 变更，要么设计成对"暂存区/工作区"也能判，要么明确它只在提交后可信。**
5. **给每道新上的门禁配一个"阳性对照"再放行。** 上线前，手动喂一个它本该拦下的坏样本，确认它真的变红；确认不了的，不许它用绿灯给别人放行。这一条把"能报错才算绿"从口号变成每次加门时的固定动作。
6. **（进阶）重构等价性举证。** 定"纯搬移必须给机械证据"的规矩：按文件性质选"声明级 / 行多重集合比对""起真实例抓运行时表逐条比对""分别打包比导出面"。关键是**不接受口头'没改逻辑'**。
7. **（进阶）结构棘轮。** 给最容易失控的度量（单文件行数、圈复杂度等）设上限 + 冻结豁免名单，只减不增，拆到达标就催你撤豁免。
8. **（文化）把自家门禁的失效如实写进状态文档。** 这条最难也最值钱：定义一套**不许夸大的措辞**（比如"实质全绿" vs "本体全绿"分开说），让"闸门此刻不能真报错"成为一个可登记、可追补的状态，而不是一句被"全绿"盖过去的尴尬。

一句话：**先做 1–3（数量基线 + 只信实测），你就拿到了这套方法八成的防护；4–5 补上"改软断言"这半个洞和可信度；6–8 是从"防糊弄"升级成"一整套反自报的工程文化"。**

## 八、局限：这套东西不覆盖什么

诚实起见，把边界摊开，免得读者按错预期去套：

- **N=1，单团队、单项目。** 本文所有"有效"都建立在一个由 AI 代理主力施工的全栈项目上，没有第二个项目的迁移记录，没有跨团队复现。它是"一个跑通了的做法"，不是"被验证普适的方法"。（同一母题的另一面——多代理协作链路里的假绿分类学与独立实测门禁方法——另文展开，本篇不重复其结论。）
- **缺命中率 / 逃逸率对照实验。** 我们有"闸门首跑就拦下真红"的天然数据点，但**没有**系统地把已知作弊样本喂进门禁、统计它拦下多少漏掉多少。因此本文能主张"我们这样组织了流程"，**不能**主张"能拦住 X% 的测试糊弄"。这是若冲学术必须先补的洞（见第六节末）。
- **"标红"是拦"合谋"，不是拦"无意"。** 测试同改闸门把"业务和测试一起动"变成一个需要书面裁决的信号，但它判断不了"这次改断言到底对不对"——那仍是人来读理由、抽查 diff。它提高的是糊弄的**成本与留痕**，不是自动判定正确性。
- **对"从头写一堆本来就空的测试"无效。** 基线管的是**倒退**；如果代理新写了一批名字花哨、断言全空的用例把数量顶上去，数量基线反而会被"增长"骗过。这类"注水增长"得靠人工复核新用例质量 + 变异测试那类"测测试"的手段兜底，不在这道闸的射程内。
- **口径依赖工具本身可信。** 正因为如此，第五节的自曝才不是花絮而是核心：一旦转调 / 正则 / 基线这些"抠数字的机械"自身有 bug，整套"只信实测"会退化成"只信一份坏掉的实测"。工具的可信度是这套方法的地基，也是它最脆的一环。
