## 摘要

一次用 `git filter-repo` 清洗仓库历史的常规操作，在非 bare 仓库收尾时把**被跟踪文件连同磁盘实体一并物理删除**，随后 `force-push` + `gc` 令本地再无回滚退路。事后靠三个彼此独立的时间窗口交叉对账完成全量抢救：**GitHub 端旧 commit 尚未被 GC 的窗口内按完整 SHA 直 fetch**、**IDE 本地历史兜底提交后未保存的改动**、**stash 与游离对象（`git fsck` 可达）捞回零散文件**；验收坚持**全量逐字节对账、不许抽查**，最终记录"真实未恢复项 = 0"。

本文不把它当"技术高超的救援"来卖。它真正的价值在两处：其一是把一次运气事件**沉淀成可复算的抢救链与"SOP 化的预防配方"**（只读体检→隔离克隆→逐文件 SHA256→回读磁盘才算数）；其二是**诚实标注方法的可迁移边界**——本次能救回来，高度依赖 IDE 本地历史这一"计划外冗余"，正如当事人自己所记"**纯属两个运气**"。**方法可迁移，运气不可迁移**；正因运气不可迁移，结论不是"下次也能这样救"，而是"下一次必须先有备份纪律，而不是事后补救"。本文给出根因（filter-repo 收尾 `reset --hard` 语义、为何本地无回滚）、抢救方法（三窗口 + 逐字节验收 + 可复算锚点）、清史安全配方（步骤化 SOP）、敏感数据误公开的三层根治，以及教训与局限。

**关键词**：git filter-repo；历史重写；数据抢救；逐字节对账；IDE 本地历史；git fsck；GitHub GC 窗口；仓库清史 SOP；敏感数据治理

## 1 事故经过（时间线）

> 说明：以下时序由本次事故所属批次的抢救记录条目重建（相关记录文件名含日期戳，即事发于该批次覆盖窗口内，具体日期对外不披露）。精确到小时的时刻未见于记录，故只给阶段次序与日期级锚点，**不虚构时刻**。事故项目为一 Ren'Py 多语言本地化仓库（本文匿名化为"项目 A"）。

1. **动因**：仓库里混入了需要清除的私有 / 个人资产内容，遂决定用官方 `git filter-repo` 重写已推送历史，一次性清洗隐私表述与文件历史版本——这一决策本身有先例、有正当性（同类需求在本知识矿的另几条批次记录里也出现过：一条是"清洗已推送历史中的隐私表述"，另一条是"私有产物清史"）。
2. **执行**：在**非 bare 工作仓库**上运行 `filter-repo` 完成重写，并 `force-push` 覆盖远端、随后做 `gc` 类清理。
3. **发现**：清洗生效后，工作区里的**个人资产与文档目录等整个从磁盘上消失**（事故现场原话："……整个从磁盘上消失了"）。`filter-repo` 按其语义把被跟踪文件从磁盘一并物理删除了。
4. **确认无退路**：`force-push` 已覆盖远端引用，`gc` 已收敛本地对象——**本地仓库层面已无回滚点**。这是本次最凶险的一点：常规"再 checkout 回来"的直觉失效。
5. **抢救**：分头利用三个窗口找回内容（详见 §3）——
   - GitHub 端被重写前的旧 commit 尚未进入 GC 窗口，用**完整 40 位 SHA 直 fetch**；
   - IDE 本地历史里保留了**提交后、未保存 / 未入库**的改动；
   - `git fsck` 可达的 stash / 游离对象里捞出零散文件。
6. **验收**：做**全量逐字节对账**（非抽查），记录"真实未恢复项 = 0""账目闭合""误删 1010 个文件"（口径与分级见附录 A）。
7. **落档**：整个过程写成一份抢救记录（文件名含日期戳），本节的时序即据此重建。

一句话复盘：**一次合法的历史清洗动作，叠加"非 bare 收尾物理删盘 + force-push + gc"三连，把可回滚操作变成了准数据丢失事件；救回来靠的是三条彼此冗余、但都不在计划内的时间窗口。**

## 2 根因：filter-repo 的收尾语义与"本地无回滚"是怎么形成的

### 2.1 filter-repo 为什么连磁盘文件一起删

社区反复踩过同一个坑（查重的公开先例见 §7）：`git filter-repo` **不只是重写对象库里的历史，它会改写工作区**。根因在收尾动作——

- 本知识矿一份清史配方记录对源码的回读结论：`git filter-repo` 在**非 bare 仓库**收尾时**一定会执行 `git reset --hard`**（该结论锚在 filter-repo 某一版本的源码收尾逻辑上，具体行号随版本变，见附录 A）。
- `reset --hard` 的语义是"把工作区强制对齐到重写后的新 HEAD"。于是凡在新历史里被剔除的被跟踪文件，工作区里对应的**磁盘实体文件随之被删**；更糟的是，它还会**吞掉尚未提交的改动**（未入 git 的对象，`reset --hard` 直接抹平）。

所以"历史被清掉了"和"磁盘上的文件也没了"是**同一个收尾动作的两面**，不是两个独立故障。这也解释了为何直觉里的"`git checkout` 一下不就回来了"失效——磁盘实体已经不在，索引与 HEAD 也已被重写。

> 附注（同源副作用）：filter-repo 重写会**顺手剥掉上游托管平台签名提交的 `gpgsig` 头**，导致提交号全变（同一份清史配方记录所载）；这也意味着"提交 SHA 变了"本身就是历史被重写的信号，可作为事后判据。

### 2.2 "本地无回滚"由三连叠加造成

单次 `filter-repo` 未必致命，致命的是它和两个动作连做：

1. **`force-push` 覆盖远端引用**——原本还能从远端旧引用找回的路径被切断；
2. **`git reflog expire --expire=now --all && git gc --prune=now`**（这正是本知识矿一条"清史 runbook"记录里的**收尾步骤**，本意是清残留、防旧对象回流）——一旦误删，这一步反而**主动摧毁了本地最后的游离对象兜底**。

三者叠加后，本地仓库内已经没有可信的回滚点。**唯一还没被本地操作污染、且仍持有旧 commit 的对象，只剩"远端托管平台尚未 GC 的旧对象"和"仓库之外的 IDE 本地历史 / 备份"——它们都不是"计划内的备份"，而是恰好还没关上的窗口。** 这就是 §3 三窗口抢救的由来，也是"运气"二字的工程含义。

### 2.3 为什么"被清的东西"里混着不该清的东西

跨批次复看，误删之所以发生，还有一个共性前置：个人资产 / 记忆整份备份被塞进了项目目录、随仓库一起被跟踪（本知识矿清史配方记录明确记为"泄漏根因常是个人资产被塞进项目目录随仓库分发"）。清史目标与"被跟踪但本就不该在库里"的内容混在同一棵工作树里，`filter-repo` 一把梭删盘时，边界就没分清。**这条会在 §5 作为"源头隔离"层根治。**

## 3 抢救方法：三窗口交叉对账 + 逐字节全量验收

核心思想：**没有任何单一窗口能救回全部**——GitHub 旧 commit 只到"最后一次成功推送的提交版"，IDE 本地历史只覆盖"编辑器经手的文件且在保留期内"，游离对象只包含"曾经 `git add` / stash 过的 blob"。三者覆盖范围部分重叠、各有盲区，因此**必须交叉对账**，取三者的并集，并在"提交版 vs 未保存改动"之间逐文件取舍（抢救链记录把其精度定位在"提交版 vs 未保存改动"的取舍上）。

### 3.1 窗口一：GitHub 端旧 commit 的 GC 窗口，按完整 SHA 直 fetch

- **原理**：`force-push` 只是移动了分支引用，**被重写前的旧 commit 对象在服务端不会立刻消失**，要等托管平台自身的后台 GC。在此窗口内，只要还握着旧 commit 的**完整 40 位 SHA**，就能把它直接 fetch 回来，即便它已不在任何分支上。
- **关键前提**：SHA 必须是**完整的 40 位**（短 SHA 不可用于直 fetch 游离对象）。所以抢救第一步往往是去 reflog、去 PR/commit 页面、去本地终端历史里**把旧完整 SHA 抠出来**。
- **可复算锚点**：
  ```bash
  # 1) 找回旧完整 SHA（本地 reflog / 终端历史 / 托管平台 commit 列表页）
  git -C <repo> reflog --all | grep <关键字>
  # 2) 在对象被 GC 前，按完整 SHA 直 fetch
  git fetch origin <40位完整SHA>
  git show <40位完整SHA>            # 确认内容确为删前版本
  git checkout <40位完整SHA> -- <被删路径...>   # 只取回需要的路径
  ```
- **窗口长度**：社区公开口径是"旧 commit 在未被后台 GC 前有一段时间窗口可按 SHA 直取"（属**外部经验口径、非本次实测**，具体天数无权威出处，本文不给精确值，见附录 A）。工程结论是：**这个窗口是"抢时间"的对象，不能赌它一定还在。**

### 3.2 窗口二：IDE 本地历史——本次真正的兜底

- **原理**：多数 IDE（含 VSCode 时间线）会在编辑器内维护一套**独立于 git 的本地文件历史**，保留提交**之后**、甚至未保存 / 未入库的改动。git 层面被 `reset --hard` 抹平的东西，在这里往往还在。
- **为什么它是"计划外冗余"**：它不是为"救 git 事故"而存在的，保留期有限（社区经验口径为"数天量级"，属外部经验值、非本次实测；精确天数无权威出处，本文不写死）。本次能靠它兜回关键内容，是**恰好命中保留期**——这正是"运气"所在，也是 §6 的诚实重点。
- **可复算锚点**：定位 IDE 的 local history 存储目录（各版本不同，**按当前所用版本现查、勿照抄路径**），按文件名 / 时间戳找回删前内容，再与窗口一的提交版逐文件比对，决定"取提交版"还是"取编辑器里的更新版"。

### 3.3 窗口三：stash 与游离对象

- **原理**：只要内容曾进入 git 对象库（`git add` 进 index、被 `stash` 过），即使引用被 `gc` 掉，短期内 `git fsck` 仍可能报出 `dangling` / `unreachable` blob，用 `cat-file` 取出。
- **可复算锚点**：
  ```bash
  git fsck --unreachable --no-reflogs        # 或 --lost-found，列游离对象
  git cat-file -p <unreachable-blob-sha> > recovered/<name>
  ```
- **注意**：本窗口在"事后又跑了 `gc --prune=now`"时会被严重削弱——**抢救动作越早，游离对象窗口越宽**。这与 §2.2 的教训一致：清残留的 `gc` 是双刃剑。

### 3.4 验收：全量逐字节对账，不许抽查

这是本案例在"方法"上最可迁移、也最反直觉的一条纪律：

- **不许抽查**：抢救完成后，人的本能是"点开几个文件看看对不对"。本案例明确**禁止抽查**，做**全量逐字节**比对——因为 `reset --hard` / 编码 / 换行符造成的破坏常常是**个别文件的个别字节**（`\r\r\n` 翻倍、BOM 累加、UTF-8↔GBK 变形），抽查几乎必漏。
- **逐字节一致的判据是"可证伪"的**：不看"能不能打开"，看"哈希 / 字节是否严格相等"。记录给出"真实未恢复项 = 0"，并把结论精度钉在"快照晚于最后提交"这一限定上（另有一项"逐字节一致"的具体计数，其计量单位口径不明，已按附录 A 存疑项处理、正文不引精确值）。
- **可复算锚点**（Windows / PowerShell 环境）：
  ```powershell
  # 逐文件 SHA256 比对：以"删前清单"为基准，对每个恢复文件算哈希并与基准比对
  Get-FileHash -Algorithm SHA256 (Get-ChildItem -Recurse -File recovered) |
    Export-Csv recovered.sha256.csv -NoTypeInformation
  # 单文件字节级差异（非 git 跟踪的两个目录）
  git diff --no-index -- <baseline-dir> <recovered-dir>
  ```
- **"回读磁盘才算数"**：验收以**磁盘实据**为准，不信任何"工具报成功 / 面板显示已恢复"。此纪律源自同类反复出现的取证事故——"Write 报了 create file success、还回显了完整 diff，可它其实没落盘"（本知识矿清史配方记录所载），以及"三级指纹（文件 / 目录树 / 提交）逐一吻合后才移动远程指针"的逐对象按字节重建法（另一条批次记录所载）。二者共同构成"**对账 = 逐文件哈希 + 回读磁盘**"的验收内核。

> **本节与查重的关系**：单看每个机制（按 SHA 直 fetch、fsck 游离对象、IDE 本地历史）都有大量公开先例（§7）。本文主张的新意**只在组合与判据**：三源抢救链 + "逐行独有行 = 0 / 逐字节一致"的可证伪判据 + 全量逐字节对账。故 §3 是"把已知零件按可复算锚点装配成一条抢救流水线"，不是宣称发明了某个零件。

## 4 "清史不伤工作区"安全配方（步骤化 SOP）

§2 的病根是"在非 bare 仓库上让 filter-repo 收尾 `reset --hard`"。根治思路：**把"重写历史"这个动作，从"活工作区"里挪出去，让被删风险与在制 / 并发改动物理隔离。** 本知识矿清史配方记录给出的旁路配方——**临时克隆 + `update-ref` + `rm --cached`，全程不 `reset --hard`、不删磁盘文件**——正是本配方的骨架；事故抢救链记录里的"九步安全撤库 SOP"是其操作化。

**SOP（步骤化，可逐条自检）：**

1. **先只读体检，禁止先动手。** 在真正改写前，只做只读侦察：列清"哪些是本次清洗目标、哪些只是恰好同在工作树里不该碰"，把"要删的"和"会被误删的"分开。判据：任何结论都回读磁盘 / 实跑核实，不照抄过期清单（照抄过期清单 = 重复事故源）。
2. **先做"仓库外"的完整备份，再谈清理。** 打 `git bundle`（本知识矿历史清洗 runbook 记录：先打 31.7MB bundle 再 rewrite）；关键个人资产另做**仓库外磁盘备份**，因为一旦脱离 git 跟踪又进 ignore 区，`git clean -fdx` 一句就能把 61MB / 1688 个文件无可恢复地抹掉（某清史配方记录的预防性反例警告，非事故实测）。
3. **在仓库外做一次临时克隆（bare / 独立目录）。** 重写历史只在临时克隆里发生，**绝不在正在使用的工作区里跑 filter-repo**。
4. **临时克隆里完成历史重写。** 把 `filter-repo` 的破坏半径锁死在"一个可丢弃的副本"里。
5. **用 `update-ref` 把重写结果落回目标引用**，而不是靠 `reset --hard` 去"对齐工作区"——**这一步是"不伤工作区"的关键差异**：`update-ref` 只动引用，不碰磁盘实体。
6. **需要移除工作区里的被跟踪内容时，用 `git rm --cached`（脱跟踪）而非删盘**，把"从历史里消失"与"从磁盘上消失"解耦。
7. **并发保护：清史期间冻结在制 / 并行会话对同文件的写入。** 旁路清史配方的明确场景是"在并发写文件时安全清史"——临时克隆法之所以安全，正是因为它不与并行工作区争抢同一棵工作树。
8. **逐文件 SHA256 对账 + 回读磁盘验收。** 清洗后，对"本应保留"的文件逐个算哈希并与备份基准比对，以磁盘实据确认"没被误伤"。
9. **最后才谈 `force-push` / `gc`。** 且推之前对 `staged` 做**反向敏感扫描**（防把敏感内容又推上去），并如实声明**不可控边界**（§5 第三层）。

> 一句话配方：**"重写"关进临时克隆，"落回"只动引用（update-ref / rm --cached），"验收"回到磁盘逐文件哈希。** 让 `reset --hard` 从清史流程里彻底消失，磁盘实体自然不会被物理删除。

**与 §2 的闭合**：本 SOP 的每一条，都对应 §2 的一个根因——步骤 3–6 消解"非 bare 收尾删盘"、步骤 9 消解"gc 自毁退路"、步骤 1/8 消解"边界没分清 + 抽查漏检"。

## 5 敏感数据误公开的三层根治

清史是"事后补救"，成本高且有硬边界。真正的根治在**三层前置**，越靠前越有效：

- **第一层 · 源头隔离（最有效）**：个人资产、记忆整份备份**绝不塞进项目目录**、绝不随仓库分发。跨批次复盘显示，泄漏的根因常常不是"密码写进了代码"，而是"把跨项目个人记忆库的整份备份放进了项目子目录，于是它躺在私有托管仓库里、随每个仓库分发"（本知识矿清史配方记录）。**把不该进库的东西挡在工作树之外，比事后 filter-repo 便宜一个数量级。**
- **第二层 · 提交前闸门**：备份只镜像本项目子目录、逐件校验码比对、**绝不跑 `/MIR`**（`/MIR` 会把目标侧多出来的文件静默删掉），**推送前对 `staged` 做反向敏感扫描**（事故抢救链记录所载的记忆备份纪律）。即在 `git push` 前设一道"扫敏感"的机械闸。
- **第三层 · 事后清史（有硬边界，须诚实）**：真误公开了，走"bundle 备份 → filter-repo 重写全历史 → 强推 → 下游服务器 `reset --hard origin/<branch>` 对齐 → 可选 `reflog expire + gc --prune=now` 清残留"（历史清洗 runbook 记录）。但**必须如实声明不可控边界**：**托管平台缓存、搜索引擎快照、别人的 fork 不在 git 可控范围内**（同一 runbook 记录原话）。也就是说，第三层"洗不干净"——这反过来正是"前两层比第三层重要"的论据。

> 三层的排序即优先级：**能靠第一层避免的，绝不留给第三层去救。** 本次事故（§1）本质是"只做了第三层、且第三层的收尾步骤反过来咬了本地"，教训正在于此。

## 6 教训与局限：运气不可迁移 → 故须前置备份纪律

这一节是本选题的"诚实点"，也是它区别于普通"我如何神勇恢复"帖的地方。

- **成功高度依赖计划外冗余。** 三窗口里，真正兜住关键内容的是 **IDE 本地历史**——它保留期有限（社区经验口径为数天量级、非本次实测）、并非为救 git 事故而设计。当事人自己写得很清楚：**"这次能救回来纯属两个运气"**。对应的交叉验证记录据此给该条打了"**需补**"限制：**"方法可迁移、运气不可迁移"**。
- **所以结论不能是"下次也能这样救"。** 若把它当"救援手册"卖，是在教人依赖运气。正确的沉淀方向是把纪律**前置**：§4 的"清史不伤工作区"配方让"删盘 + 无回滚"从流程上不可能发生；§5 的第一 / 二层让"误公开"根本不进入需要清史的境地。**能避免事故的，永远优于能挽救事故的。**
- **验收纪律是唯一可无条件迁移的硬功夫。** "全量逐字节对账、不许抽查""回读磁盘才算数""工具报成功不算数"——这三条不依赖运气，在任何数据操作中都可复算，是本文最想外发的部分。
- **二手性与数字存疑必须显式承认。** 本文数字取自知识矿**台账（二手摘要）**，交叉验证已声明"未下钻原始会话 digest 独立复现"。凡账目闭合、2352 条历史、误删 1010 个文件之类，发表前须回原记录复算，口径不明者一律降级为存疑（附录 A）。**不把"台账属实"偷换成"事实已独立复现"。**

## 7 结论

`git filter-repo` 误删不是"手滑"，而是**语义可预期、后果被三连放大**的一类结构性风险：非 bare 收尾的 `reset --hard` 删盘 + `force-push` 切远端 + `gc` 毁本地兜底。本次靠三窗口交叉对账 + 全量逐字节验收救回，是**方法**（可迁移）撞上了**运气**（不可迁移）。

因此本文交付两份东西而非一个故事：
1. 一套**可复算的抢救流水线**（§3：按 SHA 直 fetch / IDE 本地历史 / 游离对象，配逐文件 SHA256 验收与命令锚点）；
2. 一套**让抢救不必发生的前置配方**（§4 "清史不伤工作区" 九步 + §5 三层根治）。

**新意不在任何单一机制**（皆有公开先例），**而在组合与判据**：三源交叉 + 可证伪的逐字节全量对账 + 不伤工作区的旁路清史。**并且诚实地说：它的高光时刻（IDE 本地历史兜底）恰恰不可复制——这正是必须把它降级为"备份纪律"而非"救援技巧"的理由。**

（注：本文与同批另一篇"工具报成功但未落盘 → 回读磁盘才算数"主题的稿子在该判例上局部重叠，本文仅在 §3.4 引用其内核，另文展开。）
