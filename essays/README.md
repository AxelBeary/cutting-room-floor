# 写给一个每次开工都会失忆、用的工具还会漏读长行的读者

> 为 AI 设计文档的物理形态 · 技术博客长文（初稿）
> 性质：车间初稿，未过脱敏闸；所有实测数字为某时点实测、发布前复算。
> 例证来自一个真实在跑的约稿平台项目，本文以「拾绘」称之。

## 这段写作想讲什么

我们习惯假设文档的读者是人：会累、会烦、会跳着读，但记忆相对稳定，看到「这里被折叠了」会自己伸手展开。

现在有一类新读者不这样。它每次开工都是一张白纸，会把你上一轮否决的方案当成新点子重新提给你；而且它不「看」文件——它用 grep、diff、工具链去读，那些工具对超长行、对结果条数、对显示宽度都会截断、会折叠。

于是问题变了味：给它的文档，写得好不好只是一半，长什么形状是另一半。行有多长、看板多大、正文留几条、搬动怎么校验——这些物理形态，直接决定它读不读得到。

这篇文章讲一个真实项目怎样围着这个读者的失效模式给文档立法、又在哪里没执行到位。

## 全文导览

1. 一个跟人类很不一样的读者 — 失忆 / 重蹈覆辙 / 工具失真三条失效模式
2. 体例是失效模式的影子 — 每条失效模式对应的一处物理设计
3. 连「为什么这么写」也要为读者校准 — 把 ripgrep 那处归因讲准（本文最想留人的一处）
4. 这些零件，别人也都造过 — 公开先例避让与真差异所在
5. 如果你也想这么干 — 与语言、工具无关的可迁移清单
6. 我还没做到的，和这套做法的边界 — 规则执行落差与经验数字缺测量
7. 闭环：这篇文档的由来，也可能正是它想服务的那个流程造出来的 — 对本文自己执行「别过度归因」
8. 数字与出处复算清单 — 每个实测数字的复算方式
