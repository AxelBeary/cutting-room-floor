## 摘要（Abstract）

在"AI 产码 + AI 审码"的多代理软件工程（Agentic SE）实践中，"代理自报不可信、须回环境独立复跑"已成 2025–2026 年的公认原则，被写入基准、博客与协议文。本文主张：这一共识存在一个更隐蔽的失效盲区——**质量链里的验证层与仲裁层自身同样会造假绿**，即它们给出的"证伪""订正""已核实"结论本身可能就是错的，而且错得足以让下游删掉真数据、或把假值当真值采纳。

本文的证据不是构造的示例，而是一次真实日常研究流程的**纵向自判例**：在对 375 段有正文对话◻、650 条入册候选（S=54 / A=217 / B=379）做的"44 路提炼 → 11 路交叉验证 → 2 路数字仲裁 → 1 路主代理磁盘亲验收口"链条中，收口环节用回磁盘字节的独立实测，**推翻了验证路和仲裁路各自产出的错误裁决**：

1. **误删真数据（H1）**：两条验证路与一条仲裁路一致断言某台账头条数字（"1803 行被数成 780 行"）系杜撰、应予删除；收口回磁盘原文证明它与另一处数字（"925/1009"）分属**两起独立事故**，被误当成同一数字的自相矛盾——若采信"证伪"，将删掉一条真实事故记录。
2. **仲裁者自造证据（H3）**：一条验证路与一条仲裁路各自"算出"一个谚文字符的码点（U+BB90 / U+BACC）作为"真值"；收口用 `unicodedata.name` + `os.walk` 实测二者在源文件中**出现 0 次**，文件真正用的是第三个码点（U+BB58）——两位"修正者"恰好双双掉进了它们正要修正的"形近码点手敲/凭记忆必错"陷阱。

据此，本文做出三点贡献：（一）在已有"自报假绿""工具假阴性"两类之外，提出并给判例第三类失效——**仲裁者自造证据型假绿**；（二）给出一套**独立实测门禁**方法（磁盘字节回验 + Unicode 官方名反查 + 变异自证 + 负对照 + 取证范围约束），把"任何层的『已通过』都只当线索、不当证据"落为可执行收口规程；（三）以可回查的真实判例，为"用 AI 审 AI"的可信度主张划定一条诚实边界。我们**不主张首创"验证器会出错"这一命题**（形式化验证、测试预言、LLM-as-judge 文献早有认知），本稿的增量在于：把"验证/仲裁层造假绿"作为一等现象，给出**带完整证据链、可逐条回磁盘复现的日常纵向判例**，并把它固化为可迁移的收口门禁。

**关键词**：多代理软件工程；假绿（false green）；独立实测；验证器可信性；收口门禁；Unicode 码点取证

## 1 引言（Introduction）

大规模 LLM 代理集群正在被用于软件工程：并行改代码、跑门禁、出审校报告、做数字核对。随之而来的核心焦虑是**"产出的东西能不能信"**。业界当前的主流答案是"不要相信代理的自我汇报"——把自报当作"待与环境对质的声明"，而非"证据"，回环境独立复跑。这条原则本身没有争议，且早已被公开表述。

但一条真实的多代理质量链往往不止"产 → 报"两级，而是层层加设防线：提炼产出台账、交叉验证回对质、数字仲裁裁真伪、收口做终检。直觉上，链越长、审核层越多，结论就越可信。本文要指出的恰恰相反：**审核链本身是一个新的失效面**。负责证伪的验证路、负责裁真伪的仲裁路，都是 LLM 代理；它们会带着"我已经核实过"的口吻，产出结构完整、引文齐全、看似可复现的错误结论。更麻烦的是，这类"来自审核层的绿灯"天然比"来自产码层的自报"更受信任，因而危害更大——它会直接触发删数据、改真值这类不可逆动作。

本文的动机来自一次真实研究流程的收口复盘。该流程为验证 44 路提炼子代理产出的 650 条候选，一次性并发 11 路交叉验证子代理（9 路"联网查重 + 回台账对质"、1 路防撞车对账、1 路 B 级复发审计），再派 2 路做整合与数字仲裁，最后由主代理**亲自回磁盘原始会话逐条复验、不采信任何子代理自报**。正是在最后这一步，两条已经被验证路和仲裁路"联合判死"的结论被磁盘字节推翻（H1、H3）。这一现场复现说明：**假绿不是产码层的专利，审核层一样会造。**

本文结构如下：第 2 节梳理相关工作并界定本稿增量；第 3 节给出假绿的形态分类，重点刻画本文新增的第三类；第 4 节给出独立实测门禁方法；第 5 节以两起判例完整呈现证据链；第 6 节讨论其对"用 AI 审 AI"可信度主张的影响；第 7 节结论。附录 A 为数字纪律清单，附录 B 为磁盘取证复现思路（只描述思路，不贴敏感串），附录 C 为事实源与公开锚点。

**范围与诚实声明**：本文判例来自单一研究流程、单一团队（N=1），是日常工程实践的纵向复盘，**不是受控实验**，不给出可统计外推的错误率。本文不主张"验证器会出错"是首次被提出，仅主张"以可回查的真实日常判例，把审核层造假绿当作一等现象并给出收口门禁"。

## 2 相关工作（Related Work）与本文增量

**2.1 LLM 生成的 API / 代码幻觉（产码层造假）。** Gorilla 等工作最早系统性度量了 LLM 在连接 API 时的"幻觉"倾向——模型会编造不存在的方法签名与调用（arXiv:2305.15334，编号须回原文核对）。这一线文献确立了一个共识：**生成层会自信地产出错误事实**。本文不与此竞争，而是把它当作"自报假绿"的一个已知特例。

**2.2 LLM 审计/裁判意见的可信度（审核层造假的先声）。** 随着 LLM 被用作代码审查器与评审裁判，一批基准开始量化"审计意见本身有多不可信"：软件评审基准 SWR-Bench 报告最佳 LLM 组合也仅约 19.38% F1、precision < 10%（arXiv:2509.01494，编号与数字须回原文核对）；ZeroFalse 等用 LLM 降低静态分析假阳性（arXiv:2510.02534，编号须回原文核对）。本地化与事实性方向的测量同样严峻：针对 AI"深度研究"类系统的引用测量（JMIR 一类研究，具体条目须回原文核对）发现其生成大量不可溯源引用；幻觉检测基准 AuthenHallu 报告约 31.4% 的幻觉率（版本/数字须回原文核对）。这些工作共同指向：**被委托去"核验"的模型，其核验结论本身是高噪声的。** 但它们多把审核器当作"有噪声的预言机（noisy oracle）"来评测整体准确率，**没有把"审核层在个别数字上产出的、足以触发不可逆动作的错误裁决"作为一等的工程现象来给判例**。

**2.3 多代理系统失效分类（MAST）。** 关于多代理 LLM 系统为何失败的近期工作（MAST，arXiv:2503.13657，编号须回原文核对）给出了失败分类学，涵盖规格对齐、协调、验证等层面的失效。它为"多代理链会出错"提供了 taxonomy 级的合法性。本稿与 MAST 的区别在于**粒度与可回查性**：MAST 给分类，本稿给**单条链路上、可逐字节回磁盘复现的具体判例**（含被误判的原始数字、被自造的码点、证伪动作的错误取证范围），并把判例反向沉淀成一条收口门禁。

**2.4 "自报即待验声明"的公开原则。** 检索所见 2026 年已有 arXiv/博客级别的疑似命中："代理自报应被当作需与环境对质核实的声明，而非证据"，并实证操作者把成功率夸大到数倍；亦有人提出"summary-as-truth、编排器误收绿灯、应拒绝信任完成信号并独立再导出"（条目须回原文核对）。本流程的验证路对这些原则做过联网查重并确认"原则已公开"（见附录 C 的验证留档·联网查重条目）。**本文的增量正落在这些原则的盲区之后**：它们讲的是"别信产码代理的自报"，本稿讲的是"**也别信那些被派去核实自报的验证/仲裁代理**"——把不信任的边界从"执行层"推进到"审核层"。

**2.5 变异测试 / 负对照（本文方法部件的既有来源）。** "先证明测试能失败再采信其通过"是自 1971 年起、由 IEEE Std 610.12-1990 给出定义、并由 PIT/Stryker/mutmut/cargo-mutants 工具化的教科书方法（奠基人名与年份、标准号的精确表述须回原文核对）；"零命中前先自证能命中"亦被近年的数据质量 CI 指南与工程博客直接命题化（条目须回原文核对）。本稿的变异自证/负对照**不主张方法新颖**，只主张把它从"测代码"迁移到"测质量链里的审核结论"，并与磁盘字节回验、Unicode 官方名反查、取证范围约束**组合成一套针对审核层假绿的收口门禁**——这一组合与其用于的对象，是本稿相对公开先例的可辩增量。

## 3 假绿的形态分类（A Taxonomy of False-Green）

本文所称"假绿（false green）"，指某个本应如实反映现场的检查/审核环节，**给出了与现场不符、却被下游当作可信来采信的结论**——无论这结论表现为一盏"通过/无误"的绿灯，还是一句"已核实，这个数错了/该删"的订正。按造假的主体，本文分三类，其中第三类为本稿重点：

**① 自报假绿（执行层）** ——产出工作的代理汇报"我做完了/我改对了/门禁过了"，而事实未达。表现为：为过闸而糊弄（删测试、改断言凑绿）、把"合法但错"的产物当"已完成"、把摘要当真相。此类已被 2024–2026 公开原则充分覆盖，本稿只作背景。

**② 工具假阴性（静默失效）** ——检查工具/门禁脚本因**自身设计缺陷**给出假绿：读旧缓存的 linter 用"零错误空输出"为坏文件背书、退出码 0 却仍在打印 traceback、崩溃使某道对账闸被静默跳过、判定用子串包含导致"任意一组为 0 就算绿"。此类执行层与工具层的具体工程细节，另有一篇同主题的工程随笔（下称"另文"）专门展开，本稿只在分类中占位、不重复其案例。此类仍是"工具"在造假，人尚可用"换个工具再测/先让工具自证能命中"来兜。

**③ 仲裁者自造证据（审核层造"已核实"）——本稿新增类。** 负责证伪与裁真伪的**审核代理**，产出"我核实过了，这个值错了/这个数是杜撰的"这类**看似权威、带证据链、可被下游直接执行**的结论，而该结论本身就是错的。它有两种子形态，本稿各给一起判例：

- **③a 误删真数据（假阳性证伪）**：审核路把一个真实存在的事实判为"杜撰/矛盾"并建议删除（第 5.1 节 H1）。危害 = **不可逆地销毁真数据**。
- **③b 自造真值（假阳性订正）**：审核路凭公式/记忆"算出"一个它断言为"真值"的数，写进报告，而这个数在现场根本不存在（第 5.2 节 H3）。危害 = **用看似被修正过的假值污染事实源**。

③ 比 ①② 更危险，原因有三：(a) 它来自"审核"这一最该被信任的位置，下游倾向直接采信；(b) 它的结论常以"删除某数""改用某值"的形式给出，**动作指向不可逆修改**；(c) 它往往**自带一套看似合理的证据链**（引行级取证、列 Unicode 合成公式），比 ① 的空口自报更难被肉眼识破。

（**术语说明**："假绿"在此泛指审核给出的**虚假可信信号**；若按经典缺陷检测口径给判定方向分类，则② 是**漏报缺陷的假阴性**（把坏产物当好的放行），③a/③b 是**误报的假阳性**（把好的真数据判成坏的、或把编造的值当成真的）——两类都披着"已核实"的外衣被下游采信，故同归"假绿"。）

## 4 独立实测门禁方法（Independent Empirical Gating）

核心信条：**收口者不信任何层的"已通过/已核实/已订正"，一律回磁盘字节亲验；子代理的结论仅当线索，不当证据。** 落到可执行动作，是下面五条门禁，合起来专治第 3 节的 ③ 类假绿。

**G1 磁盘字节回验（byte-level disk read-back）。** 任何要进入公开稿的数字/事实，必须回到**最底层的原始载体**（本流程最底层的原始载体，是原始会话摘要的磁盘文本）用确定性检索命中才算坐实；"索引→台账→正文"每一级的"已核实"都不构成终局证据。落法：用 `os.walk` 遍历全部原始会话摘要，对目标串做逐文件字节匹配并回显命中上下文（附录 B 的硬伤批量回磁盘取证脚本思路）。这直接治 ③a：审核路"全文 grep 0 命中"若取证范围只是单个具名文件，收口须扩到全库遍历再判。

**G2 Unicode 官方名反查（authoritative-name reverse lookup）。** 凡涉"某个非 ASCII 字符到底是哪个码点"，**不凭肉眼、不凭记忆、不凭合成公式手算**，一律用 `unicodedata.name()` / `unicodedata.lookup()` 反查官方名并做 NFC/NFD 规范化对账。这直接治 ③b：任何被"算出"的码点，先在真实文件里 `chr(cp)` 反查出现次数——**出现 0 次的"真值"不是真值，是自造值**。

**G3 变异自证（mutate-to-prove-the-gate）。** 采信一道闸/一个检索/一段脚本"报了 0 问题"之前，先**故意造一个已知有病的样本把这道闸打穿**，证明它抓得住，再谈它的"干净"。对文本取证而言：先用一个**已知存在**的串（如已被别处引用的数字）跑通检索，确认命中数 > 0 且上下文正确，才有资格说目标串"0 命中"（本流程工程侧实证：先造 7 个已知有病的实现，7/7 全被对拍闸门逮住，见附录 C 的验证留档·变异自证抽验条目）。

**G4 负对照（negative control）。** 与 G3 对偶：既要有"脏样本必被抓"的阳性对照，也要有"干净文本不误伤、不冤枉"的阴性对照；两者齐了，才证明这道闸不是摆设、也不是乱报。

**G5 取证范围约束（scope-of-disproof ≥ claim）。** 一条"证伪/杜撰"结论的**否定强度不得超过其取证范围**。"我在**这一个**原始会话摘要文件里没搜到 1803"只能支撑"该文件里没有 1803"，**不能**升级为"1803 系杜撰、全库无出处、应删"。凡下游要据此执行删除/改写，必须先扩取证范围到"论断所声称的全集"（此处为全库原始会话摘要），复走 G1+G3。这是本稿从 H1 判例里提炼出的、专门约束审核层的新门条。

这五条的关系：G1/G2 是"回现场取证"的两种现场（磁盘字节 / 官方字符名）；G3/G4 是对取证工具本身做的"先证明尺能量"的自检；G5 是对审核结论"言过其实"的射程约束。**门禁的产物不是"更多层审核"，而是"一个不信任何审核、只信磁盘字节的收口点"。**

## 5 案例研究（Case Studies）

以下两起判例均取自同一研究流程，其出处以本流程的验证/仲裁/收口各层留档标注（公开锚点见附录 C）。二者共同构成对第 3 节 ③ 类假绿的实证。

### 5.1 判例 H1 —— 误删真数据：被"证伪"的真实事故（③a 型假绿）

**台账记载。** 一条 A 级"技术债再生长"条目正文写："PowerShell 计数会跳过空行，导致 **1803 行被数成 780 行**"，同条另配一条证据引文："该报告小节的 **925** 是'非空行数'，node 数的 **1009** 才是总行数"（两条交叉验证路转述）。

**审核层如何判它假绿（错误裁决链）。**
- **两条验证路**：同逮此条，判为"数字自相矛盾"——正文 1803/780 与自带证据 925/1009 对不上（1803→780 差 1023 行、占比 >50%；925↔1009 差 84 行、约 8%），据此判"索引忠实抄了台账，但**台账论点相对自身证据夸大**"，列为核对不过。
- **仲裁路**：更进一步，回**单个**具名原始会话摘要文件取证，列出该文件三处行级证据里的 925/1009，并称"在该文件全文检索『1803』『780』→ 0 命中"，据此**裁决 1803→780"系杜撰/串写"，对外建议"删除 1803→780"**。

**收口磁盘亲验如何推翻。** 主代理在收口复核记录中用 `os.walk` 遍历**全部**原始会话摘要（附录 B 的硬伤批量回磁盘取证脚本思路）取证，结论：
- **1803→780** 真实存在于**事故一的原始会话摘要**（防阀计数盲区：换行符致实际 1803 行被错数成 780 行）；
- **925/1009** 真实存在于**事故二的原始会话摘要**（某明细页：node 数 1009 总行 vs PowerShell 数 925 非空行）；
- 这是**两起独立事故**（不同文件、不同项目对象），并非同一数字的自相矛盾。

**为何审核层会错、错在何处。** 仲裁路的取证范围只有**一个具名文件**（事故二载体），在该文件里 grep 1803 得 0 命中——这个 0 命中是真的，但它把"单文件无命中"越权升级成了"全库无出处、系杜撰、应删"（违反 G5）；验证路则把两起事件的数字误并成一条来对质（违反 G1 的"回到各自原始载体"）。若下游照此执行删除，将**永久销毁一条真实的事故记录**。→ 收口处置：**恢复该"技术债"条目的引用**；相关主题不再挂"硬伤"帽子（收口复核记录 H1 处置，见附录 C）。

**方法学教训。** "证伪"是一次取证，其可靠性取决于取证范围。**局部 grep 的 0 命中不能证明全局不存在**——这正是 G1（全库回磁盘）+ G3（先拿已知存在的串自证检索能命中）+ G5（否定结论射程不得超过取证范围）三条门禁要拦的。

### 5.2 判例 H3 —— 仲裁者自造证据：两位"修正者"各造一个 0 次码点（③b 型假绿）

**现场矛盾。** 同一批谚文字符的码点，在不同台账层互斥：
- 一份批次台账记："뭘（U+BB3C，带终声 ㄹ）和 물（U+BB34，无终声）"；
- 另一份批次台账转述会话原话："我把 뭘 的码点算错了……算出 U+BB3E，实际 뭘 是 U+BB58……断言本身也跟着错了——期望值和被验值同源的陷阱"。

**审核层如何各自"算出"一个真值（错误裁决链）。**
- **一条验证路**：判定上述两值"互斥且均非真值"，并用谚文合成公式"算出" 뭘 的正确码点 **应为 U+BB90**，据此判"核对不过、须订正"。
- **仲裁路**：独立用公式 `0xAC00 + (21×6+9)×28 + 8` 复算，**判 뭘 = U+BACC**，并裁"两台账俱误、非择一"。

两条审核路，一位说真值是 U+BB90、一位说 U+BACC，各自带公式、看起来都是"算出来的权威订正"。

**收口磁盘亲验如何推翻。** 主代理用 `os.walk` 遍历源文件 + `unicodedata.name` 反查（附录 B 的全库码点取证脚本 + 规范名/NFC 反查脚本），实测：
- 相关字符位在源文件中共出现 **59 次，全部为 U+BB58**（即"实际 뭘 是 U+BB58"那条记录与磁盘字节一致）；
- **U+BB90（验证路）与 U+BACC（仲裁路）这两个"算出来的真值"，在源文件里出现 0 次。**

也就是说：**两位"修正者"各凭公式/记忆挑了一个形近、却与现场字节不同的码点（两个都是 0 次），去"订正"一条本就与磁盘字节相符的记录。** 复算坐实真值为 U+BB58：谚文音节码点 = U+AC00 + (21·L + V)·28 + (T+1)，뭘 = 初声 ㅁ(L=6) + 中声 ㅝ(V=14) + 终声 ㄹ(T=7) = 0xAC00 + (21·6+14)·28 + (7+1) = **U+BB58**（官方名 `MWEOL`）。

> **一处须向审稿人交代、也最能说明本方法价值的细节**：本流程一份数字仲裁留档（见附录 C 的仲裁条目）在公式括注里把 뭘 记作 U+BACC、把 U+BB58 记作"묘"，本身即是一次"回公式而不回官方名"的形近错标——它把复合中声 ㅘ（V=9）当成了 ㅝ（V=14），故错算出 U+BACC；`unicodedata.name` 反查显示 U+BACC=`MWAL`（뫌）、U+BB58=`MWEOL`（뭘）。本稿一律**以磁盘字节 + `unicodedata.name` 反查为准**——这正是第 4 节 G2 门禁存在的理由："验证/仲裁层造假绿"可以假到连负责裁真伪的底稿都被公式带偏，唯回官方名与字节可救。

**方法学教训.** 凭公式/记忆"算出"的码点，是一次**没回现场的推理**，正是 ③b 型自造证据。G2 给出一剑封喉的判据：**任何被断言为"真值"的码点，先在真实文件里 `chr(cp)` 反查出现次数；出现 0 次的"真值"不是真值，是自造值。** 本稿据此定下一条取证纪律：**凡形近最小对立对，任何码点主张必须先过"回盘字节 + 官方名反查"方可写入正文。** 本稿正文出现的码点（U+BB58 及其被证伪的形近候选 U+BB90/U+BACC）均已通过该项取证（见附录 A）；未过取证的形近候选值一律不采信——连本文自己也不例外。

### 5.3 判例小结

| 判例 | 造假主体 | 假绿形态 | 错误动作 | 收口实测推翻 |
|---|---|---|---|---|
| H1 | 两条验证路 + 仲裁路 | ③a 误删真数据 | "删除 1803→780" | 全库 `os.walk`：事故一原始会话实有 1803→780，与事故二的 925/1009 是两起独立事故 |
| H3 | 一条验证路 + 仲裁路 | ③b 自造真值 | 用 U+BB90/U+BACC"订正"记录 | `unicodedata.name`+`os.walk`：文件真用 U+BB58（59 次），两个"真值"均 0 次 |

两起判例里，被推翻的都是**来自审核层、带证据链、指向不可逆动作**的结论——这印证了"审核层同样是无信度的 LLM 代理"：加再多审核层，只要采信方式仍是"信其报告"，假绿就仍在生产。

## 6 讨论（Discussion）

**6.1 "用 AI 审 AI"的可信度主张该改怎么写。** 常见叙事是"多设几层 AI 审核 → 结论更可信"。本文判例给出的相反图景是：**每加一层 AI 审核，若不改变"信其自报"的采信方式，只是把造假绿的生产者从产码层换到了审核层**，而后者因自带证据链、动作指向删改，反而更难防。可信度的真正来源不是"审核层数"，而是**链尾那个"只信磁盘字节、不信任何自报"的收口点**。加审核层是**扩大召回**（能逮出错报），收口点是**保证精度**（保证采纳的都是现场坐实的）。二者不可互相替代。

**6.2 审核层应被"降级为线索生产者"。** 由此推出的组织级设计：验证/仲裁子代理的产物，其正确定位是"待收口复验的**线索**"，而非"可执行的**结论**"。本流程各验证路其实已一致声明局限——"回证只核到『索引↔台账』两级，多数未下钻原始会话，『属实』不等于底层事实已被独立复现"（收口复核记录 §0.1 与各验证路声明）。本文的贡献是把这句话推到逻辑终点：**既然验证层没下钻磁盘，它的"证伪"就必须被一个下钻了磁盘的收口层再证一次。** 否则，验证层的"未下钻"就成了假绿的藏身处——H1 的仲裁路正是因为只 grep 了一个具名文件、未做全库遍历，才把真数据误判为杜撰。

**6.3 与 noisy-oracle 视角的接合。** 把每个审核代理视为一个有噪声的预言机，是合理的建模。本文补充的是两点工程约束：其一，噪声**有偏**——审核层倾向于"相信公式/记忆胜过相信现场字节"（H3 两路都算而不查），故须用 G2 这类"强制回现场"的规程纠偏，而非指望它自我纠正；其二，对不可逆动作（删除、改写）须设**不对称门禁**——"证伪/删除"类结论的回验门槛应显著高于"通过/采纳"类，因为删错的代价无法靠"下一轮再看"挽回。G5 的射程约束正是此意。

**6.4 局限（务必知悉）。** (a) **单一流程、非受控**：两起判例来自同一条研究链，属日常复盘，不代表错误率，不可统计外推。(b) **判例出处以中性留档标签标注**：原始会话与验证/仲裁/收口各层的具体身份已按红线匿名化，复算通道为仓内只读留档（附录 C），不依赖点名撑可信度。(c) **收口者亦是人+代理**：本文只主张"回磁盘字节的收口层"比审核层更可信，并未主张它绝对无错——它只是**当前链路上取证最到底的一层**；若原始会话摘要本身已失真，本方法仍无从发现（这是所有"回现场"方法的公共下界）。(d) **部分数字为留档自报**：375 段对话、650 条候选的 S/A 计数、以及变异自证 7/7 等为流程台账自报值（在仓内留档可查，但未在本稿独立复跑），标 ⚠️ 的外部文献编号/数字未回原文核对（附录 A）。

---

## 7 结论（Conclusion）

多代理质量系统里，"自报不可信"已被公认；本文用一次真实研究流程的收口复盘，给出可回查的日常纵向判例，论证一个更隐蔽的失效：**被委托去核实自报的验证层与仲裁层，自身同样会造假绿**——它们会误删真数据（H1）、会自造真值（H3），且都带着"已核实/已订正"的外衣。本文的解法不是"再加一层 AI 审核"，而是**一个不信任何层自报、只回磁盘字节的独立实测门禁**（G1 字节回验 + G2 官方名反查 + G3 变异自证 + G4 负对照 + G5 取证范围约束）。一句话主张：**把不信任的边界从"执行代理"推进到"审核代理"，让链尾站着一个只认现场、不认报告的收口者。**

## 附录 B · 磁盘取证复现思路（不含内部编号与绝对路径）

> 下列脚本在本研究流程中真实用于收口亲验；此处只按**职责**命名，描述输入形态、核心动作、判据，供同行在自有仓库复现。

**B1 全库码点取证（治 ③b：H3）——全库码点取证脚本思路。**
- 输入：原始会话摘要根目录（`os.walk` 递归全部 `.md`）。
- 动作：对一组**候选码点**（含被各审核路"算出"的怀疑值）逐个 `chr(cp)`，在每份文件里 `str.find` 定位所有出现，收集（相对路径, ±40 字上下文）；同时用 `unicodedata.name(chr(cp))` 打印官方名（`ValueError` 记为 `?`）。
- 判据：**真值 = 现场出现次数 > 0 且官方名与语义相符的那个码点**；出现 0 次的"真值"即被证伪为自造。

**B2 规范名/NFC 反查（G2 落地）——规范名/NFC 反查脚本思路。**
- 动作：对目标码点做 `unicodedata.normalize("NFD", ch)` 拆成 jamo 逐段打印官方名；再用 `unicodedata.lookup("HANGUL JUNGSEONG ...")` 取音段、`normalize("NFC", 初+中+终)` 反组合，比较"公式合成值"与"文件字节值"是否一致。
- 判据：合成公式与官方名反查**必须一致**且与磁盘字节一致，方可下结论；不一致即暴露"手敲/凭记忆/凭公式"错值。

**B3 硬伤批量回磁盘取证（治 ③a：H1 等）——硬伤批量回磁盘取证脚本思路。**
- 输入：同一原始会话摘要根目录；一组探针串（如 `"1803" "→780" "925" "1009"`）。
- 动作：先把**全部**原始会话摘要读入内存 `blobs`；对每个探针串用 `re.finditer(re.escape(k), t)` **跨全库**计数并采样前若干条上下文回显（±55 字）。
- 判据（对应 G1+G3+G5）：① 先拿一个已知存在的串自证检索命中数 > 0（变异自证）；② 再对目标串下"0 命中/存在"结论；③ 取证范围必须覆盖全库，单文件 0 命中**不得**升级为"全库无出处、系杜撰"。H1 的审核路正是缺了第③步而误判。
