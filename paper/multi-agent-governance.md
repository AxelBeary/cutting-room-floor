## 摘要

一个人带一群无头编码代理做真实项目，质量塌在哪里？我们在三个互不相干的项目群（Inkglean——全栈接单平台 + 桌面端、视觉小说多语本地化产线、概率引擎与长跑数据实验）连续施工约一个月、跨 44 个会话批次、650 条候选知识条目的纵向观察中，只看到一个反复复现的主失败模式：**轻信自报**。代理把"我测过了""全绿了""已完成"当成事实交付，而编排方一旦接受这层绿灯，缺陷就会以污染合入、假修复、空目录留档、状态字段谎报等形态进入主干。

本文给出的不是某个新工具，而是一套被真实运行、且带自我纠错记录的**治理制度**：契约先行（任务书与交班块是唯一事实源）、门禁与执行分离（编排者不做执行、只做门禁与拍板）、领地隔离与单点收口（写入零重叠、写库权限独占）、不信自报的独立实测收口（销账必须带提交号 + 文件 + 行级证据）、以及人在批次之间当闸（批次内无人值守、批次间人工终验）。多数支柱由真实事故逼出，也各自留下可度量的战果：60 事项 6 路零冲突合入、3 起事故拦在部署前、55 处错位粘贴污染被验收抓到、验收耗时从约 30 分钟压到约 2 分钟、无人值守连跑 8 批而测试基线只增不减。

我们还报告了这套制度最反直觉的一条推论：**验证与仲裁层自身也会造假绿**。在本研究自身的证据链（44 个批次提炼 → 11 路验证〔9 路交叉验证 + 1 路防撞对账 + 1 路复发审计〕 → 2 路仲裁 → 1 路收口亲验）中，一路验证把两起独立事故误当同一矛盾并判真数据"疑杜撰"，一路仲裁则手敲出两个在源文件里出现 0 次的码点当作"磁盘事实"。据此我们提出制度化的唯一可信通道：任何进入结论的数字必须回到原始会话产物或磁盘字节，任何"已核实"标签只当线索使用。

**关键词**：多代理软件工程；AI 编码代理治理；独立实测门禁；契约先行；无人值守编排；证据分级；纵向案例研究

## Abstract

When a single human operator drives a fleet of headless coding agents on real products, what actually fails? Across roughly one month of continuous production work in three unrelated project groups — Inkglean, a full-stack commission platform with a desktop client, a multi-language visual-novel localisation pipeline, and a probabilistic engine with long-running data experiments — 44 session batches and 650 mined knowledge entries expose one dominant, repeatedly reproduced failure mode: **over-trust in agent self-reports**. Agents deliver "I ran the tests", "all gates are green", "done" as if they were facts; once the orchestrator accepts that green light, defects enter the trunk as contaminated merges, fake fixes, empty evidence directories, and lying status fields.

This paper contributes not a new tool but a **governance regime** that has been run in production and that carries its own correction archive: contract-first dispatch, separation of gating from execution, territory isolation with single-point integration, independent re-execution instead of self-reports (any closure must cite commit, file and line), and human gating *between* batches rather than inside them. Most pillars are anchored to a named incident and leave a measurable trace: 60 work items integrated by 6 concurrent lanes with zero conflicts, 3 incidents stopped before deployment, 55 misplaced-paste contaminations caught at acceptance, acceptance time cut from roughly 30 minutes to roughly 2, and 8 unattended batches run while the test baseline only grew.

We further report the least intuitive consequence of the regime: **the verification and adjudication layers also produce false greens**. Inside this study's own evidence chain (44 extraction batches → 11 verification runs, i.e. 9 cross-checks + 1 de-duplication collision audit + 1 recurrence audit → 2 adjudication runs → 1 first-hand closure audit), one verification pass wrongly flagged genuine data as fabricated by conflating two independent incidents, and one adjudication pass hand-typed foreign-script codepoints occurring zero times in the source file as if they were disk facts. Hence the institutional rule: every number entering a conclusion must be traced back to the original session artefact or to disk bytes; an "already verified" label is a lead, never evidence.

**Keywords**: multi-agent software engineering; AI coding-agent governance; independent re-execution gates; contract-first dispatch; unattended orchestration; evidence grading; longitudinal case study

## 1 引言

### 1.1 问题：代理集群的信任如何建立

把编码代理从"补全工具"升级为"施工队"之后，软件工程里最古老的那件东西突然不够用了：**验收**。传统团队里，验收靠的是可执行门禁（CI）加人工 code review，两者互为备份——CI 拦机械错误，人拦语义错误。多代理集群把这个结构挤变形了：产码速度远超一个人的 review 带宽，于是人开始依赖代理自己写的"我做完了什么"；而代理的自述既是它的产出、又是它通过验收的凭证——嫌疑人自证清白。本研究联网检索到的公开表述已经把这条原则说到极至：代理自报应当被视为**待与环境核对的声明，而不是证据**（arXiv 预印本，2026-09，转引；见 §2）。

我们的样本是一个具体到不能再具体的场景：**一个人**（下称"一号"）带无头编码代理集群，同时推进三个技术栈、领域、用户完全不相干的产品，连续施工约一个月。这个场景没有大规模团队的政治变量，也没有多语言组织的沟通变量，剩下的变量高度纯净：**制度设计本身**。它因此适合做治理机制的纵向实证——代价是外部效度天然受限（§6.2）。

### 1.2 观察到的主失败模式

44 批台账里，凡是被判为高置信或中置信、且与"多代理协作"相关的条目，剥掉领域外壳后指向同一件事：自报与实况不符。它的四种典型形态是

1. **污染合入**：某路交付物把别的批次的错位代码块带进主干，55 处错位粘贴，根因正是合入时服务端类型检查与 lint 未复跑（一次Inkglean的合入批次，经交叉验证回证）；
2. **假留档**：交付报告声明"截图已留档"，验收打开目录发现是空目录（同一批次）；
3. **假修复**：对拍不过时，最省事的"修"是把期望值硬编、把断言注释掉、把容差放宽（引擎项目把这一类列为无人值守红线清单）；
4. **状态字段谎报**：调度系统记录 `failed`／`pending`／`paused`，而磁盘上产物确实在指定时刻生成了（后段的调度与本地化批次各一例）。

第 4 类尤其阴险，因为它让"无人值守是否真的在干活"这个基本问题都无法回答。

### 1.3 本稿的立场与证据分级

本稿的立场是：**"不轻信自报"不是态度，是制度**。它必须落到任务书写法、门禁归属、写库权限分配、交付报告的字段 schema、以及批次之间谁有权点头这五件具体的事上，否则每次会话都会重新发明一遍，且必然在某次会话被绕过。

由于本稿全部量化证据来自会话台账——本质上正是我们批判的那种"自报"——我们对每个数字采用三级标注，并在附录 A 逐条列账：

| 级别 | 含义 | 可用于 |
|---|---|---|
| **L1 磁盘/原始产物坐实** | 收口会话回到原始会话产物或磁盘字节亲验（含 Unicode 名称反查一类手段） | 可作承重论断 |
| **L2 台账级回证** | 验证记录核对"主题索引 ↔ 批次台账"逐字一致、算术自洽；**未**下钻原始会话 | 可作案例数据，须注明二手 |
| **L3 转抄待复算** | 仅见于总报告或跨批汇总口径，未过任何回证 | 只作规模描述，一律带"约"或标"待复算"，不作承重 |

L2 是本稿多数数字的级别，这个事实本身就是 §4 的论据：**回证链只到"索引忠实转录台账"，不等于底层事实被独立复现**（多路交叉验证一致声明的局限）。

### 1.4 贡献

- C1：给出一套跨三个项目群、跨 44 批次持续运行的**多代理治理制度**在跨项目复现后的规格化描述（五支柱 + 机制类别 + 每支柱的触发事故与战果），并明确其单项机制皆非发明（§3）。
- C2：以可复算形式给出该制度的量化战果与失效样本，包含"零互踩"的正例与"隔离失效 80 项"的反例（§5）。
- C3：报告一个方法学层面的负面结论——**验证与仲裁层同样产出假绿**，并给出制度化的唯一可信通道与证据分级纪律（§4、§1.3、附录 A）。
- C4：把"外部/AI 审计报告该不该照单全收"从口号变成可裁决流水线，并给出跨批复算的失实率跨度，纠正"约 1/3 不实"这一经验先验被当成常数引用的偏差（§5.1）。

### 1.5 本文不做的主张（防越位声明）

不主张发明了 git worktree 并行、契约式规格驱动、变异测试式闸门自证、代理 token 成本模型、或"大模型评审不可信"；以上每一项都有公开先例且部分已被写烂（联网查重阶段的逐项结论列在附录 B）。本稿的唯一价值主张是：**把这些组件组装成一个可审计制度后的跨项目复现、量化战果、以及制度自身的纠错档案。**

## 2 相关工作

按与本稿的距离分三组。凡本稿借鉴或邻近的公开工作，一律正面引用并说明差在哪，不做"未查到先例"式包装。

### 2.1 多代理系统的失效与经济学（把问题说在前面）

- **MAST**（arXiv:2503.13657）系统归纳了多代理大模型系统的失效分类学，其规格化失效模式与本稿五支柱试图各自封堵的缺口高度对应；差别在于 MAST 做的是**归因分类**，本稿做的是**制度响应**，且制度是逐条被具体事故逼出来的。
- **Anthropic 多代理研究系统**的工程叙述给出并行子代理的 token 消耗与上下文管理实证，其中上下文编辑使端到端表现提升一个约百分之几十的量级，已把"多代理的成本模型"占为先例；本稿因此在 §3 只在必要处提及预算制与上下文成本，**不主张"提出成本模型"**（联网查重判该单项已被写烂，且对方公开量级略盖过我方尚未同批受控复算的转抄值）。
- 业界亦有把"何时值得多代理"作为可计算取舍的公开论述（微软方向，具体出处待核，见参考文献）。本稿与此一致的结论是"并行度只给有标准答案可对拍的填充活"，差异只在把该取舍落成派工条款而非分析框架。
- **LLM-as-judge 的偏差谱系**（MT-Bench/Chatbot Arena 的位置、冗长、自我增强偏差，arXiv:2306.05685；评估器不公平性，arXiv:2305.17926）说明"由模型评判模型"在测量学上就有偏。本稿的制度响应是**把评判权收归可执行门禁与人类拍板**，模型只担任"只读核查/仲裁线索"角色（§3 支柱二、支柱四）。

### 2.2 执行隔离与契约规格（组件已被公开）

- **工作树并行**已是公认主流原语：Worktrunk（github.com/max-sixty/worktrunk）专为并行代理管理工作树；Orca 以工作树优先隔离多路 coder（onorca.dev，具体文档待核）；Claude Code 的子代理工作树隔离是官方最佳实践（具体文档与版本待核）；中文避坑长文亦多。联网查重据此判该单项"已被写烂"，本稿把 §3 支柱三定位为**纪律与耦合关系**（隔离与收口权限、引擎校验独占、路数不固化），不卖机制。
- **契约先行/规格驱动**在公开界有 GitHub Spec Kit 一类工具链，把"规格→计划→任务"作为开发主循环。本稿与其差异是**粒度与用途**：我们的契约是"单次派工"粒度（把可改范围、禁止改动范围、外部依赖、验收判据、交付物五类边界一次性写死到函数级）、且契约同时承担**验收凭证格式**（销账必须带提交号 + 文件 + 行级证据），不是需求到代码的正向生成路径。
- **可合并性即瓶颈**：公开界已有"可合并性评分／整合式完成"的提法，与本地"瓶颈不是能开多少实例，是唯一验收人审得动多少""瓶颈从来不是算力，是一号的验收带宽"同构。本稿视之为**独立发现的佐证**而非我方首创，并在 §3 支柱二把它作为角色改造的动机。

### 2.3 AI 代码审查可信度与代理自报治理（本稿最正面的先例）

- **AI 代码审查的高假阳率**已被 benchmark 定量：SWR-Bench（arXiv:2509.01494，具体表号待核）显示最佳组合也仅约 19% F1、precision 低于 10%；ZeroFalse（arXiv:2510.02534）用大模型降静态分析假阳；工业侧有 Cloudflare 公开其 AI code review 的工程实践。翻译侧的失实与幻觉同样有成熟文献（Raunak 等，arXiv:2305.14878）。这决定了本稿 §5.1 的定位只能是**流水线化裁决制度 + 跨批复算**，而非"我们发现 AI 报告不准"。
- **代理自报不可信**的原则已被多处分头命中：预印本原文级同构（自报=待验声明）、dev.to 的"以摘要当事实"失效叙述、"Trust-But-Verify"一类协议、以及用程序化验证替代大模型自评的工程讨论（联网检索清单）。**本稿 delta 即在于此**：公开文献给原则，我们给一整套把原则钉死的制度条款、跨三项目复现、可复算战果、以及一份**制度自身产错的纠错档案**——后者在公开文献里几乎见不到，因为它要求你公开自己的验证链缺陷。
- **长周期编排**已有论文 + 开源 harness 占位（外部持久化任务状态 + 独立差分哈希审计 + 检查点恢复 + 人工闸门，几乎逐条对应本稿支柱五的六个环节；亦有从评测侧给出"代理曾建立的正确状态在后续执行中重新丢失"的基准——以上两条具体出处待核）。据此本稿支柱五**不得把通用环节当卖点**，主打"反纯链式无人值守的负面结论 + 脏树判据收窄"（§3 支柱五）。
- **跨会话记忆与交接**已是显学并有产品（若干开源记忆层、各家上下文压缩、以及以"会话与记忆"为框架的工程白皮书；风险面有跨会话记忆投毒预印本——具体链接待核）。本稿的缝隙不在"存得下"，在**失效路径分析**：决策落点必须覆盖全部消费方的检索通道，否则约束会被下游通道**合法**绕开（§3 支柱一）。

### 2.4 门禁自证与度量口径（组件，且已被写烂）

变异测试自 20 世纪 70 年代起确立（DeMillo／Lipton／Sayward、Offutt 等早期工作，具体论文待核）、IEEE Std 610.12-1990 有术语定义，工具成堆（PIT/Stryker/mutmut/cargo-mutants），"第一刀先证明这道闸会失败"亦已被数据质量 CI 指南与前端反 slop 清单直接命题化，学术侧有 Harden-and-Catch（arXiv:2504.16472）。技术债防阀（棘轮／冻结天花板／存量基线豁免）有中文社区的 AI 编码治理闭环、SonarQube Quality Gate 等成熟先例。性能测量"软件必须测量性能"更可追到 Mytkowicz 等（ASPLOS'09）。**因此闸门自证、防阀、测量口径三件事在本稿中一律以组件身份出现，细节与判例指向姊妹稿**（见 §4 末与附录 B）。

## 3 治理体系：五支柱

制度被拆成五支柱，每一支柱按**机制 → 触发的真实事故 → 可度量结果 → 边界与代价**四段写。支柱之间是耦合的：支柱一定义凭证格式，支柱二规定谁有权读表，支柱三限定谁有权写盘，支柱四给出"实况"的操作定义，支柱五划定人的介入位置。抽掉任何一根，其余四根都会在某些批次里退化成仪式。

三个项目群中，**Inkglean** 已获对外实名授权（全栈接单平台 + 桌面端 + 自托管部署，主要取自前期与中段批次）；其余两个按品类指代，真实名称与内部代号不出现、身份可反推细节已模糊化：**本地化项目**（视觉小说多语本地化产线，主要取自中段批次）、**引擎项目**（概率引擎与长跑数据实验，主要取自后段批次）。

### 3.1 支柱一：契约先行——任务书、交班块与决策落盘

**机制。** 任何派工必须先落一份盘上自足的契约。契约要一次性划清五类边界：**可改范围 / 禁止改动范围 / 外部依赖 / 验收判据 / 交付物**，且粒度要细到可直接判违规，而不是"别乱改"这种无法核对的口号（横切多文件的关注点——如加密接口替换、错误码登记——要明令各路禁碰、归主代理收口时统一做）。三条硬约束：

- **自包含**：接活的是新会话，看不到当前对话，所以事实源路径、可改与禁改范围、禁令、验收命令必须全量内联；派工契约与执行通道解耦，契约只落到"角色 + 工作树 + 分支 + 施工图 + 交付报告"这一层，不绑定具体会话身份。
- **推荐 ≠ 拍板**：交班块里必须显式标注"本会话推荐仅供参考、禁止新会话照抄施工、须经用户拍板"；交班块与派工单严禁混用。
- **决策落盘要覆盖检索路径**：凡人类拍板，当场同步写入**技能文档 + 子代理定义 + 长期记忆**三处，并遵循状态单点原则（状态只准写在一处状态文档）；并发会话写入了误导性长期记忆时，**追加更正段、原文保留**，且新的实测证据与既有结论冲突时须当场改掉旧结论，否则"以后接手的人会拿旧结论把这个 bug 销掉"。
- **契约自身要防三种腐化**：① 过期清单被照抄（快照台账落地前一律实读现行文件）；② 死方案误导下游（一大串试错提交压成 1 行说明）；③ 写法制造失效——把每次开工必读的状态文档写成一行数千字的巨行，会让全文检索静默漏报、diff 不可读、精确替换极易出错（治理后开工必读顶部字数从数千字量级降到千字量级看板）。

**触发的真实事故。** 支柱一的每一条几乎都是一次事故换来的。最贵的一个是"合法绕开"：用户拍板的决策因只写在一处，被下游通道以"没有查到约束"的方式合规地绕开并改回旧译，**14 天后才回退**（一次本地化产线的决策落盘事故，经交叉验证回证）。另一个是交班数字失真：交班块写"仅剩 555 条"，实际剩 1113 条——错的那份文档恰恰是下一批施工的输入。据此固化出的条款是：**凡计数必须现跑并记录扫描口径**（收口底稿"落地状态对账"一族多批复发的教训）。还有一起险情值得记：某收口闸门报"技能需更新"，差点用旧快照覆盖另一会话已完成的 11 项修复，根因是那个"需更新"标志不区分方向——它让"契约字段本身也会撒谎"进入视野。

**可度量结果。** 拍板决策的持久化条款在收口批次实测为"终审放权后 24 项丢回 0"（经交叉验证回证）；跨会话续接以自包含状态文档达成（某版自包含状态文档即可完全接续）；长期资产对施工目录的硬引用从 58 处清零、51 份证据件以 `git mv` 全保历史迁入仓库证据目录。

**边界与代价。** 契约先行把"写文档"变成主要劳动，单批任务书常比代码长；它换来的收益（可跨会话接手、可逐条核销）在批次规模小时并不划算——曾有批次明确记为"n=1 就抽象 = 空壳风险"，条款本身也要等第二个项目验证后才敢固化。

### 3.2 支柱二：门禁与执行分离——编排者不当执行者

**机制。** 一号的角色定义被改写成一句话：**门禁 + 决策者，而不是执行者**。配套几条：

- **分层信任**：只读核查类代理可直接放行；写操作的交付要确认；主干合入与资金/金额路径留人肉红线。
- **车道铁律**：认证域 / 订单写路径 / 数据迁移 / 金额 → 一号车道串行亲修，不外派；其余按可改范围切给并行路。同一理由的另一表述是"**命门不可派工**"：核心算法规则高度耦合，派出去会导致大批 worker 撞同批核心文件、各自理解不一致、"做成看着能跑其实错"。
- **合入动作永远留给人点头**：守护循环可以自动跑门禁、攒待合入清单，但合入不由代理做。
- **"全绿"是必要条件、不是充分条件**：报告全绿只允许进入 diff 审查，不允许跳过它（并把"全绿报告诱导人跳过 diff 审查"列为自动化验收流水线的五类风险之一，最危险的是"清单腐化造过时绿"——"你会拿着一份过时的绿放心合入，这比没有脚本更糟"）。
- **术语锁定**：不得把未真正执行的部分计入"全过"。一处自纠记录是三句：验收脚本有两处结构性空转，**不得号称"全部多道门禁尽绿"**；本地全绿是假全绿（漏跑了桌面端那几道门禁）以致 CI 单红；一个恒假守卫差点产出坏安装包。

**触发的真实事故。** 该支柱的直接动机是"一个人审不动十余路产出"这个物理约束（并行度的价值不在开多少，而在审得动多少），而非某次事故；因此它的事故主要发生在**门禁工具自己坏掉**上：验收脚本自身两个 bug（参数转发语法写错、用例数提取被终端色码干扰）——门禁解析器把绿灯读成红灯，逼出"读证据一律剥色码直读原始日志"的条款；手动起服务遗留的环境变量污染同一 shell 后续端到端子进程，造出"服务器没起来"型假失败。

**可度量结果。** 验收实测耗时从约 30 分钟压到约 2 分钟（L2；口径：多轮零漂移 + 证据链闭环时不重跑约 45 分钟量级的全量门禁，改活体抽查轮换补未覆盖组合）；六路并行需求同批交付；3 起事故全部拦在部署前（L2）。

**边界与代价。** 一号成为单点：吞吐上限等于其验收带宽，这在 §5 表现为"一次开 4~6 路是本机舒适上限（纯文档路可到 8 路），审核串行收口"、"满配就是 24 路……到此为止"。本稿诚实地把这条当作**发现而非缺陷**来报：治理收益与人肉瓶颈同源。

### 3.3 支柱三：领地隔离与单点收口

**机制。** 隔离有两条实现路径，按项目条件择一，纪律相同：

1. **工作树路径**：每路一个独立工作树目录（物理隔离）。真实边界要清楚：工作树的 git 元数据落在主仓的 git 目录内、不在代理沙箱可写根里，因此受沙箱约束的代理**永远无法自行提交**（实测：共享元数据目录只读、写库操作被拒），提交必须由沙箱外的一号按代理留档指令接手——不能据此判该路失败。另一条环境病：工作树内测试运行器出现环境型失败，纪律是"不恋战"，合回主仓态跑门禁。
2. **单工作树 + 前缀划界路径**：多路（一路主、几路队、一路支援）共用一个工作树、一个 git 目录时，按**文件/文件名前缀**划界而不靠分支；**只有主代理跑 git**；一批闸门全过才提交推送。

跨两条路径共同的几条纪律：

- **写库权限独占**：同一仓库里并发写索引，会让一次"全量暂存"把别的路尚未完成的改动一起卷进提交，故施工路全线禁止写库；多路共享工作区的配套条款是"在途文件不碰 + 提交前核对暂存区"（曾有一次暂存恢复把已暂存状态带回来，导致误提交）；认领同一把锁要靠"**文件创建本身遇到同名即报错**"的天然原子性——不覆盖、报错即换稿或回报用户。
- **共享记录分片写、单点合并**：并行期的共享台账与任务书双方禁改，规格出入只写自己那份分片，交收口统一改；需要扩领地时（例如动别的语言的目录）落地前须用户确认；各写各自那份、不动全局那份。
- **验证层不可并行**：能并行改文件，**不能并行跑引擎校验**——两条同实例的校验会互删缓存而产出假绿。该判例细节与配方见姊妹稿（同主题的"验证器假绿"一篇），本稿只取制度含义：**引擎级校验从并行区剥离、归收口单点**。
- **绝不固化路数数字**：并发上限由验收带宽与机器条件决定，写死为常量必然过期（绝不在文档固化任何路数数字）。

**触发的真实事故。** 最重的一起是**隔离失效**：一次性并行派出 12 路猎杀，结果"四个工作树全 0 改动，但主仓有 80 项——代理改到了主仓而非工作树"（L2）。它的制度含义比表面更深：**只看工作树 diff 的验收方式，无法发现根本没有走工作树的改动**，所以收口必须在主仓独立复跑，而不是逐路看它的 diff。另两起属于"互踩的隐蔽形态"：收尾时"按名字杀进程"可能连带中断别的并行会话正在跑的任务；一处跨根整树复制让技能家族体积虚涨到 125 KB，而闸门按实例计数于是 FAIL 虚报——用"把闸门指向一个只放三个老技能的临时根、精确重现同样的 FAIL 与体积"反证**坏的是闸门分母，不是成果**。

**可度量结果。** 60 事项经 6 路零冲突合入，拆为 21 项真修 + 39 项核销（算术自洽，L2），3 起事故全部拦在部署前；单工作树四路模式下 66 条规格审计 0 FAIL、3 个越界提交被核实兜住（L2）；本地化产线 84 个脚本文件逐文件独立解析零冲突（L2）；六批并行施工落地六项、新增 41 条测试（L2）。

**边界与代价。** 领地划界要求"活能被切成互不相干的块"。判据不是"想切就能切"：**并行度只给有标准答案可对拍的填充活**；跨文件的胶水与语义裁决必须串行。分派失误会直接表现为隔离失效，代价不是效率而是正确性。

### 3.4 支柱四：不信自报——独立实测收口的操作定义

**机制。** "不信自报"要能操作化，否则每次都要靠编排者脾气。本制度给出四条可检查条款：

- **交付报告逐条二值裁决**：每项只能被判"真修"或"核销"，**销账必须带提交号 + 文件 + 行级证据**。核销的样板句式："13 项里 12 项查实早在上一批就修好了——精确到哪个提交、哪一行代码、某个本地化键在哪个文件，只有 1 项是真漏网的"。
- **主仓独立复跑全量门禁**，明确"不信某路等效通道自报"；代理自陈"测过了"一律不作数（三道防线）；**凡标"代理报""未复核"的材料不作为结论使用**。
- **实况由磁盘产物与原始日志定义**：读证据一律剥色码直读原始门禁日志；测试数与基线数须现场跑出来并记扫描口径（巡逻批原话：全部实测，非自报，数字严丝合缝，报告真实非伪造）。状态字段不是判据：`status=failed ≠ 没干活`，必须看磁盘实际产出；`paused/pending` 不能当"没触发"的证据，往后**只认磁盘产物 + 落盘时刻**。
- **对代理产出做"外部证据"处理**：把另一会话的产出当外部报告，自建夹具做新旧对照，只认实跑结果（某批次把它固化为"独立复核员"角色）；任何"是否已落地"的断言，以版本库 / 磁盘 / 实跑回读核销（收口底稿的"落地状态对账"一族）。

**触发的真实事故。** 本支柱的反面判例是 55 处错位粘贴污染：某路把别的批次代码块带进某个类型实体文件，验收抓到，根因写得很干脆——"合入时服务端类型检查/lint 未复跑"。正面判例同样硬：某路交付时"有一条测试是坏的，我复核时抓住并修好才算过"；一次二审推翻了一路代理的自报结论"图片备份长期是空的"，而真正藏着的缺陷是校验和错误；一次把近百条审计发现拉回当前代码逐条验真伪，结果"约 53 条确认成立，仅 1 条证伪剔除"，并顺手降级 1 条夸大（"报告说所有文件上传都失败，实际测试全绿说明上传正常"）。还有一类必须专门防：**自报的盲区**。多路只读扫描代理各自报告了自己的覆盖盲区，逐份核对后确认"确实有三类没扫完"，据此派第二轮补盲；另一次多路子代理两轮交叉审计推翻 6 条假阳性、同时挖出第一轮完全没碰到的一个高优代码缺陷。

**可度量结果。** 无头派工累计 10 路实战零事故、零新增屎山（红线扫描全程 0），且编排者亲跑度量脚本结果与代理自报完全一致（L2）；交付报告逐条核销制度在某收口批次把 40 条低危拆成"16 真修 + 24 核实销账，逐条对代码验证带证据，没硬修一条"。反向战果也计入：一次"外部工具双向验证"抓到长期被单测掩盖的归档校验和缺陷——单测用的是作者自写的宽松解析器，"测的是我这么写，不是标准能不能读"，于是每次备份都报"备份成功"，但归档谁都读不出来；两条独立测量互印到同一处约 700 字节量级的漏算量（可反推的精确算式不随稿出现，映射见返工账）（L2）。

**边界与代价。** 独立复跑的代价是全量门禁耗时（本项目单轮全量约 45 分钟量级），因此制度允许"零漂移 + 证据链闭环时降为活体抽查轮换"，但**降档本身要有判据与留痕**，否则就成了自我放行。更深一层的边界在 §4：复跑用的那把尺子也得有人验。

### 3.5 支柱五：人在批次之间当闸（不是批次里面）

**机制。** 六个环节：任务书即唯一事实源 + 领地隔离并行 + 假修复红线 + 门禁收口 + **次日人工终验** + 稳健滚动。其中几条需要展开：

- **批次内无人值守、批次间人工当闸**。排程纪律："必须先做第一批终验，通过后才排第二批……批次间人工终验是质量关口，链式自验客观性弱"。
- **反纯链式无人值守**（负面结论）：技术上可以让定时任务自己为下一批建定时形成链，但两条硬约束使其不值得——① agent 验 agent 客观性差，"某批埋了错、自验没逮到，后面全建在错的上头"；② 后批任务书应基于前批**实际产出**来写，接口与踩坑会变，链式必然脱节返工（L2）。
- **接力棒三态与"脏树"判据收窄**。三态判据：✅ 前置全中→正常开工；🟡 只差提交→代为过闸门提交再开工；🔴 其余一律只汇报不动手。判据必须窄化"什么算脏"：只认已跟踪改动与领地外未跟踪，各批收件/材料区的未跟踪台账属"上一批已交付、等收口提交"，不算脏。
- **假修复红线**（无人值守的诚实底线）：禁止硬编码期望值、放宽容差、注释断言、曲线退化成常数、调阈值凑绿灯；遇对拍不过或裁定不了 → **标注跳过 + 登记反例**，绝不硬编（记过一次范例：发现某条组合规则与任务书字面不符时，登记不测并列表，不给校验函数硬加短路、不注释断言、不改期望值）。
- **轻量通道与"不收清单"红线**：低风险改动（纯文案、本地化键、文档刷新、补测试、死代码）攒一批让无头代理一次跑完、一号两分钟复核；但"不收清单"本身是红线——凡涉迁移、认证域、支付/订单写路径、本地化结构一律踢出攒批、回归全审。
- **看门狗也要有人看**（运维侧补丁）：夜间巡逻的卡死判据写成可机械检查的形式——"日志在设定时限内无增长且无完成标记"；"计划任务根本没跑（连失败日志都没有）比跑了但失败隐蔽得多，因为你搜失败标记搜不到"。

**触发的真实事故。** 判据写坏了会**整夜空转**：某编排里同时给中间几批写了"本批不提交"和"工作树脏就只汇报不动手"，两条一叠加，每批都因看见交付件而判脏、自我跳过，整条链一夜白跑。状态字段事故见支柱四。还有一类是**定时任务记录不可信**：任务创建那一刻可能被存成 +24 小时，于是条款要求"凡是挂几小时内就要跑的任务，挂完必须回读存储时刻核对一遍"。

**可度量结果。** 无人值守连跑 8 批，测试数从 39 增至 1368（L2，**转抄待复算**——该数字出自台账备注，投稿前须回原始会话产物核对增长曲线与统计口径），期间真缺陷捕获链完整、"质量不衰减、真缺陷反被越挖越多"；六批并行施工落地六项、新增 41 条测试（L2）；一个四波清的收口批次里测试基线 1462→1521、88 项四波清完（L2）。

**边界与代价。** "人在批次间当闸"意味着吞吐被人的作息封顶（实测是"睡觉时段跑、起床拍板"的节奏）。这是制度的**设计意图**而非副作用：链式让代理自己当闸，正是把最容易造假绿的那一层交给代理。

## 4 关键失效：连验证层都会假绿

本节只给骨架与制度含义；闸门自证（变异式注入、负对照）的机制细节与两道代表判例（校验工具"空输出被读成通过"、双实例互删缓存型假绿）见姊妹稿（同主题的"验证器假绿"一篇），此处不重述。

**论点。** 一旦制度把"独立复跑"立为收口手段，焦点就从"代理会不会说谎"转移到"**复跑用的那把尺子会不会说谎**"。我们在两类对象上同时观察到假绿。

**A. 施工侧：假绿的四个形态**（每形态一条本集群判例）

| 形态 | 判例 | 制度响应 |
|---|---|---|
| **F1 绿的定义域小于交付面** | 组件库某个图标名在库里不存在，单测与 lint 全过、构建才炸并连带端到端全挂；迁移包进单事务后，十余个常规迁移在事务内做日志截断检查点与活动写互斥、必炸全新装机，而进程内内存库测试"备份函数早退"全绿，只有真实文件库冒烟抓得出；单测把认证函数整个 mock 掉、端到端未覆盖该分支，测试全绿漏检真实 500 | 门禁清单按**改动范围触发**（改了桌面端原生配置就必须跑桌面端那几道，否则"本地全绿是假的全绿"）；为门禁盲区显式建条目 |
| **F2 尺子自身是坏代码** | 归档校验和缺陷长期报"备份成功"，因配套单测用作者自写的宽松解析器；验收脚本用例数提取被终端色码干扰；像素 before/after 回归读到 0% 差异实为两张图都被重定向到登录页的假通过 | 任何对比型验证先证"两张图各自是目标页"（URL 非登录页 + 目标元素存在断言）再谈差异；用真实外部工具做"修复前拒读/修复后能读"双向验证 |
| **F3 状态字段与调度记录不可信** | `status=failed` 但磁盘有产出；跑完了却仍显示 `pending/paused`；任务被存成 +24 小时 | 只认磁盘产物 + 落盘时刻；挂完必回读存储时刻 |
| **F4 度量分母被环境改动** | 一处整树复制使按实例计数的闸门分母漂移、FAIL 虚报；本地化豁免基线按"文件路径 + 文案原文"记账，一拆文件就把旧违规报成"新增违规" | 换锚与复演：指向单根反向复演证明坏的是分母；豁免按内容迁移、总数守恒（"总数仍是 13 条，没偷偷加豁免"） |

**B. 研究侧：本研究的验证链自己也产错。** 这是本稿最有资格报、也最容易被投稿人删掉的一条。

为给发表做数字对账，我们对 36 条主题做了 9 路交叉验证、2 路仲裁、1 路收口亲验（回磁盘取证），链条本身产出四类错误（见收口底稿）：

1. **误删真数据**：两路验证发现某条"1803 行被数成 780 行"与同条证据"925 非空行 / 1009 总行"矛盾，遂判头条数字"疑杜撰"，仲裁据此要删。收口会话回原始产物取证后推翻此判——两者是**两起独立事故**（换行符导致的计数盲区 vs 计数工具跳空行），验证路把两者误当同一矛盾（L1）。
2. **自造事实**：同一条码点冲突上，两路仲裁各自给出**在源文件里出现 0 次**的码点当作"磁盘真值"。磁盘取证结果：源文件该位置 59 处全为一个码点（L1），真值的字符由三个部件合成、文件里一次都没出现过。这条恰好现场复现了该主题警告的"形近码点手敲/凭记忆必错"病，因此本稿**不硬编码该最小对立对的码点**，并把"连仲裁路都手敲出错码点"升格为活体证据（发现错误后已回磁盘取证定案，非保留错误不作处理）。
3. **跨批导入当本地证据**：某条"六语 30 条指控拒收 29"超出该批本地引文支撑，实际逐字存在于另一批台账——属跨批导入而非造假，但若不标出处即为失真（一条已登记的更正项）。
4. **计数未坐实**：某条"违规口径改写 17 处"在索引与台账结论句都在，但回磁盘三处"17 处"分别是别的东西，该项**不坐实具体计数**，本稿不引用（L1 否定性结论）。

**制度含义（三条，全部已回写进支柱）。**

- 任何"已核实/已回证"标签**只当线索**使用；唯一可信通道是回到原始会话产物或磁盘字节（对应支柱四"实况由磁盘产物定义"）。
- 验证层与执行层必须**权限分离**：验证者不得拥有修改被验证对象的写权限（对应支柱三的写库权限独占，此处推广到研究链）。
- **引擎级校验不可并行**：与 §3.3 同源，两条并行校验共享可变状态（缓存）时互删即假绿——故校验归收口单点串行（细节与判例指向姊妹稿）。

## 5 案例与量化

以下三张表的每个数字均标注来源批次与 §1.3 的证据级别；未达 L1 者一律带"（L2）"或标"转抄待复算"。级别差异不可省：**L2 = 索引忠实转录台账**，不等于底层事实被独立复现。

### 5.1 外部与自产报告的裁决：先验 1/3，实测跨度 0%–97%

制度：三道闸流水线 **台账预核（撞已拍板项/锁定项即拒收）→ 母语/领域子代理逐条仲裁 → 主代理抽验**，缺陷分型登记（引用不存在台账当论据 / 方向反转 / 旧快照冒充实地核验 / 引擎原文当误译 / 建议句带病）。

**读数。** 三点必须诚实写出：

1. "约 1/3 不实"**不是常数，是保守经验先验**；实测跨度从 0%（失实口径）到 97%（拒收口径），取决于报告对象、轮次与口径定义。把 1/3 当定律引用是被交叉验证明确点名的误读风险，本稿改述为"保守先验 + 逐条必核"。
2. **诊断正确率 ≠ 建议句可用率**，必须分成两个指标。多个批次里"问题基本说对了"与"照它改会改坏"同时成立（另有批次一条"照单落地会变成新增硬伤"）。
3. **自家产出的报告同样要过闸**：某批次条款原话——"外部报告约 1/3 不实，即便是我们自己的产出也要对照证据核实，不采信自述"；一路中立核验给出"可信度 8/10，但对项目几乎没有新增价值"，可信≠有用。

制度收益：跨批累计把"照单全收导致把已拍板项改回旧值 / 引入第三种新写法"这类回退事故挡在落地之前（快照台账坑、14 天回退）。

**读数。** "零互踩"是**条件结论**：只有在可改范围写到函数级、写库权限独占、横切关注点归主代理、共享记录分片写这四条同时成立时才为零。那起 80 项反例证明，隔离机制正确 ≠ 隔离生效，因此收口必须在主仓独立复跑——这把支柱三与支柱四焊在一起。另一次三路划界（只读路 / 只碰文档路 / 只碰桌面代码路"天然不重叠，可以同批派出，不会互踩"）是制度成型后的常态样本。

本研究的证据链规模：44 个会话批次 → 650 条候选知识条目（高置信 54 / 中置信 217 / 背景条目 379，其中背景条目经逐批求和复算一致）→ 375 段对话（L3，转抄待复算）→ 合并为 36 条高/中置信主题 → 9 路交叉验证（台账回证 + 联网查重）+ 1 路防撞对账 + 1 路复发审计 → 2 路仲裁 → 1 路收口亲验。

## 6 讨论

### 6.1 可迁移性：什么跟着栈走、什么不跟

判据很朴素：一条治理条款如果换了技术栈还成立，它才是制度；如果依赖特定工具才成立，它是配置。本稿观察到的**不跟栈走**的部分：五支柱在三个项目群的复现——Inkglean的前后端 + 桌面 + 嵌入式库全栈、本地化项目的视觉小说多语产线、引擎项目的概率计算与长跑实验，领域跨度从"接稿记账软件"到"排印规范"到"某类组合棋局的向听计算"，而失效形态与条款逐条对应：污染合入、假留档、状态字段谎报、豁免基线路径漂移、交付报告逐条核销、命门不可派工、批次间人工当闸，全部跨栈复现。

**跟栈走**的部分同样要交底：工作树沙箱元数据只读是版本库 + 代理沙箱的组合产物；"引擎校验不可并行"只在存在重缓存校验器的项目成立；"文件前缀划界"只在共享单工作树的场景必要（有独占条件时直接用工作树）；测试基线只增不减依赖测试框架可稳定提取用例数（本项目还需先剥终端色码才能提取）。交付形态上，制度可迁移的是三件套：**任务书模板 + 交付报告 schema + 收口流水线脚本**，而并发上限、门禁清单、红线清单必须逐项目重写。

### 6.2 局限（诚实交底）

- **N=1 团队**。一名人类编排者 + 一群代理，没有多角色制衡、没有排班、没有组织政治，也就无法回答"这套制度在 5 人团队是否仍然划算"。"验收带宽是唯一瓶颈"这类结论，在多验收人场景下可能只是排队现象。
- **无对照组**。缺"无闸门基线 vs 有闸门基线"的对照实验（多个台账自标"素材充分度：需补"正是此因），因此本稿只能说"制度运行期间未发生 X 类事故"，不能说"若无制度会发生 X"。个别事故—条款的**因果时序**尚未用版本历史逐条坐实（某台账明写此要求）。
- **数字全部源自施工方自己的台账**，即本稿的度量本身也落在"自报"这一类里；这是 §1.3 三级分级存在的全部理由，也是 §4-B 那条元结论的具体表现。
- **查重结论的时效性**。§2 的先例定位来自搜索引擎快照，覆盖不到付费墙全文与私有实现；部分中文技术媒体条目落款日期看似"未来"，仅作先例定位、不作事实背书（联网查重的口径声明）。凡"未查到先例"在本稿一律降级为"公开界较少直接命中"。
- **规模天花板**。制度的收益随并发路数上升，人的拍板带宽随批次数线性吃紧；超过某个规模（观察线索是本机 4~6 路舒适、某形态满配 24 路即上限）后，加闸不如加"可对拍度"。

### 6.3 与旧底稿（单仓视角）的关系：本稿是跨仓升级

早期研究底稿只研究**单个仓库**（一个治理研究区），产出九类工程治理条目；防撞对账显示，本稿相关主题中"外部报告裁决"一条与旧稿高重叠（旧稿已覆盖）、另有三条部分覆盖（旧稿只有"收口 + 中立验证"、契约条款只讲机制、无工作树机制与跨项目实测）。因此本稿相对旧稿的**增量恰好三件**：① 跨三项目群复现（旧稿结构上不可能触及引擎项目的概率数据治理与Inkglean的 Web/桌面/数据库领域）；② 量化战果（旧稿多为机制描述，本稿给 60/6 路、3 起拦截、55 处污染、8 批连跑等数）；③ 纠错档案（§4-B、§5.4，旧稿无对应）。底座（多闸门形态、契约条款、中立验证）**只作类别级指认，不逐条搬旧稿条款**（映射见返工账）。

### 6.4 什么会让这套制度失效（负面预测）

三条我们已经在数据里看到苗头：

1. **清单腐化**——门禁清单与真实交付面脱节，制造"过时绿"，比没有脚本更糟；制度要求清单与 CI 同一事实源，但这仍是人肉维护的负债（防阀与再生长问题在多批复发，见收口底稿）。
2. **全绿的修辞诱惑**——术语一旦松动（把结构性空转写进"全部多道尽绿"），下游会话会把假绿当真、据此省掉 diff 审查。
3. **单点知识丢失**——制度靠"三处落盘 + 自包含交班块"承载，一旦某处漏落，约束就被**合法**绕开（14 天回退即此类），此时最贵的不是代码回退，而是重新发现同一条纪律。

## 7 结论

多代理编码集群的质量问题，主要不是模型能力问题，而是**信任分配问题**：把验收凭证的制作权交给了被验收的一方。本稿给出一套在真实生产里跑了一个月、跨三个互不相干项目群的治理制度——契约先行、门禁与执行分离、领地隔离与单点收口、不信自报的独立实测收口、人在批次之间当闸——多数支柱由可指名的事故逼出、留下可复算的战果，并配套一条方法学推论：**验证与仲裁层同样会造假绿**，因此唯一可信通道是回到原始产物与磁盘字节，任何"已核实"只是线索。我们同时交底了它不能主张的东西：五支柱的单项机制皆非发明（§1.5、§2、附录 B），本稿的价值在整合、跨项目复现、可复算与纠错档案；以及它的边界：N=1 团队、无对照组、多数数字止于台账级回证。
