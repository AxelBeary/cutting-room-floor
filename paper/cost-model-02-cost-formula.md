# 一、这笔账该怎么写：成本 = 往返次数 × 每次往返的上下文基数

## 1.1 一个能拿笔算的式子

把一次多代理协作拆成最小记账单元，只需要三个量：

- `N`：这次任务总共发生多少次"发起—等待—回读"（一次往返，一个 turn）
- `C0`：常驻上下文基数——系统提示、工具定义、项目规范文件、任务说明，凡是每一趟都原样挂在那儿的
- `u`：每趟新往上添加的固定开销（模型自己的回复、工具调用参数）
- `r`：每趟新读进来的内容体积（工具输出、日志片段、文件内容）

第 k 趟要搬上去的输入长度约是 `C0 + (k−1)·(u + r)`。把 k 从 1 加到 N，等差求和就得到闭式：

```
Total_input ≈ N·C0  +  u·N(N+1)/2  +  r·N(N−1)/2
              └一次方┘  └──────二次方──────┘
```

这个形状是本节全部结论的来源：**同一份内容，成本关于趟数 N 是二次的，关于常驻基数 C0 才是一次的。** N 一小，二次项没起来，你看到的账就近似正比于"内容多少"；N 一大，二次项吃掉一切，你看到的账就近似正比于"N²"，跟内容多少关系反而不大了。

这解释了我们第一节那个翻车现场：单次读取体积砍了 30%，总账不动——因为真正在长大的那两项都跟 N 有关，而 N 一点没变。

顺带说一句，这不是我们发明的观察。公开的量化工作已经把它钉得很实：研究代理轮次预算的论文（arXiv 2510.16786）在真实编码任务上直接测到 **token 成本随轮次呈二次方增长**，并明确把"管住轮次数量"列为被低估的成本主因——该实测样本的中位轮次在四十到六十这个量级（为论文口径，非本项目数据），仅施加轮次上限就省下 24%–68%，配合动态预算再省 12%–24%。模型厂商自己的口径也一样：把代理系统的成本描述为"上下文 × 轮次 × 并发"，并且承认每一轮都会把此前的全部历史重新发一遍（prompt caching 那条折扣除外，见 1.3）。

## 1.2 于是有了那条硬口径

从式子直接得到我们现在的评审纪律，两条：

**① 两个因子都压，但往返次数优先。** 因为 N 同时出现在一次项和二次项里，压 N 的收益是超线性的；压 C0 只是线性打折。

**② 禁止只用 token / MB 体量做成本测算，或者据此承诺降幅。** 因为同一批内容切成 3 趟和切成 30 趟，体量数字完全相同，成本差一个数量级以上。拿"这堆东西有多大"去报"这活要多少钱"，是把自变量搞错了。这条尤其针对方案评审里的口头承诺——"我把输出压缩一半，成本就降一半"这种话，在 N 未定的时候没有任何意义。

## 1.3 缓存计费：不是反例，恰恰是最强的佐证

到这里必须处理一个非常自然的反驳：**"现在有 prompt caching 了，重复重传不是按全价算的，你那套'重传历史很贵'是不是过时了？"**

先把机制说准（以主流代理 API 的公开计价为例）：命中缓存的前缀按基础输入价的 **0.1×** 计价（个别新模型降到 **0.025×**，即四十分之一）；写缓存要额外付一笔，5 分钟有效期是 **1.25×**、1 小时有效期是 **2×**；缓存有存活时间（典型 5 分钟）也有最小可缓存长度，太短的片段根本进不了缓存。

关键在于**缓存能压住的是哪一项**。缓存命中要求逐字一致的前缀，所以它压得住的东西恰好就是 `C0`——系统提示、工具定义、常驻规范文件，这些每趟都一样的部分。它压不住的，是**每一趟新加进来的那部分**：新读的工具输出、新产生的对话。而式子里随 N 二次方增长的，正是新增项。

所以缓存不是把"往返优先"削弱了，而是把它**纯化**了：

- 有了缓存之后，`N·C0` 这项被打了 0.1× 甚至 0.025× 的折，一次方部分几乎不疼了；
- 剩下的 `u·N(N+1)/2 + r·N(N−1)/2` 一分没折，成了账单主体；
- 结论：**贵的东西从"上下文有多大"彻底转移到"每趟新增多少 × 有多少趟"。** 用总 MB 去估成本，在有缓存的世界里比过去更离谱——因为同样的 MB，处在"命中"和"未命中"两种状态时价格能差十倍到四十倍。

这个修正对我们的实际影响是加了一条而不是减了一条：既然缓存只奖励稳定前缀，那么**让前缀稳定**本身是一项便宜可得的优化（不要因为每轮重排上下文顺序、不要把易变内容放在最前面、不要在批次中途换工具定义）。这条和"压往返"不冲突，它们作用在式子的不同项上。

## 1.4 三个该问的问题

于是评审任何多代理方案，我们只要求作者能回答这三问，按优先级：

1. **一共几趟？** 给出 N 的估计和它为什么不能更少。
2. **每趟新增多少？** 新增内容能不能干脆不进上下文（落盘、留指针、只把汇总读进来）。
3. **前缀稳不稳定？** 常驻基数能不能被缓存吃掉。

"总数据量多大"不在这三问里。它不是不重要，它是**第三个问题里被缓存折扣处理掉的那部分**。
