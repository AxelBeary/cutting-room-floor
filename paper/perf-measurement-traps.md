# 被缓存画反的热点排名：AI 代理自跑性能测量的六类污染与机器状态锚

> slug: paper-perf-measurement-traps ｜ 方向：性能工程 / 测量可信度 ｜ 正文中"证据甲/证据乙"为本稿两段施工实录的**稿内锚点**（其对应的仓内复算映射不入库，见文末证据来源与返工账留档）

## 摘要（中）

一台共享 Windows 机器上，一个 AI 代理连续跑了八批、无人值守的自研规则引擎性能改造。它自产代码、自跑基准、自写报告。有一天它拿着一份"热点画像"照图施工——直到换一种取法重测，发现**同一批 seed、先计时后剖析会跑出两份完全不是一回事的画像，冷/热比高达 57 倍，足以把热点排名整个画反**：真正占 61% 时间的热点被假画像压到 2.2%，一个"不值得动"的东西被排成第一名（证据乙）。这不是某个工具的 bug，而是一类系统性风险：在代理自主测量、且批次内没有人类复核查表里，性能数字极易被 **lru_cache、冷/热画像、跨会话机器负载、shell 环境变量残留、并行负载、探针自身开销**六类污染源成规模地伪造（证据甲）。本文逐条给出这六类污染源在一个真实长跑项目里的症状、量级与抓法：约 0.2µs/次 vs 真实约 94~290µs 的缓存假数（证据甲）、同机同天间隔 30 分钟 DFS 测出约 94/150/209/291µs 的 3 倍漂移（证据乙）、同一份负载 269s→1002s 的 3.7 倍跨会话漂移（证据甲/乙）、砍掉 97% 某类调用只换来 1.06× 实测的"计数≠耗时"教训（证据乙）。文章主张的可信结论纪律是四件套——**只报同轮比值 + 机器状态锚 + 冷画像 + 真实墙钟**（证据甲）。

必须前置声明：本文**不宣称发明测量学**。缓存/热身效应、CI 噪声、剖析器高估、"机器状态"对测量的影响，在 frappe 微基准讨论、pythonspeed 的 CI 一致性指南、Mytkowicz 等人在 ASPLOS 2009 的经典论文、以及 cProfile 官方文档里都已被反复写透。本文的增量只做一件事：把这些**已知**的测量陷阱，聚合复现到"AI 代理无人值守长跑"这一放大危害的新场景，并把散落的经验固化成一条可执行的"机器状态锚"纪律。

## Abstract (English)

On a shared Windows machine, an AI agent ran eight consecutive batches of unattended performance work on a self-built rule engine — generating code, running benchmarks, and writing its own reports. One day it built against a "hotspot profile," until a different way of capturing the data revealed that **the same seeds, profiled after timing, produce two entirely different pictures: the cold/hot ratio was 57×, enough to invert the hotspot ranking** — a function truly consuming 61% of the time was pushed down to 2.2%, while something "not worth touching" was ranked first (evidence 2). This is not one tool's bug but a class of systematic risk: with agent-driven measurement and no human review inside a batch, performance numbers can be mass-forged by six pollution sources — lru_cache, cold/hot profiles, cross-session machine load, leftover shell environment variables, concurrent load, and probe overhead itself (evidence 1). This article documents each source's symptom, magnitude, and detection with real incidents: ≈0.2µs/move cache artifacts vs a true ≈94–290µs (evidence 1), a 3× spread of ≈94/150/209/291µs for DFS measured 30 minutes apart on the same machine and day (evidence 2), a 3.7× drift of 269s→1002s for the same workload (evidence 1/2), and the "count ≠ cost" lesson that cutting 97% of a class of calls bought only a 1.06× wall-clock gain (evidence 2). The takeaway discipline is a four-part rule: **report same-round ratios only, anchor on machine state, profile cold, and measure real wall-clock time** (evidence 1).

We state up front: **this paper claims no invention in measurement science.** Cache/warm-up effects, CI noise, profiler over-counting, and "machine state" bias are already well covered by frappe's microbenchmark discussion, pythonspeed's CI consistency guide, Mytkowicz et al. (ASPLOS 2009), and the cProfile docs. Our only delta is re-aggregating these *known* traps into the harm-amplifying scenario of unattended AI-agent long runs, and hardening scattered folklore into one executable "machine-state anchor" discipline.

## 1. 引子：一份把排名画反的画像

故事的起点不是失败，而是"太成功"。代理在一台 Windows 共享机上给自研引擎做性能改造，流程是常规的两步：先跑计时拿总耗时，再挂剖析器拿热点排名，然后"照热点施工"。第一份画像出来后，排名第一名的是一个看起来理所当然、但"不太值得动"的函数；反倒是真正的重头戏只排在末尾。代理准备照这份排名开工。

问题出在取数据的顺序上：**同一批 seed，先跑计时、再跑剖析，第二遍剖析时数据已经全命中缓存**。当代理换一种取法——新进程、从头挂剖析器、喂全新输入——重测一次，得到的画像与第一份"完全不是一回事"：冷/热比达到 57 倍，热点排名整个翻转，第一份画像把真热点（实测占 61% 时间）压到了 2.2%，把"不值得动"的顶成了第一名（证据乙）。代理的原始记录里那句"这份画像推翻了原计划"，说的就是这一刻（证据乙）。

值得警惕的是这份假画像**并非异常崩溃，而是自洽、可信、还全绿**——数字规规矩矩、排名清清楚楚、没有任何报错。在有人盯着的场景里，工程师多半会本能地怀疑一句"这个数会不会太漂亮了"；但在无人值守的批次里，这份热画像会被当成事实源直接喂进下一步施工。它把优化预算指向了一个非瓶颈，如果照它改完再收工，读者会看到一份"依据充分、方法规范"的性能报告，而实际上**优化错了地方**——最危险的那种错误：不是算错，而是算对了不该算的东西。

这份被缓存画反的排名，只是冰山露出水面的一角。水面之下，是代理自主测量时一整套系统性的污染源。

## 2. 相关工作：已知问题，新场景

先划清边界：本文报告的每一类"污染"，在性能工程与系统测量文献里都有明确的先例。下面按实际查到的来源列出，并说明本稿与它们的关系——**聚合复现，不是首创**。

**CI/噪声机器上的一致性基准。** pythonspeed 的《Consistent benchmarking in CI》系统讨论了共享/虚拟化的持续集成机器上基准漂移、绑核/关 turbo/固定 CPU 频率、GC 干扰等噪声源，核心信息与本文同源：测量环境不可控时，绝对数字不可比。本稿的"跨会话机器负载""并行负载"两类污染，是这些已知噪声在**一台 Windows 共享单机、且并发长跑与性能实测抢同一批核**这一具体拓扑下的复现（证据乙）。

**机器状态与测量偏置。** Mytkowicz、Diwan、Hauswirth、Sweeney 在 ASPLOS 2009 的《Producing Wrong Data Without Doing Anything Obviously Wrong!》是本领域绕不过去的经典：作者证明，仅仅改变库的**链接顺序**，或改变**环境变量的字节长度**（经由栈对齐等间接路径），对基准运行时产生的影响，可以大到盖过被测优化本身——也就是说，"没做任何明显错事"也能产出方向反了的结论。本文的"环境变量残留"污染，以及"机器状态锚"这一命名，本质上就是这条已知结论在一台自跑机器上的落地；我们沿用其"machine state"的既有提法，不主张新的测量理论（证据甲/乙）。此外，Thomas Dullien 在其 QCon 演讲《Adventures in Performance》中转述的 ClickHouse 工程实践——"把 A、B 两版同一负载放在同一台机器、同一时刻跑，让两边的噪声尽量一致"——正是本文四件套里"同轮比值"的直接先例；同一演讲还把噪声邻居、核降频、ASLR 等列为测量之大敌，与本文"机器状态"关切一致。

**热身/缓存效应与微基准。** frappe 的《Microbenchmarks considered useful (if used correctly)》以及大量中文技术博客都反复强调：微基准要先热身、要看分布而非单点、警惕首慢后快的热身效应。本文的"lru_cache 缓存命中"与"冷/热画像"两类污染，是热身效应最极端的一个变体——被测实现自带记忆化，使得"第二遍"不是略快，而是快 57 倍乃至 1450 倍，直接把排名画反（证据甲/乙）。

**剖析器自身失真。** cProfile / pstats 的官方文档明确写着：剖析器会给每个函数"增加额外的处理开销"（additional overhead），因此 profile 出的时间**不等于**程序真实运行的挂钟时间，官方本身就把 profiling 数据定位为"定方向"而非"出收益"。本文的"探针自身开销"污染、以及"砍 97% 调用只快 1.06×"的教训（证据乙），正是这条官方告诫在高频内建函数场景下的一次代价高昂的印证。

**本稿的定位。** 上面每一条，单拎出来都不新。本文唯一的增量是把它们**放进"AI 代理无人值守、自产码自测自报、连跑八批没有人类在批次内复核"这一放大器里重新聚合**，说明：当测量者是一个不会"凭直觉怀疑漂亮数字"、且会把画像当事实源照图施工的主体时，这些已知陷阱如何从"偶发误差"升级为"系统性伪造决策"，以及据此沉淀出的工程纪律。

## 3. 六类污染源逐条：症状 / 量级 / 抓法

以下六类污染源，取自该项目八批施工中的真实事故记录（证据甲/乙）。每一类给三件事：症状长什么样、量级到多少、怎么把它抓出来。所有数字带稿内证据锚点。

### 3.1 lru_cache：记忆化让"第二遍"变成假数

**症状。** 被测实现自带 `@lru_cache`。多轮基准里，只要不主动清缓存，第 2/3 轮就全部命中，测出一个荒谬地快的"每次耗时"。更阴险的是，如果按"取中位数"来聚合多轮，中位数**会恰好选中那一轮被污染的假数**（证据甲）——你用来抗噪的统计量，反而把噪声挑了出来当代表值。

**量级。** 缓存命中把单次核心评估测成 **约 0.2µs/次**，而真实值在 **约 94~290µs** 区间（证据甲）——差了三个数量级。这个假数还差点改写路线判断：项目一度以为"查表化比原算法更慢"，事后确认"查表更慢纯属我用 lru_cache 的实现问题，不是路线问题"（证据甲）；换成扁平形态后，查表约 28.3µs vs DFS 约 291.6µs，实为快 10.31 倍（证据甲）。同一坑族下，一次真实约 395× 的提速，被未清缓存的脚本压成 1.7×（证据乙）。

**抓法。** 清缓存是**双条件**，缺一即出假数：① 每轮换**全新输入**（避免输入层复用），② 每轮前**显式清缓存**（`cache_clear()`）（证据乙）。多轮聚合取 **min** 而非 median/mean——微基准里外部干扰只会拖慢不会凭空加速，最小值更接近"少受污染"的真值（证据乙）。

### 3.2 冷/热画像：同一批数据画出两份排名

**症状。** 这就是引子里的事故。计时先跑、剖析后跑，等于剖析时一切已热；这份"热画像"与从头取的"冷画像"是两份东西，热点排名可以整体错位（证据甲/乙）。

**量级。** 同 seed 两遍，**冷/热比 57 倍**（证据甲/乙）。假画像把真热点（占 **61%** 时间）压到 **2.2%**，把"不值得动"的排到第一名（证据乙）——照它施工就会把预算全砸在非瓶颈上。

**抓法。** 用**冷画像探针**：新进程 + 从头挂剖析器 + 喂全新输入，并在报告里自带一个"冷/热比"自证字段，用它量化本轮到底热没热（证据乙）。冷画像才配当施工依据。

### 3.3 跨会话机器负载：同机同算法的绝对耗时不可信

**症状。** 同一台机器、同一份代码、同一个算法，换个时间点重测，绝对耗时能大幅漂移。跨会话拿绝对秒数互比，几乎必然得出错误结论（证据乙）。

**量级。** DFS 单次核心评估在**同机、同一天、间隔 30 分钟**下测出 **约 94 / 150 / 209 / 291 µs**，最大最小差约 3 倍（证据乙）。更狠的是跨会话：同一份负载从 **269s 变成 1002s（慢 3.7 倍）**（证据甲），绝对耗时跨会话漂移 **3.7 倍**——项目正是靠机器状态锚，用这个漂移**推翻了自己上一批下的结论**（证据乙）。

**抓法。** 三条：① **只报同轮比值，不报绝对耗时**（证据乙）；② 达标判定必须**带机器状态锚**（见第 4 节）（证据乙）；③ A/B 对比必须**同二进制、只差一个环境变量开关**，把变量隔离到唯一那一处（证据乙）。

### 3.4 shell 环境变量残留：没做错任何事，但环境变了

**症状。** 会话之间 shell 环境变量会残留。上一批 export 的某个开关/路径没清，这一批的"对照组"其实悄悄带着上一批的配置，A/B 变成"A 与 A'比"，对比失效。这一类比崩溃更隐蔽，因为它不留报错痕迹。

**量级 / 事故。** 该项目的直接教训就是把这条写成了硬约束：A/B 必须"同二进制只差一个环境变量开关"（证据乙），正是为了堵住"对比双方环境不干净"这个缺口。口径失控的量级可作旁证：同一件事换口径能差 6 倍——同一评估"纯内核 590× / 含胶水边界 98×"（证据乙）——说明"你测的到底是哪一层"只要没说清，结论就能被环境/口径带着走。Mytkowicz 等人的 ASPLOS 2009 结果在此提供外部背书：环境变量的字节长度这一"没人会去改"的东西，就足以翻转基准结论（见第 2 节）。

**抓法。** 进入性能实测前，显式重置一个已知干净的环境（清空/固定相关变量），并把"用了哪些环境变量"写进测量头；A/B 只容许差一个受控开关（证据乙）。

### 3.5 并行负载：旁边在跑，这里的数就废了

**症状。** 共享单机上，性能实测与长跑任务同时抢 CPU。被测算法旁边挂着一个满载的后台长跑，实测数字被邻居的调度/缓存/内存压力污染（证据乙）。

**量级 / 事故。** 该项目立了红线："**性能与长跑不得同时占用机器**——同一算法旁挂满载长跑时性能出数直接作废"（证据乙），并把排程定为"长杆无决策的长跑挂后台、性能实测等机器安静后单独跑"。抢核的代价有具体数字：曾出现 **34 个 worker 抢 28 核**的场面（证据乙），此时任何性能读数都无意义。

**抓法。** 跑前查同名进程、**同参数只允许一棵树**（证据乙）；性能出数**必须在机器安静时单独测**（证据乙）；对拍类不受此限可先做，性能类不行（证据乙）。

### 3.6 探针自身开销：剖析器的"计数"不是"耗时"

**症状。** 把 cProfile 的 `tottime`/调用计数直接当成"优化收益预算"。剖析器为每个函数加了额外处理开销，且对**高频内建**的计数尤其会系统性高估其"重要性"（证据乙），于是你去砍一个"调用次数吓人但其实很便宜"的东西，砍完发现总耗时纹丝不动。

**量级。** 该项目据此砍掉了某类调用 **97%**，实测只换来 **1.06×** 提升（证据乙）。这是一记响亮的"计数≠耗时"耳光：剖析器上的 97% 与墙钟上的 1.06×，是两个几乎不相干的世界。

**抓法。** **剖析器数字只用来定"往哪儿砸"，收益大小必须墙钟实测**（证据乙）。把 profiler 的计数/占比直接当收益，就是自我欺骗。这条与第 4 节的"真实墙钟"是同一件事的两面。

## 4. 机器状态锚与四件套纪律

六类污染的共同解法，不是"更小心"，而是一套可执行的取数纪律。核心是四件套（证据甲）：

1. **同轮比值。** 绝口不提绝对耗时，只报"同一轮里 A/B 的比值"。3.3 节的 3 倍、3.7 倍漂移，在"同轮比值"口径下会被自然抵消（证据乙）。
2. **机器状态锚。** 在每轮测量里固定挂一段"**与本批改动无关的已知负载**"当锚。跨会话比较时，先用锚的读数校准本轮机况，锚漂了就把整轮作废或换算。项目把"达标判定必须带机器状态锚"写成铁律，并靠它**推翻了自己上一批的结论**（证据乙）——这正是"机器状态"这一 Mytkowicz 既有概念的工程落地（证据乙）。
3. **冷画像。** 新进程 + 从头挂剖析器 + 全新输入，并自带冷/热比自证字段（证据乙）。只有冷画像才配当施工依据，因为真实生产路径就是冷的（新输入进来时缓存里没有它）。
4. **真实墙钟。** 收益一律以墙钟实测为准，剖析器数字只定方向（证据乙）。凡"砍了 X% 只快 1.06×"这类反差点（证据乙），都要如实进报告，不许用剖析器占比冒充收益。

配套还有两条防自证条款：**回退计数闸门**——开关改造必须挂回退计数器，靠"关侧全部回退、开侧零回退"证明开关真的生效（项目实测关侧 38.7 万次调用全部退回旧算法、开侧退回 0 次）（证据甲），否则"对拍通过"可能只是新旧都走了老路径；**口径写清**——"单次核心评估 ≤0.5 微秒"这类指标，纯内核约 0.16µs 达标、含传参边界就不达标，报告必须写清口径并把不达标那条登记成偏差，不得自选有利口径（证据乙）。

四件套不是空谈，它在该项目里跑通了一个正向闭环：**先冷画像→最小刀→逐位全等→回退计数→再画像定下一靶**（证据乙）。这个循环两次推翻既有结论——旧"核心评分占 99% 时间"的热画像直接作废、计分模块连前 14 名都没进——最终把整轮评估从 **11,438 ms 降到 1,144 ms（10.00×）**、落进 1.5s 产品预算，且逐位全等（证据乙）；评估 DFS 的时间占比也从 41% 掉到 2.1%，榜首换人（证据乙）。同一条链路上还顺手逮出了真正的头号瓶颈：一个对整数做 `str(int).upper().startswith(...)`、每轮被调 1250 万次的字符串判定（证据乙）——它不在任何"性能优化候选清单"上，是冷画像把它顶到了该动的位置。

## 5. 代理场景的特殊性：无人复核把小污染放大成大事故

以上污染，人类工程师也会中。但"AI 代理无人值守自跑"这个场景，有四个放大器，把同一类污染的危害从"偶发返工"抬升到"系统性错方向施工"（证据甲/乙）：

- **没有'这数太快了不可能'的直觉刹车。** 人类看到约 0.2µs/次会本能起疑；代理不会——它把 0.2µs 当事实往下用（证据甲）。缓存假数、热画像排名，在无人复核时畅通无阻。
- **聚合统计替污染背书。** "取中位数"这种在人手里用于抗噪的操作，在自带记忆化的被测实现上会**恰好选中被污染那轮**（证据甲/乙）。代理用规范统计量，反而给假数盖了章。
- **画像是直接施工输入，且会被照图执行。** 人类拿一份可疑画像，通常还要拍脑袋权衡；代理把它当事实源直接优化。一份热画像"推翻了原计划"（证据乙）这句话的分量在于：如果没有换取法重测，代理会**忠实地、高效地**优化错地方。
- **自产码自测自报，"全绿"本身不含信息量。** 当代码、基准、验证报告都由同一代理产出时，"0 分歧/全量绿灯"这类声明不具备可信度——这是无人值守施工的结构性弱点。项目的应对是把它上升为红线："报'0 分歧'之前，先故意造若干已知有病的实现，证明对拍闸门**抓得住**"（证据乙记的 mutate-to-prove-the-gate），并把"批次内无人值守、人在批次之间当闸做人工终验"作为治理节律（证据甲）。测量可信度，是这套防假绿制度在性能维度上的一个切面。

一句话：代理场景不产生新的测量陷阱，但它**取消了对陷阱的人工免疫**，并给每个陷阱配了一个"自动照做"的执行器。这正是值得把这六类污染单独立档的原因。

## 6. 复核清单（收工前逐条自检）

对任何一次代理自跑的性能测量，采信其结论前逐条过：

- [ ] 被测实现是否自带记忆化/缓存？若有，是否**每轮换全新输入 + 每轮前清缓存**（双条件）？（证据乙）
- [ ] 多轮聚合用的是 min 还是 median/mean？median 有没有可能选中被污染轮？（证据甲/乙）
- [ ] 热点画像来自**冷**取法（新进程 + 从头挂剖析器 + 新输入）吗？报告里有没有冷/热比自证？（证据乙）
- [ ] 结论只报**同轮比值**了吗？有没有偷偷夹带跨会话绝对耗时互比？（证据乙）
- [ ] 本轮挂了**机器状态锚**吗？锚的读数与上一批一致吗，差多少？（证据乙）
- [ ] 收益是**墙钟实测**的吗？有没有把剖析器占比/计数直接当收益？（证据乙）
- [ ] 实测时机器**安静**吗？有没有并发长跑抢核（如 34 worker 抢 28 核）？（证据乙）
- [ ] A/B 是**同二进制只差一个环境变量开关**吗？进实测前环境清干净了吗？（证据乙）
- [ ] 开关改造挂**回退计数器**了吗？做到了"关侧全退、开侧零退"吗？（证据甲）
- [ ] 报告写清了**口径**（纯内核 vs 含边界生产路径）吗？不达标那条登记成偏差了吗？（证据乙）
- [ ] 门禁数字全是**实测值**吗？有没有夹带"推定值"当实测？（证据乙）

任一勾选不过，本轮性能结论降级为"仅定方向、不作达标判定"。

## 7. 局限

诚实边界，读者据此判断可迁移范围：

- **回证的层级。** 本文引用的六类污染与全部数字，核到的是两段施工实录（证据甲/乙）的逐字条目；实录本身是会话摘要的二手转录，**尚未下钻到最底层会话执行记录逐字复算**。其中被点名的约 0.2µs↔约 290µs、57×、约 94~291µs、3.7×、1.06× 等，在两级索引间互校一致（见本仓交叉验证留档对本主题的抽验），但对 57×、3.7× 等仍标"⚠️转抄待复算"，发表前须回到原始会话执行记录逐字复算坐实（附录 B）。
- **拓扑特例。** 事故来自**一台 Windows 共享单机**、纯 Python 实现、CPU 密集、且并发长跑与实测抢同批核的具体环境。数字（如 28 核、20,312,500 字节的表、1250 万次调用）是该引擎特有量级，**倍数量级不迁移**到受控基准台 / 数据中心 / 其他栈。
- **档案完备度参差。** 污染里"探针高估（cProfile tottime）"与"绝对耗时跨会话漂移"两条，实录自评素材为"需补"档（证据乙），事故链完整但独立复算样本尚薄；发表前应补测或明确标注为经验之谈。
- **不宣称发明。** 如第 2 节所述，六类污染的机制在公开文献中皆已知，本稿价值在聚合场景与纪律化，不在新测量原理。若审稿人指出某一具体数字与公开基准更接近某已知效应，应以外部先例为准、相应收缩本稿主张。
- **测量条件缺项。** 本稿 µs 级读数（约 0.2µs/次、约 94~290µs、约 94/150/209/291µs、约 28.3/291.6µs、约 0.16µs）在实录中**未附带可坐实的解释器/引擎小版本与被测轮数**，故一律降为"约"；秒/毫秒级与调用计数（269s→1002s、11,438→1,144ms、38.7 万次、1250 万次）在实录中带明确采样条件（同负载 / 墙钟 / 逐位全等 / 同机同天间隔 30 分钟），予以保留。

## 8. 结论

性能测量的坑不是新的；新的是**坑的宿主换成了不会怀疑漂亮数字、还会照图施工的 AI 代理**。在一个连跑八批、批次内无人复核的自研引擎项目里，六类污染源——lru_cache、冷/热画像、跨会话负载、环境变量残留、并行负载、探针自身开销——各自制造了真实事故：约 0.2µs/次冒充约 94~290µs（证据甲）、同 seed 冷/热差 57 倍把热点排名画反、真热点 61% 被压成 2.2%（证据乙）、同机同天 3 倍与跨会话 3.7 倍的绝对耗时漂移（证据乙/甲）、砍 97% 调用只快 1.06×（证据乙）。对这些陷阱唯一站得住的回应是一条纪律：**只报同轮比值、以机器状态锚对齐机况、只信冷画像、收益一律墙钟实测**（证据甲），外加回退计数与口径写清两条防自证条款。四件套让人类工程师免于自欺，在无人值守的代理流水线上，它从"良好习惯"升级为"不可替代的质量闸门"——因为没有第二双眼睛，纪律本身就是那双眼睛。

## 附录 A：数字纪律清单

本项目的性能/评估报告有一套贯穿的"数字纪律"，与测量污染同属一脉，一并沉淀如下：

- **门禁数字只填实测值，推定值一律等跑完再填。** 报告里先写"1171 passed"是推定值不是实测值；后来实跑确实等于 1171 属运气不属纪律，须改成"等真跑出来再填"（证据乙，原话"那是运气不是纪律"）。
- **全量计数自洽核对。** 收口时用"上批总数 + 本批新增 = 本批总数"校验（1171+47=1218、1218+80=1298），防测试文件被静默丢弃造成假绿（证据乙）。
- **降级/异常计数进报告正文。** "EV 降级次数=0"作为必写字段：`ev_errors>0` 意味着那段其实在跑贪心而非目标算法，照样报数就是假绿（证据乙）。
- **达标判定带机器状态锚，且跨代不混比。** 绝对耗时跨会话不可比（实测漂移 3.7 倍，证据乙/甲）；新跑的组只能组间互比，禁止与旧存档跨代比较（证据乙）。
- **口径写清、偏差登记。** 同一件事换口径差 6 倍（同一评估纯内核 590× / 含胶水 98×，证据乙）；硬指标随口径翻转时，报告必须写清口径、把不达标那条登记成偏差，不得自选有利口径、也不得去改设计书数字（证据乙）。

这套纪律的内核与"四件套"一致：**任何进入结论的数字，都要能回答"你在什么机况、什么口径、冷还是热、实测还是推定下拿到的"**。
