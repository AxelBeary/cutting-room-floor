## 摘要（中）

一个约稿类平台用「8 位邀请码 + 每 IP 每 5 分钟 10 次限流 + 默认 3 天有效期」做注册闸门。当时有人问：要不要把码加长？要不要支持一码多次？本文把这两个问题还原成一道可复算的算术：把**组合数 \(N\)**、**同时在流通的可用码数 \(S\)**、**单身份单位时间尝试上限 \(R\)**、**码有效期窗口 \(W\)**（再加一项**攻击者可支配的独立限流身份数 \(I\)**）摆进一个公式，一次算清「期望突破时间」，并据此给出两条反直觉结论：

1. **加长码是纯亏。** 真正决定可行性的是闸门（\(R\) 与 \(I\) 的乘积），不是码长。在算例口径下，单身份随机猜一次命中的成功率只有 \(7.86\times10^{-9}\)（3 天窗口），攻击者要压穿窗口需要同时握有约 \(2.5\times10^{6}\) 个不可被限流识别的独立身份；把码从 8 位加到 10 位只是把这个身份门槛乘 \(32^2\)，而代价由**每一个手抄邀请码的合法用户**永久支付。闸门一旦可绕（源站 IP 泄露 + 未开 Authenticated Origin Pulls），加长买到的东西直接归零。
2. **多次码与等量一次码「撞码期望相同」这句要在口径上打折。** 用「名额数」当除数时两者恒等（这是同义反复）；用攻击者真实面对的**命中集大小**（不同有效码字符串数）算，一张 50 次码比 50 张一次码**难撞 50 倍**；用「抽干全部名额」算，前者反而**易 4.5 倍**。三个口径的差都在个位数倍数量级，而闸门提供的是 \(10^{6}\) 倍冗余——所以决定安全性的既不是码长也不是次数，而是**泄露面**：一张码被转发出去就一次损失 \(M\) 个注册位。该防的是名额封顶（算例拍板 100）+ 短有效期 + 随时吊销 + 使用名单可归因。

本文附完整复算过程与差异登记：原始记录（评估会话摘要）的 10 项数字中 7 项复算吻合（其中 1 项原口径取整偏低 4.5%，保留"约"），3 项不符并已就地降级标注差值（详见 §3.3 与附录 A）。另附一节同构的语义缺口——**"重置口令 ≠ 踢下线"**（§6），它与本文主线的病根相同：你以为在生效的那道防线，和实际拦住攻击者的那道，不是同一道。

## Abstract (English)

A commission-platform registration gate was protected by "8-character invite codes + 10 attempts per IP per 5 minutes + 3-day default validity". The questions raised at the time were: should the code be longer, and should multi-use codes be allowed? Both reduce to reproducible arithmetic once you write down four quantities — code space \(N\), currently-valid codes in circulation \(S\), per-identity attempt rate \(R\), and validity window \(W\), plus the attacker's budget of distinct rate-limit identities \(I\) — and compute the expected break-through time. Two counter-intuitive results follow. **(1) Lengthening the code is strictly negative-value.** The gate (\(R\times I\)), not the code space, decides feasibility: at the case parameters a single identity achieves first-hit probability \(7.86\times10^{-9}\) per 3-day window, and an attacker needs \(\sim2.5\times10^{6}\) un-throttleable identities to break the window; going from 8 to 10 characters merely multiplies that identity threshold by \(32^2\) while every legitimate user who hand-transcribes a code pays forever. If the gate is bypassable (origin IP leak without Authenticated Origin Pulls), length buys nothing. **(2) "Multi-use codes have the same brute-force expectation as the equivalent number of single-use codes" is metric-dependent.** Under a slot-count divisor it is an identity; under the size of the actual hit set (distinct live strings) a single 50-use code is 50× *harder* to hit; under a drain-all-slots metric it is 4.5× *easier*. All three divergences are small-count factors against \(10^{6}\times\) gate headroom, so the real variable is leakage surface, addressed by per-code caps (100 in this case), short validity, revocation and attribution logs. Full recomputation with a discrepancy register is included: of 10 published figures, 7 reproduce (one within 4.5%, kept as "approx."), 3 do not and have been downgraded in place. A companion section documents the isomorphic semantic gap — *resetting a password does not log the user out* (§6).

**关键词**：邀请码、短码系统、暴力破解可行性、限流闸门、定量风险评估、Authenticated Origin Pulls、会话失效、多认证通道

## 1 场景

案例系统是一个约稿类平台（下文称 **S 系统**），Web 端 + 自托管单机部署，链路为 `CDN → 反向代理 → 应用`。注册不开放：**新用户必须填一张管理员生成的邀请码**。

当时的实现口径（下表即本文的 **表 1**，后文所有输入值都指回它；取值来自某次安全评估会话对代码与配置的现场核对——读的是实现，不是文档）：

**表 1 案例系统注册闸门的实现口径（评估会话当时的记录，非推荐值）**

| 项 | 口径 |
|---|---|
| 码长 | 8 位 |
| 字符表 | 字母数字去掉易混字符 `0/O/1/I` → 32 进制 |
| 生成 | 密码学安全随机数（`crypto.randomInt`） |
| 限流 | 注册接口按 **IP** 滑动窗口 **10 次 / 5 分钟**（与登录验证码同强度） |
| 有效期 | 默认 3 天，最长 30 天，到期自动失效 |
| 消耗 | 一码一人，提交注册即消耗，用后作废，可提前吊销 |
| 错误提示 | 码不存在 / 已使用 / 已过期 / 已吊销 → 统一返回「邀请码无效」（防枚举） |

用户提出的两个问题非常典型、也极其常见：

- **「加长更好吗还是就这样？」**
- **「能不能开发多次使用的码？」**（后续追问：**多次码要不要加长，还是短码足够？**）

这两个问题不需要观点，需要算术。而算术的价值在于：算完之后，两个直觉答案（"加长更安全所以加"、"多次码更危险所以要加长"）**都是错的**，或者更准确地说，都是**问错了变量**。

同期还暴露出一个不相关的、但同病根的问题：管理员重置动态口令后，用户仍在登录态里（案例事实链见 §6）。§6 单独处理。

## 2 威胁模型与假设

写公式之前必须先把攻击面钉死，否则后面所有数字都是装饰。

### 2.1 攻击者

- **目标**：在不持有任何有效邀请码的前提下完成一次注册（获得一个入驻账号），或尽可能多地获得账号。
- **能力**：可向注册接口提交任意次数请求；可控制来源身份（IP 地址、User-Agent、Cookie、请求头）；可租用代理池。
- **不能做**：**离线验证**。码在服务端校验，攻击者拿不到可比对的密文或哈希，无法下载一个字典在 GPU 上跑。
- **辅助通道（本文不建模）**：社工、钓鱼、内部人员泄码、把码所在的群聊公开转发。§7 说明为什么这条通道的实际风险远高于撞码。

> **"不能离线验证"是本类系统天然安全的第一前提，必须明写。** 一旦攻击者能离线验证（例如把码写进可被拖库的表、或存在可预测的短令牌哈希），速度上限就从"被防方设的 120 次/小时"变成"攻击者的算力"，两者相差约 10 个数量级。任何短码系统的定量分析，第一件事都是确认它是**在线攻击**。

### 2.2 假设清单（读者迁移时逐条替换）

| # | 假设 | 算例取值 | 迁移时怎么验 |
|---|---|---|---|
| A1 | 字符表大小 \(C\) | 32 | 数一遍生成器的字典；去掉易混字符会显著缩小 \(N\)，别默认 62/36 |

| A4 | 单身份尝试上限 \(R\) | 2,880 次/天 | 从限流器配置读"窗口/次数/键"，注意键是 IP 还是账号还是全局 |
| A5 | 同一时刻流通的可用码字符串数 \(S\) | 50（假设） | 这必须是**分布**不是常数：读发码节奏，取峰值 |

### 2.3 攻击面修正（原文没算但会翻转结论的三处）

**修正一：限流按 IP 计 → \(I\) 的可控性取决于源站是否可被直连。**
S 系统的限流键是"CDN 回源时标注的真实访客 IP"。当时运维文档记录了明确风险场景：**若源站真实 IP 泄露、且 CDN 的 Authenticated Origin Pulls（AOP）未开**，攻击者可绕过 CDN 直连源站并自写转发头，限流形同虚设（风险口径见同一次评估会话里的运维文档记录，加固落地过程见 §5①）。这一项当时列为"推荐加固"而非"必做"，用户在该次会话中回了一句"Authenticated Origin Pulls 开过了"，缺口视为闭合。

> 定量影响：\(I\) 从 1 变成"攻击者预算的函数"。§3.4 会给出让闸门在 \(W\) 内失效所需的 \(I\) 门槛值——这才是这个缺口的真实价格。

**修正二：防枚举一旦漏了，\(S\) 的口径会从"当前可用"放大到"历史累计"。**
统一返回「邀请码无效」的意义不是"减少信息"这种软话，而是一个硬算术：**命中集只包含当前可用的码**。如果"已过期"与"不存在"可区分，攻击者的有效命中集扩大到**系统历史上生成过的每一个码**（已用/已过期/已吊销都算命中信号，即使不能再用，也给了他"这个字符串曾经是码"的确认，可用于分型号/分批次探测）。S 系统单次压测一批就灌了约 35,300 个码（该峰值同时用作 §3.4 敏感性分析的中间档）。若历史累计到 \(10^6\)，则

\[E_1 = N/S = 1.0995\times10^{12}/10^{6} = 1.0995\times10^{6}\ \text{次}\]

单 IP（2,880 次/天）**382 天**可命中一个"曾经有效的码"；若同时限流失效（\(I\) 无约束、按 1,000 次/秒算），**18.3 分钟**。这个数与本文主结论不冲突（撞出来的码已失效，不能注册），但它说明：**防枚举不是"锦上添花的隐私设计"，它是把 \(S\) 的口径锁死在当前可用集的那根销子。**

**修正三：\(S\) 是时变的，最坏时刻是大批量发码期。**
运营节奏（一次放出一批入驻名额）会让 \(S\) 短时冲高。§3.4 用压测峰值 \(S=35{,}300\) 做了一档敏感性——结论是闸门仍然稳，但"稳"的裕度从 \(10^{6}\) 掉到 \(3.6\times10^{2}\)（读这档数时注意：\(S\) 取的是单批峰值，\(W\) 同时取最长 30 天窗口，与默认 3 天基线不是同一档输入）。这直接给出 §5 的一条动作：**批量灌码期临时收紧限流或缩短有效期**。

## 3 定量框架与复算过程

### 3.1 四因子框架与主公式

记号：

- \(N = C^{L}\) —— 组合空间
- \(S\) —— 同一时刻**流通中的有效码字符串数**（多个可命中的目标）
- \(R\) —— 单个限流身份在单位时间（本文统一取"每天"）内的最大尝试次数
- \(W\) —— 一个码从生成到失效的时间窗（天）
- \(I\) —— 攻击者可支配的、彼此不被限流器关联起来的独立身份数

四条公式：

1. **首次撞中期望尝试数**（无放回均匀猜测，命中集大小 \(S\)）：

\[\ E_{1}=\frac{N+1}{S+1}\ \approx\ \frac{N}{S}\quad (N\gg S)\]

2. **期望突破时间**（天）：

\[\ D=\frac{E_{1}}{R\cdot I}\]

3. **可行性判据**——攻击者只有在窗口内得手才有意义：

\[\ \text{可行}\iff D \le W\quad\Longleftrightarrow\quad I \ge \underbrace{\frac{E_{1}}{R\cdot W}}_{\displaystyle I_{\text{need}}}\]

4. **裕度**（本文统一用这个无量纲量比较"加固值不值"）：

\[\ k=\frac{D}{W}\qquad(\text{单身份口径下 } k=I_{\text{need}})\]

> \(k\) 就是"窗口能装进几个突破时间"。\(k\gg1\) 不可行，\(k\lesssim1\) 可行，中间看预算。**注意那个恒等式**：单身份的突破天数除以窗口天数，恰好等于攻击者所需的独立身份数。这一个式子把"加长/收紧限流/缩短有效期"和"伪造 IP"两类动作放进了同一杆秤——它们都只是 \(k\) 的乘子，而 \(I\) 是**唯一由攻击者自己填的量**。

原会话用的除数是"还能用的名额数"而不是"有效字符串数"，这在 §4.2 会被证明是口径选择而不是错误，本文两种都算。

**顺手量出的两处收紧点**（原文没提，属复算副产品）：

- 现闸门 10 次/5 分钟/IP = **120 次/小时/IP**。OWASP ASVS v4.0.3 的要求 2.2.1 明写了"验证单个账号每小时失败尝试不超过 100 次"（英文本为 "Verify that no more than 100 failed attempts per hour is possible on a single account"；该条自带 NIST SP 800-63B §5.2.2 的映射列，即数字与 NIST 同源，但它是 ASVS 自己的要求句、不是转引参考值）。口径不同：账号 vs IP，不能直接判违规，但同量级。收紧到 6 次/5 分钟即 72 次/小时，代价是合法用户重试机会仍够用。
- 单身份 3 天窗口的首次命中成功率 \(P_1 = R\cdot W/N = 8640/1.0995\times10^{12} = 7.86\times10^{-9} \approx 2^{-26.9}\)。

### 3.4 两个"压穿阈值"（把结论变成可复用的判据）

**阈值一：攻击者身份预算 \(I_{\text{need}}=E_1/(R\cdot W)\)**

| \(W\) | \(I_{\text{need}}\)（\(S=50\)） | 读法 |
|---|---|---|
| 3 天 | **2.55×10⁶** | 需要约 255 万个彼此不被关联的限流身份，才在窗口内有一次期望命中 |
| 30 天（最长） | **2.55×10⁵** | 放宽到最长有效期，门槛降 10×，仍是十万级 |

**阈值二：流通名额压穿值 \(S^{*}=N/(R\cdot W)\)**（攻击者不需要伪造身份，只等活动方自己把码堆出去）

| \(W\) | \(S^{*}\) | 对照 |
|---|---|---|
| 3 天 | 1.27×10⁸ | — |
| 30 天 | **1.27×10⁷** | 压测单批峰值 3.53×10⁴（§2.3 修正三同一档），差 **360 倍** |

\(S=35{,}300\) 档复算：\(E_1=3.11\times10^{7}\)，单 IP **10,815 天 ≈ 29.6 年**——仍 ≫ 30 天窗口，闸门不穿，但裕度从 \(10^{6}\) 掉到 \(3.6\times10^{2}\)。**这就是 §5 那条"批量灌码期临时收紧"动作的算术依据。**

### 3.5 对照 RFC 8628 §5.1 的 2⁻³² 判据

RFC 8628（OAuth 2.0 Device Grant）§5.1 "User Code Brute Forcing" 是短码暴破可行性最成体系的公开表述，而且它的推理与本文完全同构：

> "Since the user code is typed by the user, shorter codes are more desirable for usability reasons… Therefore, it is recommended that the server rate-limit user code attempts."（RFC 8628 §5.1）
>
> "The rate-limiting and finite lifetime on the user code place an artificial limit on the amount of work an attacker can 'do'. If, for instance, one uses an 8-character base 20 user code (with roughly 34.5 bits of entropy), the rate-limiting interval and validity period would need to only allow 5 attempts in order to get the same 2⁻³² probability of success…"（同节）

把这条判据搬到 S 系统：要求 \(P_1 = R\cdot W/N \le 2^{-32}\)，即窗口内允许尝试数 \(A \le N\cdot2^{-32} = 256\) 次。代入现状（\(A=8640\)）：

- 不达标，差 33.8 倍（\(2^{-26.9}\) vs \(2^{-32}\)）。
- 三条独立达标路径：①**缩短有效期**到 2.13 小时（256/2880 天）——过狠；②**收紧限流**到 ≤3.56 次/小时——合法用户几乎无感；③**加长**到 10 位（9 位仍差 5.5%，\(2.46\times10^{-10}>2.33\times10^{-10}\)）。

这个对照是本节的价值所在，也是它必须被写出来的原因：**它给"加长确有边际收益"留了一个诚实的缺口。** 为什么仍然判"纯亏"，见 §4.1。

## 4 反直觉结论与边际分析

### 4.1 结论一：加长是纯亏（含成立区间与例外）

原文的论证是"2 万年变 200 万年，没有实质区别"。复算后这句话的**绝对值错了**（差异二），但**方向对，而且理由要找得更准**。准确的论证分三步：

**第一步：可行性由 \(k=D/W\) 判定，不由 \(D\) 的绝对值判定。**
算例 \(k=2.5\times10^{6}\)。加 1 位 → \(k\times32=8.1\times10^{7}\)。从"完全不可行"到"更加完全不可行"，**可行性判定不变**。安全预算的汇率应该按"改变了哪一档判定"结算，而不是按倍数结算。

**第二步：加长的成本不是零，且由全体用户分摊。**
邀请码的真实使用路径是"管理员在即时通讯群里发一串字符 → 用户手抄进输入框"。若单字符抄错率为 \(p\)，整码失败率为 \(1-(1-p)^{L}\)。取 \(p=1\%\)（**这是演示假设，S 系统未实测，见附录 B 待办**）：

| \(L\) | 整码失败率（\(p=1\%\)，演示假设） | 相对 8 位 |
|---|---|---|
| 8 | 7.73% | 基线 |
| 10 | 9.56% | **+23.8%** |
| 12 | 11.36% | **+47.1%** |

失败的表现形式是"码明明是对的却提示无效"——而错误提示被（正确地）统一成了防枚举口径，所以这类客诉**无法从错误码区分出来**，只能靠人工。这是加长的真实标价。

**第三步：闸门一旦可绕，加长买到的东西归零。**
\(P\) 随 \(I\) 线性放大。若源站可被直连、IP 头可自写，\(I\) 就是攻击者预算的自变量：从 \(2.5\times10^{6}\) 抬到 \(8.1\times10^{7}\)（+1 位）或 \(2.6\times10^{9}\)（+2 位），在"按小时租住宅代理池"的预算模型里不构成数量级障碍；而抄写失败率是每一次合法注册都要付的。**同一笔钱花在 AOP 上是配置一次、永久生效；花在码长上是永久收用户的税。**

> **结论一的严格表述**：在 \(k\gtrsim10^{3}\) 的区间（本案例 \(k\approx2.5\times10^{6}\)，深居该区间）内，加长是纯亏。**区间外的例外必须一并写出来，否则这条结论会被读者误用**：若某系统 \(k<10^{3}\)（例如纯数字 4–6 位、或限流键可被轻易伪造、或码长期有效），加长/收限流就重新回到桌面，是必要动作而不是可选动作。RFC 8628 §5.1 的 2⁻³² 对照（§3.5）恰好给出这个例外的边界：S 系统单身份口径未达该线，达到它需要 10 位——但达到它的性价比明显低于收紧限流（路径②，合法用户几乎无感）。
>
> 一句话：**加长不是不能加，是不该用加长的方式解决这个题。**

### 4.2 结论二：多次码 vs 等量一次码——"数学上完全一样"必须打折

原会话在回答"多次码要不要加长"时给出：

> 暴力撞码的期望次数 = 总组合数 ÷ 在流通的"还能用"的名额数
> 一次码 × 50 张 ≈ 50 个名额 → 平均要试 220 亿次
> 一张 50 次码 = 同样 50 个名额 → **数学上完全一样**，还是 220 亿次

**这条推理的除数是"名额数"。** 而"名额数"在两种方案下被定义为同一个数（\(S\times M\)），所以"完全一样"是这个定义的直接推论——它同义反复，不构成发现。换成攻击者真实面对的**命中集大小**（不同有效码字符串数 \(S_{\text{str}}\)），三张牌摊开：

| 方案 | 有效字符串 \(S_{\text{str}}\) | 总名额 | \(E_1\)（首次撞中） | \(D\)（\(I=1,R=2880\)） |
|---|---|---|---|---|
| 50 张一次码 | 50 | 50 | \(N/50=2.199\times10^{10}\) | 2.09×10⁴ 年 |
| 1 张 50 次码 | 1 | 50 | \(N/1=1.0995\times10^{12}\) | **104.5 万年**（难 50×） |
| 1 张 100 次码（算例封顶） | 1 | 100 | \(1.0995\times10^{12}\) | 104.5 万年 |

反过来，若攻击者的目标不是"进去一次"而是"抽干全部名额"，需要集齐所有命中目标，期望为 \(N\cdot H_{S_{\text{str}}}\)（\(H\) 为调和数，\(H_{50}=4.4992\))：

| 方案 | 抽干全部名额 \(E\) | \(D\) |
|---|---|---|
| 50 张一次码 | \(4.95\times10^{12}\) | **470 万年** |
| 1 张 50 次码 | \(1.10\times10^{12}\)（只需命中一次） | **104.5 万年**（易 4.50×） |

**所以正确的表述是**：三个口径给出的答案分别是 1×（名额口径，同义反复）、50×（命中集口径，多次码**更难撞**）、4.50×（抽干口径，多次码**更易被抽干**）。三个分歧都是**小倍数量级**，而闸门提供的冗余是 \(10^{6}\) 量级——在 \(k\) 面前，码长和次数**都不是变量**。

那什么才是变量？**泄露面。** 一次码泄露 = 损失 1 个注册位；一张 50 次码发到群里被转出去 = 一次损失 50 个注册位，而且**事后无法归因是谁泄的**（原文对多次码的提醒正是这一句）。加长对这件事零帮助——码长不改变"谁能看见这张码"。能改变的只有四件事：

- **名额封顶**（\(M\le100\)，不提供"无限次"）——把单次泄露的最大损失钉住；无限次会让撞码期望一路往下掉，也给泄露留无限空间；
- **短有效期**（默认 3 天）——把泄露的存活窗口钉住；
- **随时吊销 + 到期自动失效**；
- **使用名单可归因**（谁、何时、用什么码）——把"防不住"变成"事后可查"。

这四项里没有一项需要碰码长。这是结论二真正的落点。

### 4.3 边际分析：谁是乘子，谁翻转判定

把 §3.1 的四个量按"能不能被攻击者自己填"二分：

| 动作 | 对 \(k\) 的效果 | 谁付成本 | 攻击者可控性 |
|---|---|---|---|
| 码长 +1 位 | ×32 | 全体手抄用户，永久 | 不可控 |
| 限流强度 | ×\(1/x\) | 撞错次的合法用户（弱） | 不可控 |
| 有效期 \(W\downarrow\) | ÷\(W\)（\(k=D/W\) 直接放大） | 发码节奏，用户无感 | 不可控 |
| 流通名额 \(S\downarrow\) | ×\(1/S\) | **业务本身**（名额是要放出去卖的东西） | 不可控 |
| **\(I\uparrow\)（IP 可伪造 / 代理池）** | **÷\(I\)，可到 \(k\le1\)** | — | **完全可控** |

前四行全是线性乘子，在 \(k\approx2.5\times10^{6}\) 的冗余下互相之间没有决策意义；只有最后一行能把 \(k\) 从 \(10^{6}\) 拉到 \(10^{0}\)。**这就是"防线在哪里"的全部答案：加固预算应该按"是否封堵攻击者可控量"排序，而不是按"是否让数字看起来更大"排序。**

### 4.4 两条结论的可迁移形式

对任何"人工转抄 + 服务端在线校验"的短码闸门（邀请码、设备码、短链、一次性口令、激活码），三步：

1. 算 \(k = N/(S\cdot R\cdot W)\)。
2. \(k \ge 10^{3}\) → 停止优化码长，全部预算转投：①身份完整性（限流键不可伪造）②泄露面（封顶/短窗口/吊销/归因）③防枚举（\(S\) 口径的销子）。
3. \(k < 10^{3}\) → 依次收紧 \(R\)、缩短 \(W\)、缩小 \(S\)（分批放量），**最后才考虑加长**。

## 5 正确加固动作（按决策顺序，不是按实现顺序）

以下每一条都能回溯到当时的实际动作或明确的待办，不是通用户外。

**① 守住限流键的身份完整性（最高优先）。**
开 CDN 的 Authenticated Origin Pulls，使源站只接受带合法客户端证书的请求；用 CDN 回源时自动附带的真实访客 IP 头去覆盖 `X-Forwarded-For` 再透传给应用，避免应用读到可自写的头（各厂商的自定义头名不统一，这里只写机制）。S 系统落地时踩了顺序与语法坑：**先开 CDN 侧开关，再 reload 反代**（说反会中断），且 `restart` 失败会直接把服务停掉造成 502。同源教训：反代协议头必须走白名单信任链，"无条件信任 `X-Forwarded-Proto`"这一弱点在另一批被堵并补了回归（当批后端全量用例一千六百余条全绿）。
> 验收方式：从公网直连源站 IP，伪造 `X-Forwarded-For` 打注册接口，确认**要么连不上，要么限流键落到真实来源**。这条不通，本文其余一切数字作废。

**② 把限流强度对齐参考线，并加次级键。**
主键（真实 IP）之外叠加"同 IP 段 / 设备指纹 / 会话"次级键，避免 \(I\) 靠 IPv6 段或代理池线性扩张。强度参考：ASVS v4.0.3 要求 2.2.1（CWE-307）明写"验证单个账号每小时失败尝试不超过 100 次"，并要求限速措施能扛住凭证库测试/暴破/锁号三种攻击（含递增延迟、CAPTCHA、风险判定）；该条文末自带的 NIST 映射列就是 §5.2.2。本文 §3.3 量出现闸门为 120 次/小时/IP，建议收一档到 72。缓解误锁的合法手段（CAPTCHA、递增等待、历史可信来源白名单、风险自适应）NIST SP 800-63B §5.2.2 列了同一组。

**③ 有效期取业务最短，且批量发码期临时收紧。**
\(W\) 是唯一"用户无感"的乘子（§4.3 表第 3 行）。3 天默认 + 30 天上限本身合理；但 §3.4 显示 \(S=35{,}300\) 档裕度掉到 \(3.6\times10^{2}\)，所以**大批量灌码（活动放量、压测）期间应临时降 \(R\) 或降 \(W\)**，而不是把峰值当常态。

**④ 名额封顶，不设无限次。**
本案例拍板值 100（"可用次数"入参 1–100，默认 1 保持向后兼容；用满自动作废）。定量语义见 §4.2：封顶管的不是撞码，是**单次泄露的最大损失**。

**⑤ 防枚举：统一错误口径是 \(S\) 的销子，不是隐私装饰。**
不存在 / 已用 / 已过期 / 已吊销 → 同一提示（见 §2.3 修正二的算术）。

**⑥ 一次性消耗 + 并发防双花。**
提交注册即消耗、用满即作废、抢最后一格只放行一人——撞中即作废意味着攻击者**没有静默验证通道**，必须用掉一个真实名额才能确认命中。

**⑦ 可归因与可吊销。**
管理端展示"已用 \(n/M\)"与完整使用名单（谁、账号 ID、时间，最近在前），支持状态筛选（未使用/已使用/已过期/已吊销）与服务端分页。这属于把"防不住"降级成"查得清"。

**⑧ 留痕：登录 IP 与凭据操作日志是上面第 ① 条的可审计前提。**
S 系统真实踩过：公网部署版本偏旧导致 `last_login_ip` 列不存在，管理员"看不到谁从哪登录"，一次入侵排查因此无法对号（本例即 §6 开头那次排查）。**闸门完好性如果没有可观测性，等于没有闸门。**

**明确不做的事**：不加长（§4.1）、不做无限次码、不扩字符表到含易混字符的 62 进制（把安全性换成抄错率）、不把"防枚举统一提示"改回"精确提示"以方便客服。

## 6 附节：语义缺口——"重置口令 ≠ 踢下线"

这一节与邀请码无关，但病根与本文完全同构，因此放在同一篇文章里。案例事实链取自作者自存的同一次审计记录（与 §5⑧ 那次排查同一段），下文时刻只作相对描述、账号一律匿名为"用户 U"。

**现象**：管理后台显示用户 U"未绑定"动态口令，但他已经登录在后台里。U 自述"右键登录进去了"。

**第一步归因（错的）**：系统有两扇独立的门——动态口令（TOTP）与 Passkey。经查代码，Passkey 登录通道的放行条件只有三条：凭据有效、账号未删除、未封禁——**完全不检查动态口令是否绑定**。所以"未绑定却能登录"可以解释为设计内行为：U 设备上存过 Passkey，浏览器右键快捷登录一点就进。这条推理方向对，但**不是本案正犯**。

**真凶**：管理员点"绑定/重新绑定"生成二维码的那一刻，系统只做了两件事——换新密钥（旧验证器 App 立即作废）、状态改为"未绑定"。**但没有作废已发出的登录门票**（会话 cookie，最长 7 天有效），而且登录态校验从头到尾不看"绑没绑定"，只看门票真不真。日志佐证：设备访问后台时处于登录态，而该时刻前后**没有任何登录请求**——用的就是旧门票。所以"刷新一下就进去了"不是刷新有魔法，是**旧门票从没被收走过**。

**缺口的一句话表述**：管理员心里"重置/重绑 = 让他立刻出局"，系统实际语义 = 只换钥匙、不收票、另一扇门照开。

**修法（三点同口径）**：

| 拦截点 | 行为 |
|---|---|
| 重置/重绑的瞬间 | 作废旧会话（会话版本号 +1，立即生效，不等下一次请求） |
| 登录态门禁（所有后台请求） | 未绑定 → 拒绝 + 指路文案 |
| Passkey 登录入口 | 未绑定 → 直接拒，同款提示 |

关键设计选择：**凭据不删，未绑定期间停用，重绑完成自动复活**。这样既拿到"重置 = 彻底锁门"的效果，又保留 Passkey 作为自助恢复通道——比"重置时连 Passkey 一起删"的杀伤面小得多。施工后三道门禁全绿：后端用例一千六百余条、前端八百余条、端到端十余条（精确计数不随稿公开，它是"改完验过"的证据强度而非论证输入）。

两个必须记下的边角：

- **管理员给自己重置会死锁**（确认接口会把他拦在门外）——这是"重置即锁门"语义的必然推论，兜底是服务器上的命令行重绑脚本。**任何"锁门"动作都该自带一条管理员救援路径。**
- 同批排查还挖出注册流程的**半程态缺口**：注册是两步（填码建号 → 扫码绑口令），而二维码页状态全在内存里，**刷新即清零**；此时码已消耗、账号未绑定、页面没有任何找回入口，唯一出路是管理员手工重绑。修法是复用"首绑确认"接口（只要账号 ID + 六位码）做找回入口，另允许"未完成绑定的空壳账号"用新码覆盖重建（同一批记录里还有一条前置合规设计：把验证器预告与隐私告知提到消耗一次性码之前，与本句同一课）。**一次性凭证的消耗时机与流程状态机，也要写进威胁模型，而不是只当作业务规则。**

**与主线的同构关系（这才是它值得进这篇的原因）**：

| | 你以为在防的 | 实际在防的 |
|---|---|---|
| 邀请码 | 码长 \(N\) | 闸门 \(R\cdot I\) 与窗口 \(W\) |
| 重置口令 | "重置"这个动作 | 门票（会话）集合是否被清空 |
| 半程注册 | 状态机走完了 | 凭证在哪一步被消耗 |

方法只有一条：**把每个"安全动作"翻译成"它之后仍然可用的凭证集合"，与"它之前可用的凭证集合"求差集，差集就是缺口。** 同理，把每个"防线参数"翻译成"攻击者所需预算"，预算不够大的参数就是装饰。

标准对照：ASVS v4.0.3 要求 3.3.3 规定"成功改密（含通过重置/找回改密）后，应提供终止其他所有活动会话的选项，并在应用与联盟登录范围内有效"（L2/L3，CWE-613）。注意两件事：①该条主语是**用户自己改密**，而本案例是**管理员侧重置/重绑**，落在条款之外——这正是多认证通道系统容易漏的缝；②"重置口令 ≠ 失效会话"在标准里是被明确要求的，不是可选的好设计。NIST SP 800-63B §5.2.2 另给出限速与误锁缓解的同源要求，可与 §5②对读。

## 7 局限与迁移须知

1. **参数是产品口径，不是推荐值。** \(C=32\)、\(L=8\)、\(R=10/5\text{min/IP}\)、\(W=3/30\) 天、\(S=50\) 全部是评估当时该系统的实现快照（见表 1）。换任何系统必须重新读代码取值；\(S\) 尤其不能当常数（它是发码节奏的函数，取峰值）。本文对 \(S\) 给了 50 / 3.53×10⁴ / 10⁶（历史累计）三档，就是防止读者把 50 当通用值。
2. **模型是"无放回均匀随机猜"。** 依赖 A3（CSPRNG、独立、无种子共享）。若码由时间/序号派生，\(N\) 立刻坍缩到可枚举，本文全部数字失效。
3. **期望值口径混用已标明。** \(E_1\) 用 \(N/S\)（原口径）与 \((N+1)/(S+1)\)（严格）两种都算了，差异 2.0%，不影响任何结论；抽干口径用 \(N\cdot H_{S}\) 近似。
4. **没建模真实主通道。** 撞码概率极低 ≠ 风险极低。码被转发到公开群、内部人员泄码、钓鱼，才是这类邀请制平台的主要泄露路径；本文只覆盖"在线暴力猜码"这一支，其余分支的对策恰好也是 §5④–⑦（封顶、短窗口、吊销、归因）。
5. **\(I\) 的门槛数是"需要多少"，不是"攻击者实际有多少"。** 本文没有做代理池市场调研，因此不宣称 \(2.5\times10^{6}\) 不可获得；恰恰相反，§4.1 用它来论证"别把希望放在这个数字上，去开 AOP"。
6. **三处数字不符已降级但保留原值。** 差异一（十几天 → 约 255 天）、差异二（200 万年 → 千万年量级）、差异三（完全一样 → 口径限定）。登记于 §3.3，脚本可复跑（附录 A）。
7. **抄写失败率模型未实测。** \(p=1\%\) 仅为演示二项放大效应；正式发表前应向客服工单/重填次数取基线，否则该表只作为"方向论证"存在（附录 B）。
8. **一次性凭证与状态机部分（§6）是案例证据，不是统计结论。** 单点事故，n=1。
9. **部署态风险。** 本文发表的是**当时已确认闭合**的缺口（AOP 已开）。发布前需复核现网仍闭合（附录 B 最后一条闸）。

## 8 结论

- 邀请码这类"人工转抄 + 服务端在线校验"的短码闸门，安全性可以用一个式子算清：\(k=N/(S\cdot R\cdot W)\)，而攻击者唯一能自己填的量是独立限流身份数 \(I\)。**\(k\ge10^{3}\) 之后，码长就不再是决策变量。**
- 算例口径下 \(k\approx2.5\times10^{6}\)、单身份 3 天窗口首中概率 \(7.86\times10^{-9}\)、攻击者需 \(\sim2.5\times10^{6}\) 个身份才可能压穿——**"现实不可行"成立，成立的原因是闸门，不是 8 位**。因此**加长是纯亏**（+24%/+47% 的整码抄写失败率换 \(\times32/\text{位}\) 的身份门槛，且闸门失守时归零）。
- **多次码 vs 一次码：撞码期望是否相同取决于口径**（名额口径恒等 / 命中集 50× / 抽干 4.50×），三者的量级都远小于闸门冗余，所以真正需要防的是**泄露面**：名额封顶（100）、短有效期、随时吊销、使用名单归因。
- 同一次审计顺带挖出的"重置口令 ≠ 踢下线"，与"码长 ≠ 防线"是同一种病：**把动作的名字当成了动作的效果**。统一修法是把每个安全动作翻译成"仍可使用的凭证集合"，逐条求差集。
- 复算本身是这篇文章的方法论交付物：10 项对外数字里 **7 项吻合、3 项不符并已降级标注**。任何"万年量级""完全一样"式结论，都值得先花十分钟把它写成四个输入值和一个除法。

## 附录 A 复算脚本思路与数字纪律清单

### A.1 脚本结构（不含任何生产数据，只吃表 1 输入值）

设计目标：**任何一项数字被改，整张表自动重算并自动重判**，而不是靠人记住"220 亿"是从哪个除法来的。

```
INPUTS（唯一事实源，逐条带稿内锚点）
  C = 32; L = 8
  R_per_ip_day = attempts_per_window * (86400 // window_seconds)   # 10 * 288 = 2880
  S = 50;  W_days = 3;  W_max = 30
  I_grid = [1, 1e3, 1e4, 2.55e6]
  S_grid = [50, 35300, 1e6]          # 当前可用 / 压测峰值 / 历史累计（枚举漏）

DERIVE（纯函数，禁止在正文里口算）
  N   = C ** L
  E1  = N / S                     # 原口径（表 1）
  E1x = (N + 1) / (S + 1)         # 严格口径（无放回）
  D   = E1 / (R * I)              # 天
  k   = D / W
  Ineed  = E1 / (R * W)           # 单身份恒等式：k == Ineed
  Sstar  = N / (R * W)            # 名额压穿阈值
  P1     = R * W / N              # 单身份窗口首中概率
  A_bar  = N * 2**-32             # RFC 8628 §5.1 类比达标所需窗口尝试上限
  E_drain = N * H(S)              # 抽干全部命中目标（调和数）

COMPARE（对每一条被引用的数字做四元组判定）
  for 每条 claim(名称, 原口径值, 表达式):
      rel = (复算 - 原口径) / 原口径
      verdict = "吻合" if |rel| <= 0.10 else "降级"
      输出 (名称, 原口径值, 复算值, rel, 是否影响结论方向)
  非"吻合"的条目必须落进差异登记表（差异一/二/…），并在正文就地改写，
  不允许"正文照抄原口径、附录另给复算值"两张皮。
```

三条实现纪律：① 所有对外数字必须是脚本输出，不允许从旧文里搬；② `INPUTS` 里每一行都挂稿内锚点，改值必须同时改锚点；③ 量级比较统一走 \(\log_{10} k\)（本文 \(k\approx2.5\times10^{6}\)，\(\log_{10}k=6.4\)），避免"万年 vs 200 万年"这类口算翻车——差异二正是这么翻的。

### A.2 数字纪律清单（本次复算的实际执法记录）

1. **无出处不引用。** 正文每个数字都指向一条稿内锚点（表 1 的行、或 §3.3 的原口径行）；锚点里没有的数字（例如本文新增的 \(I_{\text{need}}\)、\(S^{*}\)、\(P_1\)）在写作时单独标注"本文推导"，不混进"当时结论"。
2. **输入值原样用，不顺手修正。** 明写假设 \(S=50\) 是"假设"也照样算，不替换成自己觉得更合理的值。
3. **口径随行标注。** "每次 / 每身份 / 每小时 / 全局 / 单账号"不得跨口径并列——ASVS 的 100 次/小时是**单账号**，本案例 120 次/小时是**单 IP**，只能对读、不能判违规。
4. **原口径带"约"的先复算再决定保留。** 2880 复算为精确值 → 去"约"；2 万年复算为 20,905 → 保留"约 2.1 万年"。
5. **不符 → 就地降级 + 登记。** 登记五列：原值 / 复算值 / 比值 / 是否影响结论方向 / 处置。禁止把"十几天"改成"较长时间"这类含糊化逃过判定。
6. **被降级数字支撑的结论必须补边界证明。** 差异一：255 天 ≫ 30 天窗口 ⇒ 结论不变；差异二：结论依赖的是 ×32/位 的乘子，与绝对值无关；差异三：三口径分歧 ≤50× ≪ \(k=2.5\times10^{6}\)。
7. **反直觉断言必须标明成立区间。** "纯亏"仅对 \(k\gtrsim10^{3}\) 成立（§4.1 例外条款）；"完全一样"仅在名额除数口径成立（§4.2）。
8. **同义反复不算发现。** 把除数定义成"名额数"之后再断言"多次码与等量一次码相同"，是定义推论；必须换成命中集口径重算才能判断这句话有没有信息量。
9. **未实测的演示参数必须标"假设"并挂待办。** \(p=1\%\)（抄错率）、\(S=10^{6}\)（历史累计码数）属此类。
10. **每个乘子可一行复算。** \(32^{L}\)、\(\times32/\text{位}\)、\(2880=10\times288\)、\(120=10\times12\ \text{次/小时}\)——读者不该需要计算器来验证本文的自我批评。
